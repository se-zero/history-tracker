## 개요 (Overview)

whycode(서비스명 2026-08-23 확정 — 도메인 why-code.com, 워드마크는 소문자)는
GitHub·Jira·Slack을 비롯한 9종 소스에서 만든 Neo4j 지식그래프 위에서 추론해
"이 코드가 왜 이렇게 바뀌었나", "이 도메인을 가장 잘 아는 사람은 누구인가" 같은
질문에 답한다. 이 제품의 세계는 버전 관리·diff·터미널·코드 아카이브다 —
아래 모든 시각 결정은 일반적인 다크 SaaS 템플릿이 아니라 바로 그 세계에서 파생됐다.

**시그니처(기억에 남길 단 하나):** 지식그래프는 프로젝트 히스토리의 어두운 캔버스다.
질문을 보내면 스피너가 도는 동안 화면은 조용히 기다리고, 답변이 도착하는 순간
*텍스트와 함께 관련 노드와 그 사이의 경로가 앰버빛으로 켜진다.* 둘이 한 번에
해소되는 이 순간이 곧 제품이다. 디자인의 대담함은 여기에만 쓰고, 나머지는
전부 조용하게 유지한다.

기본 정체성은 **디폴트 다크가 아니라 "신경 쓴 다크"**다. 이 시스템이 피하려는 실패
모드는 AI가 만든 다크 룩(슬레이트 `#0f172a` + 블루나 acid-green 액센트 + Inter)이다.
탈출 방법 세 가지: 실제 elevation 레이어가 있는 틴트 near-black, 주연으로서의
모노스페이스, 그리고 절제해서 쓰는 근거 있는 앰버 액센트.

## 색 (Colors)

배경은 틴트된 near-black을 **4단 elevation 레이어**(`surface-0` → `surface-3`)로
쌓고, 각 단계는 의도적으로 한 칸씩 밝게 한다. 깊이는 무거운 테두리가 아니라
elevation에서 나온다 — 테두리는 헤어라인·저대비로 유지한다.

### 들린 표면과 섹션 지형

- **상단 엣지 하이라이트** — 들린 표면(카드, 미디어 슬롯, 커넥터 행 등 surface-2 이상)의
  위쪽 모서리에만 `edge-highlight` 1px 내부 하이라이트(`box-shadow: inset 0 1px 0`)를
  넣는다. 위에서 빛을 받는 질감이 표면을 "렌더링된" 것으로 만든다. 드롭섀도의
  대체물이지 병용물이 아니다 — 깊이는 여전히 surface 사다리와 헤어라인으로만 만든다.
- **섹션 전환은 "흐름"** — 긴 수직 흐름에서 섹션을 밝기 상승·경계선으로 급격히 나누면
  단절이 생긴다. 2026-07-26 같은 날 두 차례 사람 판정으로 확정: 초판(surface-1 한 단계
  변주)은 "여기만 색이 뜬다"로, 재판(surface-2 + 상하 헤어라인)은 "다른 페이지가 끼어든
  것"으로 읽혀 **둘 다 폐기**. 섹션 구분은 **여백 + 부드러운 톤 변화 + 콘텐츠 형식
  차이**(도식·카드·타이포)로만 만든다. 톤 변화가 필요하면 위로 밝히지 말고 **아래로
  깊어진다**(surface-0 → surface-canvas — "페이지가 깊어지며 끝나는" 최종 CTA가 원형).
  인접 surface 토큰 두 값 사이의 **무채 보간 이음**(수백 px 구간 linear-gradient)은 이
  원칙의 허용 기법이다 — 금지된 "대기 그라데이션"(장식용 컬러)과는 다르다. 컴포넌트
  프레임(카드·슬롯·미리보기)의 헤어라인은 섹션 경계가 아니므로 유지한다.
- **그래프 캔버스 층** — 그래프가 앉는 배경은 `surface-canvas`로 사다리보다 한 칸 더
  내린다. UI 표면(카드·패널·모달)은 여전히 `surface-0`에서 시작한다 — 이 층은 캔버스
  전용이다. 노드가 더 떠 보이고, 캔버스 구간과 `surface-0` 구간의 경계가 색차만으로
  생긴다. (첫 적용: 랜딩 히어로의 풀블리드 배경 그래프. 앱의 그래프 탐색 캔버스에도
  같은 층을 쓴다.)

이 규칙들은 랜딩 전용이 아니라 시스템 차원의 결정이다 — 앱 리스타일에도 그대로 적용한다.

### 네임스페이스 분리 (이 팔레트의 최상위 원칙)

색은 두 영역으로 나뉘고 서로 넘나들지 않는다. 영역을 가르는 기준은 *화면상의
위치*가 아니라 **그 색이 무엇을 가리키는가**다.

- **노드 타입 색**은 특정 그래프 노드를 지시할 때만 쓴다. 캔버스 안의 점과 범례
  칩은 물론, 캔버스 밖이라도 노드를 가리킨다면 쓴다 — 채팅 입력창의 첨부 노드 칩이
  대표적이다. (출처 카드는 2026-08-21 실앱 일치화로 타입 배지를 노드색에서 브랜드
  로고+무채 라벨로 바꿨다 — 카드↔노드 연동은 더 이상 색이 아니라 호버가 담당한다,
  컴포넌트 절 "출처 카드" 참조.)
- **시맨틱 색**은 시스템 상태를 말할 때만 쓴다. 노드를 지시하는 자리에는 쓰지 않는다.
- **액센트**만이 유일하게 두 영역을 넘나든다 — "선택됨"은 어디서나 성립하므로.

경계가 위치가 아니라 지시 대상이므로, 캔버스 밖이라고 노드 색이 금지되지 않고
반대로 노드와 무관하면 캔버스 근처라도 쓰지 않는다. 데이터 소스 카드의 커넥터
로고가 대표적인 금지 사례다 — Jira 로고는 어떤 노드도 가리키지 않으므로
`node-issue`가 아니라 Jira 브랜드 색을 쓴다.

이 규칙 덕분에 시맨틱과 노드가 같은 hex를 공유해도 충돌하지 않는다. `success`와
`node-commit`은 같은 초록이지만, 초록 점이 노드 라벨 옆에 있으면 "커밋"이고 상태
라벨 옆에 있으면 "정상"이다 — 색이 아니라 무엇을 가리키는지가 의미를 정한다.
색을 늘려 구분하는 대신, 색의 지시 대상을 분리해서 해결한다.

### 액센트

**액센트는 앰버(`#EBA23C`), 어디서나 의미는 하나다: "라이브 / 실행 / 선택".**
기본 CTA, 포커스된 입력, 선택된 그래프 노드, 답변 경로, 활성 내비 항목. 의미가
일관되기 때문에 이 색은 장식이 아니라 신호로 읽힌다. 두 번째 강조색은 절대 넣지
않는다 — 강조가 필요하지만 "라이브한 것"이 아니라면 텍스트 웨이트나 elevation으로 푼다.

이 규칙의 대가로 **앰버 계열(hue 약 60~90)은 액센트가 독점한다.** 노드 팔레트도
시맨틱 팔레트도 이 영역에 들어오지 않는다. 어떤 색이 앰버로 보인다면, 그것은
반드시 "지금 살아있는 것"이어야 한다.

### warning이 없는 이유

시맨틱 팔레트에 `warning`은 의도적으로 존재하지 않는다. 관용적인 경고색은 앰버·노랑
계열인데, 그것이 곧 액센트의 영역이다. 둘을 함께 두면 첫날부터 "앰버 = 라이브 신호"가
무너진다. 색을 억지로 좁은 hue 공간에 끼워넣는 대신, 갈 곳 없는 시맨틱을 없앤다.

경고에 해당하던 상태는 색이 아닌 다른 수단으로 표현한다:

- **지연 / 오래됨 / degraded** → `text-muted` + 모노 상태 라벨. 조용한 것이 맞다.
  동기화가 조금 밀린 것은 응급이 아니다.
- **결과 신뢰도 고지** → 색 없이. `text-muted` 본문 + 헤어라인 테두리 상자.
  "이 답변은 범용 그래프 탐색으로 나왔다" 같은 안내는 시스템 이상도 아니고
  사용자가 할 일도 아니다. 읽히되 답변 자체보다 앞서면 안 되므로 무채색이 맞다.
- **막힌 문제 / 파괴적 동작** → `danger`.
- **즉시 처리해야 하는 것** → `accent`. 이것은 액센트의 희석이 아니라 일관이다.
  액센트의 의미가 "실행"이고 "처리 필요"는 실행 어포던스이기 때문이다.
  단 규율 하나: **바로 옆에 누를 컨트롤이 실제로 있을 때만** 앰버를 쓴다.
  컨트롤 없는 단순 상태 표시에 앰버를 쓰는 순간 의미가 무너진다.

훗날 별도의 경고색이 정말 필요해지면, 앰버 쪽이 아니라 `danger`와 같은 hue의
저강도 버전으로 만든다 — 심각도를 하나의 hue 램프로 표현하고, 앰버 영역은
계속 액센트에게 남긴다.

### 노드 팔레트

**노드 타입 색은 무채도 통일 패밀리**로, 채도와 명도를 맞춰 7개 카테고리가 하나의
시스템으로 읽히게 튜닝한다. 이건 *타입*(노드가 무엇인가)을 담는다. 앰버 액센트는
*상태*(선택됨 / 답변 경로 위)를 담는다. 이 두 역할을 다른 색에 두는 것이 500개 노드가
빽빽한 그래프 안에서 강조된 트레이스를 읽히게 만든다. `node-file`은 가장 수가 많으니
가장 조용하게(cool grey) 둔다.

### 구현 노트

이 파일의 hex 값이 정본이다. 구현이 다른 색공간(oklch 등)을 쓴다면 여기서 변환하되,
**hue만 바꿔 파생시키지 않는다.** 특히 앰버는 명도가 높아야 앰버로 읽히므로, 기존
색상의 hue만 앰버로 돌리면 갈색이 된다 — 명도와 채도를 함께 다시 잡아야 한다.

라이트 테마에서 앰버는 구조적으로 까다롭다(흰 배경에서 대비를 맞추려 명도를 낮추면
갈색이 된다). 따라서 라이트 테마의 앰버는 **채움(fill) 위의 어두운 텍스트**로만 쓰고,
텍스트·보더용으로는 대비를 확보한 별도의 어두운 앰버 변수를 둔다. 액센트 hue의
명도만 낮춰 재사용하지 않는다. (이 원칙은 아래 라이트 테마의 `accent`/`accent-ink`
쌍으로 구현됐다.)

### 라이트 테마

2026-07-26 사람 승인으로 확정된 대응 토큰 세트다(frontmatter `colors-light`). **기본
테마는 여전히 다크**고, 현재는 랜딩의 다크/라이트 토글로 제공된다 — 제품 전면 채택
여부는 별도 판단으로 남아 있다. 라이트는 다크의 색 반전이 아니라 세 가지를 재설계한
결과다.

- **깊이의 주인이 바뀐다** — 라이트 사다리는 밝기 단조 증가가 아니다. 카드부터는
  흰색으로 고정하고(`surface-2` = `surface-3` = `#FFFFFF`), 층은 그림자 사다리
  (`shadow-sm/md/lg`) + 헤어라인이 만든다. 그림자는 라이트 전용이다 — 다크의 깊이는
  여전히 surface 사다리 + `edge-highlight`가 담당하고 그림자를 쓰지 않는다(다크 값
  `none`). `edge-highlight`는 라이트에서 끈다. 그림자 적용 기준은 "다크에서
  edge-highlight를 갖던 들린 표면"이다 — 카드·행은 sm, 들린 미디어·슬롯은 md,
  모달·팝오버는 lg.
- **우물이 반전된다** — 그래프 캔버스(`surface-canvas`)는 라이트에서 페이지보다
  가라앉은 회색이다. "톤 변화는 아래로 깊어진다" 원칙의 라이트 번역은 "회색으로
  깊어진다"다 — 어두워지는 것이 아니라.
- **액센트가 2단으로 갈라진다** — 채움(기본 CTA, 전송 버튼)은 앰버 `#EBA23C`를
  유지하고 위에 잉크 텍스트를 얹는다. 선·텍스트·링·점등 경로는 코퍼 `accent-ink`
  `#B3550B` — 앰버 hue의 명도만 낮춘 갈색이 아니라 hue를 오렌지 쪽으로 당기고 채도를
  유지해 재선정한 색이다. 다크에서 `accent-ink`는 `accent`와 동치이므로 구현은 참조만
  분리하면 되고 다크 시각은 변하지 않는다. **앰버 독점 규칙은 라이트에서 이 페어의
  독점으로 확장된다** — 채움 앰버든 코퍼든, 그렇게 보이는 색은 반드시 "지금 살아있는
  것"이어야 한다.

그래프는 라이트 실험의 핵심이었다. 다크의 "어두운 캔버스 위 발광"은 라이트에서
성립하지 않으므로 **"잉크로 찍힌 도식"으로 번역**한다: 노드 7종은 동일 hue 계열의
저명도 재선정(우물 위 전부 3:1 이상), 엣지는 전용 `graph-edge` 저대비 회색(노이즈
방지), 글로우는 소멸하고 라이브는 코퍼 스트로크의 **굵기 + 링 + 채도**로 읽힌다.
시그니처 순간("경로가 켜진다")의 의미는 유지되지만 질감은 인광이 아니라 형광펜에
가깝다.

외부 브랜드 마크의 다크 배경용 흰 변형은 라이트에서 보이지 않으므로 각 브랜드의
라이트 배경용 공식 변형으로 교체한다(GitHub 공식 `#181717` 도입은 승인 대기 — 현재는
잉크색 잠정 대체).

## 타이포그래피 (Typography)

세 티어로 나눈다: 헤딩(display), 본문·UI(body), 기술 데이터(mono). 각 스택은
**라틴을 앞에 두고 한글이 뒤로 흐르게** 구성한다.

### 한글을 어디에 둘 것인가

Space Grotesk·General Sans·JetBrains Mono에는 한글 글리프가 없다. 그런데 이 제품의
UI 텍스트는 대부분 한글이므로, 한글 폴백으로 무엇을 두느냐가 곧 "제품 서체"를 정한다.
Pretendard를 전 티어에 쓰면 사실상 Pretendard가 제품 서체가 되는데, Pretendard는 한국
제품의 디폴트(한글판 Inter)라 이 시스템이 피하려는 "디폴트 티"와 정확히 겹친다.

그래서 티어별로 나눈다.

- **헤딩(display)** — 개성은 여기에서만. 한글은 Wanted Sans가 받는다. 헤딩은 절제해서
  쓰므로 개성 있는 서체를 써도 화면을 지배하지 않는다.
- **본문(body)** — 한글은 Pretendard. 15px 산문 가독성이 개성보다 우선이고,
  "디스플레이는 절제해서, 본문엔 쓰지 않는다"는 원칙과도 일치한다.
- **모노(mono)** — 서체를 더 늘리지 않고 스코프로 해결한다(아래).

### 디스플레이 트래킹

디스플레이 서체 헤드라인에는 네거티브 트래킹 `-0.02em`을 기본으로 건다. 기본(0)
트래킹의 헤드라인은 다크 배경에서 느슨하게 풀려 보인다. 한글 헤드라인(Wanted Sans)에도
같은 값이 과하지 않음을 렌더로 확인했다 — 특정 조합에서 뭉치면 `-0.015em`까지만
완화한다. 본문·모노에는 적용하지 않고, eyebrow는 자체 트래킹 규칙(`0.08em` / 한글 0)을
따른다.

### 모노의 스코프

JetBrains Mono에도 한글이 없다. 여기서 한글 모노 서체를 하나 더 들이는 대신, 모노를
쓰는 범위 자체를 좁힌다.

- **모노를 쓴다** — 라틴 기술 토큰: 키(`PAY-64`), 해시, 타임스탬프, 파일 경로, 대문자
  eyebrow 라벨.
- **모노를 쓰지 않는다** — 한글이 포함된 콘텐츠는 데이터 맥락이라도 본문 서체로
  조판한다. 커밋 메시지, Slack 본문, 출처 카드의 내용 줄이 여기 해당한다. 정렬이 꼭
  필요한 표에서만 D2Coding 폴백을 쓴다.

"모든 기술 데이터는 모노"라는 원래 규칙은 유지되지만, 그 대상이 *라틴 기술 토큰*으로
좁혀진 것이다. 한글 문장을 모노로 조판하면 질감이 아니라 사고처럼 보인다.

### 혼용 조판 디테일

라틴과 한글이 한 줄에 섞이면 아래 넷을 맞춰야 한다.

1. **size-adjust** — 한글 폴백 `@font-face`에 92~96%. 한글은 같은 `font-size`에서
   라틴보다 크고 무겁게 보이기 때문이다. 단 `size-adjust`는 `@font-face` 디스크립터라
   그 선언을 우리가 소유해야 하고, CDN 동적 서브셋(유니코드 레인지별 다수
   `@font-face`)에는 적용할 수 없다. **자체 호스팅/서브셋이 전제이며 현재는 보류다.**
2. **웨이트 매핑** — 한글은 시각 무게가 커서 한 단계 낮춘다
   (Space Grotesk 600 ↔ 한글 500~600).
3. **eyebrow 트래킹** — `0.08em`은 대문자 라틴 전용이다. 한글에 자간을 넓히면 깨져
   보이므로 한글 eyebrow는 트래킹 0.
4. **행간** — 본문 15px 기준으로 라틴 1.5~1.6, 한글 1.7~1.75.
5. **여러 줄 꺾임** — 줄바꿈이 생길 수 있는 한글 헤드라인·짧은 본문 블록에는
   `word-break: keep-all`과 `text-wrap: balance`를 함께 건다. 기본 줄바꿈은 좁은
   화면에서 "알려준다." 같은 서술어 하나를 고아 줄로 남기는데, 조판 사고처럼 보인다.
   keep-all이 어절 중간 꺾임을 막고 balance가 줄 길이를 고르게 나눈다.
   단, 긴 산문 문단에는 balance를 걸지 않는다 — 줄 수가 많으면 오히려 어색해진다.

**display(제목) 서체는 공개 페이지(랜딩·약관·개인정보) 전용이다(2026-08-21 사용자
결정) — 앱은 제목·본문 모두 Pretendard를 쓴다.** 앱은 도구형 UI라 큰 제목이 서너 곳
(온보딩 h1, 채팅 빈 화면 h2, 페이지 타이틀)뿐이고 전부 한글이라, Wanted Sans로 바꿔도
체감이 작다는 판단에서다. 다만 **모노 스코프 규칙(라틴 기술 토큰 전용)과 본문 티어,
혼용 조판 규칙(size-adjust·웨이트 매핑·트래킹·행간·꺾임)은 앱과 공통으로 유지**한다 —
이 셋은 헤딩 서체 선택과 무관하게 한글·라틴 혼용 자체에서 나오는 규칙이기 때문이다.

**랜딩 영문 헤드라인은 Space Grotesk가 아니라 Wanted Sans를 쓴다(2026-08-24 사용자
확정).** 한글 헤드라인이 전부 Wanted Sans 폴백으로 렌더되므로 제품이 실제로 보여 온
디스플레이 서체는 처음부터 Wanted Sans였다 — 영어 버전이 스택 첫 번째 Space Grotesk를
처음으로 실노출하자 "한글판과 다른 제품 인상 + 각짐"이 생겼다(사용자 실물 판정). 언어를
바꿔도 같은 제품으로 보이도록 영문 헤드라인도 Wanted Sans(weight 600 — 한글 500과의
웨이트 매핑 등가)로 통일한다. 스택 선언은 바꾸지 않고 랜딩 en 스코프
(`.lp[data-lang="en"]`)에서 적용만 뒤집는다 — 신규 서체 아님(한글용으로 이미 로드되는
패밀리의 라틴 글리프). 같은 라운드에서 **히어로 eyebrow는 라벨이 아니라 문장형**이라
양 언어 모두 본문 서체·트래킹 0으로 확정했다(대문자 라틴 모노 eyebrow 규칙은 섹션
라벨(HOW IT WORKS 등)에만 적용 — 히어로는 한글판 예외의 영문 확장).

## 간격과 레이아웃 (Spacing & Layout)

4px 베이스 그리드. 산문(채팅 답변)에는 넉넉한 수직 리듬, 데이터 표면(그래프 범례,
출처 카드, 데이터 소스 행)에는 더 촘촘한 밀도. 코너 radius는 중간값 — 카드·입력은
`md`(10px) — 이 정밀한 느낌은 pill처럼 둥글지도, 브루탈리즘처럼 각지지도 않다.
`pill` radius는 필터 칩과 상태 태그에만 예약한다.

앱 코어 레이아웃은 3단 셸이다: 좌측 레일(내비 + 대화 히스토리), 중앙 컬럼(채팅
스트림, 답변 가독성을 위해 최대 ~760px), 우측 패널(관련 그래프 — 보여줄 게 있을 때만 슬라이드).

## 모션 (Motion)

모션은 상태를 전달한다; 절대 장식이 아니다. 브라우저 기본 이징이 곧 로봇 같은 "AI"
티이므로, 위 토큰으로 전역 교체한다.

- **그래프:** force-directed 노드는 스프링 물리로 정착한다(linear 스냅 금지). 호버 시
  해당 노드의 이웃을 하이라이트하고 나머지는 ~20%로 딤 — 이건 빽빽한 그래프 가독성
  문제의 해결책이기도 하다. 선택 시 이웃으로 스프링 줌 후 앰버 링 + 헤일로를 그린다.
- **시그니처 순간:** 답변은 완성된 뒤 한 덩어리로 도착한다. 그 순간 답변 텍스트가
  페이드+상승으로 들어오고, 우측 패널에서 인용된 노드와 그 사이 엣지가 앰버빛으로
  켜지며 나머지는 딤 처리된다 — 텍스트와 그래프가 함께 해소된다.
  (서버가 응답을 한 번에 반환하므로 토큰 단위 스트리밍은 현재 범위 밖이다.)
  구현 확정(2026-08-22, 실물 확인): 텍스트는 도착 즉시 `duration-slow`/standard로
  상승하고 출처 카드는 120+70i ms 스태거. 그래프 점등은 서브그래프 조회(별도 왕복)가
  끝나는 렌더 시점에 시작한다 — 엄밀한 동시가 아니라 "연이어 해소"가 실측 감각이며,
  텍스트를 조회 완료까지 붙잡지 않는다. 점등은 인용 순서의 순차 체인: 노드 발화
  280ms(링·헤일로는 `easing-spring`) + 실존 엣지 드로잉 600ms 교대, 순차는 앞 3개까지,
  나머지 시드·엣지는 마지막 박자에 일괄 — 총길이 2040ms 상한. 재생은 **패널이 열린
  상태에서 새 답변이 도착했을 때 1회뿐** — 과거 대화 로드·활성 전환·나중에 연 패널은
  즉시 최종 상태(앰버 링·경로는 상시 표시라 안무 종점과 같은 그림)다.
- **패널·카드:** 우측 그래프 패널은 `duration-slow`로 열린다. 이징은 **`easing-standard`다
  — `easing-spring`을 쓰지 않는다.** 이 패널은 얹혀서 미끄러져 들어오는 오버레이가 아니라
  본문과 폭을 나눠 갖는 열이라, 오버슛을 걸면 패널이 목표 폭을 넘었다 돌아오는 동안
  읽고 있던 중앙 본문까지 함께 밀렸다 당겨진다. 실물로 확인하고 내린 결정이다(2026-08-22).
  출처 카드는 `easing-standard`로 페이드+상승.
- **마이크로:** 호버/포커스는 `duration-fast`; 버튼엔 미묘한 프레스. 답변 대기는
  스피너로 알리되 장식적으로 키우지 않는다 — 조용한 회전 + "처리 중" 한 줄이면 충분하다.
- `prefers-reduced-motion` 준수: opacity 변화는 유지, transform과 graph-settle
  애니메이션은 제거(최종 위치로 즉시 점프).

## 컴포넌트 (Components)

- **채팅 답변:** 어시스턴트 텍스트는 General Sans 산문(버블 없음); 사용자 메시지는
  `surface-2` 버블에 우측 정렬. 대기 중엔 스피너, 답변은 완성된 상태로 한 번에 렌더된다.
- **출처 카드:** `surface-2`, `radius-md`. `#N` 모노 칩, 브랜드 로고 + 무채 타입 라벨
  (issue / message / PR — 2026-08-21 실앱 기준 반영, 이전의 노드색 틴트 배지는 폐기),
  작성자, 모노 날짜, 인용문 한 줄. 카드에 호버하면 우측 패널의 대응 노드가
  하이라이트되고(역방향도) — 카드↔그래프 연동은 이제 색이 아니라 이 호버 연동이 담당하며,
  여전히 핵심 차별점이다.
- **그래프 캔버스:** 노드 = 채워진 점(노드 타입 색) + 모노 라벨; 엣지는 헤어라인·저투명.
  범례/필터 = 노드 색 pill 칩, 토글로 필터링. 앰버 링 + `accent-glow` 헤일로의 주인은
  **인용(시드) 노드**다(관련 그래프 패널, 상시 — 시그니처 점등의 종점이 곧 정적 상태).
  선택 노드는 노드색 헤일로를 유지한다(2026-08-22 실앱 기준 — 앰버는 "근거"에만 쓴다).
  줌 컨트롤은 `surface-2`로 우하단에 플로팅.
- **데이터 소스 카드:** 커넥터 로고, 모노 sync 상태, 기본 액션 하나. 커넥터 로고는
  각 서비스의 브랜드 색을 쓴다 — 노드를 가리키는 게 아니므로 노드 색을 빌리지 않는다.
- **버튼:** 기본 = 앰버(`accent`), "실행" 색; 보조 = `surface-2` + `border`;
  고스트 = 텍스트 + 호버 틴트. focus-visible 링은 앰버.
- **eyebrow/라벨:** 대문자 JetBrains Mono, `eyebrow` 트래킹, `text-muted`.

## 랜딩 페이지 (Landing Page)

앱과 동일한 다크 정체성 — 랜딩과 제품은 연속적으로 느껴져야 한다(밝고 말랑한 랜딩
뒤에 어두운 기술 앱이 뜨면 로그인 시 신뢰가 깨진다).

**포지셔닝 한 줄:** 머지되면 사라지는 개발 맥락을, 지식그래프로 되살려 자연어로 질문한다.

랜딩 최우선 품질 목표: **"AI가 만들어준 것 같다"는 인상이 나지 않을 것.** 아래 중
하나라도 해당하면 실패다 — 슬레이트(`#0f172a`) + 블루 + Inter; near-black +
acid-green/vermilion; 컬러풀 blob·3D·무지개 그라데이션; 브라우저 기본 이징; 좌우
50:50 대칭 히어로 + 중앙정렬 디폴트 여백; 어느 SaaS에나 성립하는 카피.

실행 방식은 Notion(영상 히어로·섹션 리듬), 진정성은 Linear/Vercel(실제 UI), 톤은
Cursor(개발자·절제). 노션의 스킨(라이트·말랑한 3D)은 쓰지 않는다.

| 레퍼런스 | 가져온 것 | 버린 것 |
|----------|-----------|---------|
| Notion | 영상 히어로, `모노 eyebrow → 헤드라인 → 실제 화면` 리듬, 레이어드 스크린샷 | 라이트·3D 이모지·대중 톤 |
| Linear | 다크 네이티브, 실제 UI, 밀도 | — |
| Vercel | 히어로가 제품을 시연, 목적 있는 모션 | — |
| Cursor | 개발자 톤, 절제된 카피 | — |

랜딩 전용 값은 공유 `tokens.css`에 `--lp-*`로만 추가한다(앱의 `--surface-*` 등과
이름이 겹친다). 별도 파일로 포크하지 않는다. 커넥터 브랜드 색은 `--brand-*`(외부
자산 — 앰버 독점 비대상).

### 레이아웃 기준선

모든 섹션은 `padding-inline: 32px`(모바일 24px)을 갖고, inner는 `max-width: 1200px`의
순수 컨테이너다. 헤더 로고·히어로 텍스트·히어로 슬롯·문제 정의~푸터가 **같은 좌측
기준선**에 앉는다(1440 뷰포트 실측 x=115). 한 섹션만 inner에 패딩을 넣으면 기준선이
어긋난다.

`scroll-snap`은 금지(접근성·리듬 붕괴). `#how`의 `scroll-margin-top: 64px`(sticky
헤더 보정)만 예외다.

### 섹션 리듬

같은 형식을 연속으로 나열하지 않는다.

| 섹션 | 형식 |
|------|------|
| 히어로 | 상단 텍스트(좌측 정렬) / 하단 전폭 제품 UI 영상 슬롯(하단만 폴드 크롭) |
| 문제 정의 | 타이포만, 뷰포트 높이·세로 중앙 — 숨 쉬는 자리 |
| 작동 방식 | 3단 가로 개념 도식(점 격자, 자기 화면 세로 중앙) |
| 기능 1~3 | 좌/우 교차. 기능 2만 우 텍스트 / 좌 미디어 |
| 유스케이스 | 카드 그리드 |
| Slack 앱 | 좌측 정렬 타이포 + 세로(모바일)·3단(데스크톱) 설치 스텝. 미니 그래프·카드 없음 |
| 최종 CTA | 중앙 집중, 넓은 여백 |
| 푸터 | 미니멀 |

신뢰 스트립(고객 로고)은 **두지 않는다** — 히어로 eyebrow가 이미 소스를 말하고, 로고
없는 스트립은 약한 섹션이다.

### 카피 규칙

아래 확정 카피는 임의로 다시 쓰지 않는다. 한국어가 원문이고, 영어는
`LandingLanguageProvider`의 `Localized` 사전 — 원문을 고치면 번역도 같은 승인으로
함께 고친다. 언어를 바꿔도 데스크톱 섹션·컨테이너 크기는 한국어 기준과 픽셀 같아야
한다(상세는 `docs/i18n.md`).

**카피에 내부 구현을 노출하지 않는다** — 노드/엣지 정의, Neo4j 등 스택 이름. 사용자
자산(커밋·PR·이슈·대화·문서)과 제품 경험으로서의 "그래프"는 허용.

소스 나열(`GitHub, Jira, Slack`) 대신 **자산 중심**(`코드, 티켓, 대화, 문서`)으로
쓴다 — 소스가 늘어도 낡지 않는다. 브랜드 폭은 기능 3 카탈로그가 전달한다.
예외: Slack 앱 절은 마켓플레이스·Installation landing page가 가리키는 자리라
워크스페이스·커맨드 이름을 그대로 쓴다.

### 로고

어두운 라운드 타일 위 그래프에서 세 노드를 잇는 경로만 앰버로 점등("트레이스",
2026-08-23). 정본은 `public/favicon.svg` 하나이고 헤더 `<img>`가 같은 파일을 그린다.
테마 불변. 로고 앰버는 답변 경로 점등과 지시 대상이 같아 액센트 규칙에 맞다.

### 히어로

상하 구조: 위 텍스트(좌측 정렬) → 아래 전폭 슬롯. **잘림은 하단(첫 화면 폴드) 한
방향뿐.** 슬롯 비율 `1280/675` ≈ 1.9:1, 폭은 콘텐츠 100%(기준선 공유). 16:9 녹화는
상하 크롭이 크롬을 잘라 기각 — 녹화 자체를 1.9:1로 찍고 최종 인코딩은 표시 크기의
2배(2400×1266).

- **카피:** eyebrow `개발 히스토리를 위한 지식 그래프`(한글이므로 모노 금지) →
  헤드라인 `코드베이스의 모든 결정을, 되짚을 수 있게.`(마침표는 본문 색, 앰버 아님)
  → 서브 `흩어진 커밋·PR·이슈·대화·문서를 하나의 그래프로 묶어, 물으면 근거와 함께
  답합니다.` CTA `GitHub으로 시작`(accent 채움, OAuth 직행).
- **데스크톱(≥768px):** 실녹화 영상. 파일명 `hero-demo-{lang}-{theme}.*`(언어×테마
  4벌). `prefers-reduced-motion`이면 poster 정지. 파이프라인은
  `clients/web-dashboard/tools/hero-video/`.
- **모바일(<768px):** 영상이 아니라 DOM 목업 — 모바일 UI 완성 전 주력 자산으로 유지.
- **히어로 앰버 허용:** CTA primary, focus ring, 관련 그래프 점등 링·헤일로·경로,
  컴포저 전송 버튼, 헤더 로고. 레일 활성은 중립 강조(surface-2) — 앰버가 늘면 패널
  점등이 묻힌다.

### 문제 정의

```
git blame은 누가 바꿨는지 알려준다.
왜 바꿨는지는 아무도 모른다.

결정은 Slack에, 근거는 티켓에, 결과만 코드에 남는다.
셋 다 검색되지만, 그 사이의 관계는 어디에도 저장되지 않는다.
```

`git blame`만 모노. 이미지·앰버 금지. ≥768px에서 `min-height: calc(100svh - 64px)` +
콘텐츠 세로 중앙.

### 작동 방식

```
eyebrow: HOW IT WORKS
헤드라인: 연결하고, 묻는다. 그 사이는 자동이다.
01 / 연결 — 저장소와 워크스페이스를 연결한다. 코드, 티켓, 대화, 문서.
02 / 구축 — 흩어진 기록 사이의 관계를 찾아 하나의 히스토리 그래프로 엮는다.
03 / 질문 — 자연어로 묻는다. 답과 함께, 근거가 된 노드와 경로가 돌아온다.
```

실제 제품 UI가 아니라 **개념 도식**이 최종 형태다. `01/02/03`은 모노. 같은 노드
배치에서 01 엣지 0개 / 02 클러스터 / 03 앰버 경로+나머지 딤. 도식 신호는 점 격자
(블루프린트) — 실제 캔버스(우물)와 구분. 03의 앰버는 시그니처와 같은 "답변 경로".
`howItWorksGraph.ts`는 이 섹션 전용.

### 기능 3섹션

미디어 슬롯은 스크린샷 대체가 아니라 **이 파일 토큰으로 만든 라이브 DOM**이다.
원칙: **축소하지 말고 잘라내라.** 실제 스크린샷/영상 교체는 선택.

```
CHAT — 답과 근거를 함께 돌려준다.
GRAPH EXPLORER — 코드베이스를 지도처럼 본다.
DATA SOURCES — 한 번 연결하면, 계속 쌓인다.
```

기능 1은 실앱 대화(레일·2열 출처 카드·컴포저). 기능 2는 실앱 작업 단위 뷰 축소
재현 + 점등 트리오(PAY-64 → PR #142 → #dev-pay). 기능 3은 실앱 소스 화면(연동 중
행 + 추가 가능 타일).

**데모 세계관(payflow):** 프로젝트·티켓·org 경로는 히어로 영상과 같다(`payflow`,
`PAY-*`). **질문·스토리는 영상과 다르게 유지**한다 — 질문 폭을 보여 주기 위함.
티켓 번호는 영상(PAY-218 계열)과 겹치지 않게. 히스토리 제목은 그럴듯한 데모
데이터(실제 앱의 `6060`·`테스트` 금지). 단일 출처는 `demoCopy.tsx`.

**미리보기 앰버 허용:** 기능 1 활성 내비(accent-soft), 기능 1 전송 버튼, 기능 2
점등 트리오의 링·헤일로·경로. 그 외 미리보기는 무채.

eyebrow: USE CASES

### Slack 앱

마켓플레이스와 Slack 앱 설정의 Installation landing page가 `/landing#in-slack`로
착지하는 절. Add to Slack(direct install)은 등재 후 항목이라 두지 않는다 —
설치 경로는 GitHub 로그인 → 프로젝트 → 소스에서 워크스페이스 연결.

```
eyebrow: IN SLACK
헤드라인: Slack 안에서 묻는다.
본문: 채널에서 /why-code 뒤에 질문을 붙이면, 연결된 그래프에서 답을 찾아
      본인에게만 보여 줍니다. 설치는 Slack이 아니라 GitHub 로그인으로 시작합니다.
01 / 시작 — GitHub으로 로그인한 뒤 프로젝트를 만듭니다.
02 / 연결 — 소스에서 Slack 워크스페이스를 고릅니다.
03 / 질문 — 채널에서 커맨드 뒤에 질문을 적습니다.
고지: 답은 AI가 그래프를 근거로 만든 것이며, 사실과 다르거나 빠질 수 있습니다.
링크: 개인정보처리방침 · 지원
```

`/why-code`와 `01 /`만 모노. 고지는 무채 헤어라인 상자(결과 신뢰도 고지 규칙 —
앰버 금지). 실행 버튼 없음(히어로·최종 CTA의 GitHub CTA와 중복).

## 보이스와 카피 (Voice & Copy)

정밀한 개발자 동료처럼 쓴다 — 담백하고, 구체적이고, 약간 포렌식/아카이브적으로.
사용자가 제어하는 것으로 명명한다("커넥터 config"이 아니라 "데이터 소스"). 컨트롤은
능동태로: 버튼은 무슨 일이 일어날지 정확히 말한다. 에러는 사과하지 않고, 무엇이
왜 깨졌고 어떻게 고치는지 절대 모호하지 않다. 빈 상태는 장식된 공백이 아니라 첫
질문을 던지라는 초대다.

랜딩 카피는 위 「랜딩 페이지」 절의 확정문이 정본이다. 내부 데이터 모델·스택 이름을
마케팅 문장에 넣지 않는다.
