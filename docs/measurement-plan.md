# 정량 측정 계획 (GraphRAG 품질 eval)

작성일: 2026-07-03 · 수정일: 2026-07-05 (선행 작업 계획 병합)

> **스코프**: 이 문서는 **응답 품질 측정**만 다룬다. 데이터 처리 효율(수집 처리량·지연·비용)
> 측정은 별도 문서로 분리한다.

---

## 배경과 목적

현재 그래프 연결과 응답 품질이 MVP 기준에 미치지 못해, 앞으로 그래프 연결 로직 개선과
응답 품질 개선 작업을 반복적으로 진행할 예정이다. 이때 개선이 실제로 효과가 있었는지를
감(感)이 아니라 **숫자로 검증**하기 위한 측정 체계를 정의한다.

측정 체계가 있으면:

- 개선 작업 하나하나의 효과를 "변경 → 점수 변화"로 확인할 수 있다.
- 새 기능 추가나 리팩토링이 기존 응답 품질을 몰래 떨어뜨리는 **회귀를 감지**할 수 있다.
- Redis 도입 같은 인프라 변경이 품질에 영향을 주지 않았음을 증명할 수 있다.

---

## 측정 층 구조 — 엣지 레벨과 e2e 레벨

측정은 두 층으로 나눈다. e2e 하네스의 주 지표(evidence recall·환각률·사실 정답률)는
구조적으로 **잘못된 엣지(false positive)에 둔감**하기 때문이다.

- recall은 필요한 근거를 찾았는지만 재고, 엉뚱한 근거가 딸려와도 감점하지 않는다.
- 환각률은 "summary가 인용된 evidence로 뒷받침되는가"를 재므로, **잘못 연결된 메시지를
  충실하게 요약한 문장은 환각으로 잡히지 않는다.**
- 사실 정답률은 기대 사실이 담겼는지만 보고, 잘못된 엣지가 주입한 틀린 추가 주장은 잡지 못한다.
- 질의 경로의 confidence 필터(`_MIN_CONFIDENCE`)는 TRIGGERED_BY에만 적용되고
  REFERENCE 순회에는 없어서, 저신뢰 엣지가 답변에 그대로 흘러든다.

| 층 | 대상 | 지표 | 용도 |
|---|---|---|---|
| **엣지 레벨** | 그래프 연결 (시맨틱 엣지) | 엣지 precision / recall | 그래프 개선 루프의 주 지표. 빌더 변경 → 지표는 인과 사슬이 한 칸이라 귀속이 명확하고, `/query` 실행이 없어 한 번 도는 데 몇 분·몇 센트 수준 |
| **e2e 레벨** | `/query` 응답 전체 | evidence recall · 환각률 · 사실 정답률 등 | "그 결과 사용자 답변이 실제로 좋아졌나"를 확인하는 상위 층 |

그래프 개선 루프는 엣지 레벨 지표로 돌리고, e2e 하네스는 상위 확인 층으로 쓴다.

## e2e eval 하네스

LLM 응답에 대한 **자동 채점 시스템**이다. 유닛 테스트는 "입력 X → 출력이 정확히 Y인가"를
pass/fail로 판정하지만, LLM 응답은 실행마다 문장이 달라 정확 일치 비교가 불가능하다.
그래서 pass/fail 대신 **점수**를 매기고, 코드 변경 전후의 점수 변화를 추적한다.

구성 요소는 세 가지다.

### 1. 골든셋 (golden dataset)

정답을 아는 질문 모음. 사람이 직접 그래프를 뒤져서 기대 근거와 핵심 사실을 정의한다.
20~40케이스 규모면 충분하며, `docs/query-quality-issues.md`의 케이스 1~9가 초기 씨앗이 된다.
현재 시스템이 틀리는 질문을 의도적으로 포함해야 개선 여지가 숫자로 드러난다.

케이스 예시:

```yaml
id: case-07
question: "HT-3 작업의 배경과 변경 내용을 알려줘"
focus_evidence: []            # 노드 선택 질문이면 /query 요청 형식 그대로: [{type: issue, id: HT-3}]
expected_evidence_ids:        # 반드시 인용돼야 할 근거 (recall 분모)
  - "issue:HT-3"
  - "commit:abc1234"
  - id: "message:1778586053.322069"   # 메시지 id는 스레드 루트 ts(conversation_id)로 기록
    aliases:                          # 리플라이 ts — id 정규화 매치용 별칭
      - "message:1778590761.356869"
acceptable_evidence_ids:      # 인용해도 감점하지 않는 추가 근거 (precision 판정에만 사용)
  - "issue:HT-3-1"
expected_facts:               # summary에 담겨야 할 핵심 사실 (LLM-judge가 판정)
  - "하위 이슈 HT-3-1의 커밋이 실제 변경을 담당"
  - "Slack에서 스키마 논의가 선행됨"
expected_absent:              # 오염 감지 — 등장하면 감점
  evidence_ids: []            #   인용되면 안 되는 근거 (알려진 잘못된 엣지가 끌어오는 노드)
  facts: []                   #   summary에 담기면 안 되는 사실 (근거 없는 추론 등)
rule_checks:                  # 케이스별 기계 채점 검사 (키워드·필드 존재 검사 수준)
  - "summary에 슬랙 언급 시 type: message evidence 존재"
```

- 노드 선택 질문은 하네스 전용 표기(anchor_node_id 등)를 만들지 않고 `/query`의 실제
  요청 필드 `focus_evidence`를 그대로 쓴다 — 러너에 변환 계층이 생기지 않고, API 스키마가
  바뀌면 골든셋도 같이 마이그레이션하면 된다. 일반 질문과 노드 선택 질문을 같은 하네스로 채점한다.
- **Stage 1 스코프는 단발 질문**이다. 멀티턴 후속 질문(history·prior_evidence·running_summary)
  채점은 스키마에 해당 슬롯을 추가하는 확장으로 미룬다.
- `expected_absent`는 잘못된 엣지·근거 없는 추론이 답을 오염시키는 **알려진 케이스**에 쓴다.
  recall·사실 정답률이 구조적으로 못 잡는 false positive를 케이스 단위로 잡는 장치다.
- `rule_checks`는 채점기의 "규칙 검사"에 들어가는 케이스별 항목이다. 기계로 판정 가능한
  수준(키워드·필드 존재 검사)으로만 적는다. 그래프에 답이 없는 "왜" 질문은 expected_facts를
  그래프에 실제로 있는 사실로 제한하고, "unknown_aspects에 '배경 미확인' 취지 항목 존재"
  같은 rule_check로 **모른다고 인정했는가**를 정답으로 표현한다.
- 케이스를 추가하면 **골든셋 버전을 올린다**. 버전이 다른 측정끼리 비교할 때는 공통
  부분집합으로 비교한다 — 케이스 추가만으로 집계 점수가 출렁이는 것을 막는다.
- 케이스당 YAML 파일 하나로 관리한다 (예: `eval/golden/case-01.yaml`) — 케이스 추가가
  git diff로 남아 골든셋 버전 관리와 자연스럽게 맞물린다.

### 2. 러너 (runner)

골든셋의 질문을 하나씩 ai-engine `/query`에 **직접** 던지고(backend 미경유 — ai-engine 품질만
격리 측정) 구조화 응답을 수집하는 스크립트. LLM은 비결정적이므로 **케이스당 3회 실행해 평균**을 낸다.

### 3. 채점기 (grader)

응답을 점수화한다. `/query` 응답이 Structured Outputs로 `summary` + `evidence[]`
(엄격한 id 형식) + `unknown_aspects[]`를 강제하므로, 채점의 상당 부분을 기계적으로 처리할 수 있다.

**기계 채점** — 문자열 비교만으로 판정, 비용 없음:

| 지표 | 정의 | 의미 |
|------|------|------|
| evidence recall | `expected_evidence_ids` 중 실제 인용된 비율 | 필요한 근거를 찾아왔는가 (검색 품질) |
| evidence precision | 인용된 evidence 중 expected+acceptable에 있는 비율 | 엉뚱한 근거를 끌어오지 않았는가 |
| 오염 검사 | `expected_absent.evidence_ids`가 인용되지 않았는가 | 잘못된 엣지가 답에 새는지 |
| 규칙 검사 | id 포맷 위반 + 케이스별 체크 (예: summary에 슬랙 언급 시 `type: message` evidence 존재) | 시스템 프롬프트 규칙 준수 여부 |

**id 비교는 정규화 후 수행한다.** 현 시스템의 알려진 결함 중 상당수가 id 포맷 자체에 있어서다
(PR `"19"` vs `"#19"`, 커밋 해시 6자리, 리플라이 ts vs conversation_id —
`query-quality-issues.md` 케이스 3·4·5). 정규화 없이 엄격 비교하면 "근거는 제대로 찾았는데
포맷이 틀린" 케이스가 recall 실패로 집계되어, 검색 품질 저하와 포맷 위반이 한 지표에 섞인다.

- 정규화 규칙: PR id의 `#` 유무 무시, 커밋 해시는 prefix 매치, 메시지는 골든셋의
  `aliases` 필드(리플라이 ts)로 매치.
- 포맷 위반 자체는 버리지 않고 **규칙 검사 지표로 따로 집계**한다 — recall은 검색 품질만,
  규칙 검사는 포맷 준수만 잰다.

**precision의 위상은 질문 유형에 따라 다르다.** 골든셋은 "필수 근거"만 정의하므로, 골든셋에
없지만 타당한 근거를 추가 인용한 응답을 감점하면 근거를 풍부하게 가져올수록 벌점을 받는
역인센티브가 된다. 일반 질문에서는 `acceptable_evidence_ids`로 완화하되 precision을 참고용
보조 지표로 본다. 단 **focus 질문(노드 선택) 서브셋은 타당한 근거의 범위가 좁아 전수 정의가
가능하므로 precision을 주 지표로 승격**한다.

**LLM 채점 (LLM-as-judge)** — 기계로 못 재는 것을 강한 모델에 루브릭을 주고 판정:

| 지표 | 정의 |
|------|------|
| 환각률 | summary의 문장 중 evidence로 뒷받침되지 않는 비율 |
| 사실 정답률 | `expected_facts`가 summary에 담긴 비율 |
| 금지 사실 검사 | `expected_absent.facts`가 summary에 담기지 않았는가 |

환각률 judge에는 답변이 담은 quote가 아니라 **그래프에서 가져온 evidence 원문 전체**를
제공한다 — quote만 주면 "quote를 충실히 옮겼는가"만 재게 되어, 잘린 인용을 임의로 완성하거나
원문에 없는 맥락을 덧붙인 문장을 놓친다.

## 엣지 레벨 eval — 그래프 개선 루프용 최소 측정

e2e 하네스 완성을 기다리지 않고 그래프 개선을 시작할 수 있게 하는 층. 전체 하루 안팎 규모.

### 1. 엣지 샘플 라벨링 → 엣지 precision baseline

그래프 스냅샷에서 시맨틱 엣지를 층화 샘플링해 관련/무관을 라벨링한다.

- **샘플링**: REFERENCE · DISCUSSED_IN · TRIGGERED_BY × confidence 구간별 층화, 50~100개.
- **라벨링**: LLM 판정 + 일부 사람 검수 (특히 LLM과 사람의 판정이 갈리는 케이스).
- 라벨은 파일로 버전 관리한다 — 이후 빌더를 고칠 때마다 같은 쌍을 재평가할 수 있어야 한다.

### 2. "연결됐어야 하는 쌍" 골든 목록 → 엣지 recall

사람이 아는 확실한 사례 위주로 소규모(10~20쌍)로 시작한다.
"이 Slack 스레드는 이 커밋에 대한 것" 수준의 명백한 쌍이면 충분하다.

### 3. 엣지 eval 스크립트

라벨 대비 현재 그래프의 엣지 precision/recall을 출력하는 스크립트.
빌더 변경마다 실행해 "변경 → 엣지 지표 델타"를 기록한다.

## 측정 원칙 — 무엇을 고정하고 무엇을 바꾸는가

고정하는 것은 **측정 장치(자·저울)**이지, 개선 대상 시스템이 아니다.
개선 대상은 얼마든지 바꾸고, 그 변화가 점수에 미친 영향을 보는 것이 측정의 목적이다.

**바꿔도 되는 것 (측정 대상 = 개선 레버)**

- 그래프 연결 로직 (Layer 1~4 수정·추가)
- 시스템 프롬프트, tools 추가·수정
- 응답 구조 (단, 아래 예외 참고)
- 답변 생성 모델 (모델 업그레이드도 정당한 개선 조치다)

단 **한 번에 하나씩 바꾸고 측정**해야 어떤 조치가 효과였는지 귀속할 수 있다.

**고정하는 것 (측정 장치)**

1. **원천 데이터 스냅샷**: 특정 시점까지 수집된 데이터(NormalizedEvent 셋)를 스냅샷으로
   보존한다. 그래프 구축 로직을 바꾸는 개선은 이 스냅샷으로 그래프를 재구축한 뒤 측정한다.
   (Neo4j 덤프가 아니라 *입력 데이터*를 고정해야 "연결 방법 변경 → 답 개선"을 공정하게 비교할 수 있다.)
   캡처·재생 메커니즘은 현재 없으므로 새로 만들어야 한다 — 아래 선행 작업 A-1·C-1 참고.
2. **그래프 스냅샷 (빌드 산출물)**: 원천 스냅샷으로 재구축한 그래프는 Neo4j 덤프로 버전을
   붙여 `eval/snapshots/graph-YYYY-MM-DD.dump`에 보관한다. **그래프 로직을 바꾸지 않은
   측정(프롬프트·tools·모델·응답 구조 변경)은 동일 그래프 덤프 위에서 실행**하고, 그래프
   로직 변경 시에만 재구축한다. 덤프 교체·복원은 `infra/docker/graph-swap.sh`로 한다.
3. **골든셋**: 질문과 기대값(expected)은 측정 기간 내내 유지한다. 케이스 추가는 가능하지만
   (골든셋 버전 규칙 참고) 기존 케이스의 수정·삭제는 비교 연속성을 깨뜨린다.
4. **채점 조건**: LLM-as-judge의 채점 모델·채점 프롬프트는 동결한다.
   *답변 생성 모델과 채점 모델은 별개다* — 응시자는 바꿔도 되지만 채점자가 바뀌면
   점수 변화가 시스템 개선인지 채점 기준 변화인지 구분할 수 없다. 동결의 실체:
   - 채점 모델은 **날짜 스냅샷 버전으로 고정**한다 (`gpt-4o` 같은 alias는 내부 업데이트되므로 금지).
   - temperature 0, 채점 프롬프트는 파일로 버전 관리.
   - 최초 1회 **judge 신뢰도 검증**: 10~20건을 사람이 채점해 LLM 판정과 대조한다.
     특히 환각률처럼 판정이 미묘한 지표의 루브릭을 이때 보정한다.
5. **3회 실행 평균 + 노이즈 플로어**: 비결정성을 평균으로 흡수하되, 평균으로도 run-to-run
   변동은 남는다. **노이즈 플로어(최소 유의미 델타)는 baseline 3-run의 분산 기반 ~2σ로
   정의**한다 (2회 측정의 차이 같은 표본 1개짜리 추정은 쓰지 않는다). 판정은 집계 평균
   델타에 더해 **케이스별 짝지은 비교**(개선/악화 케이스 수, sign test)를 함께 본다 —
   집계만 보면 케이스 간 상쇄(5개 좋아지고 5개 나빠짐)를 놓친다.
6. **결과 기록**: 실행마다 `{날짜, git 커밋 해시, 원천 스냅샷 버전, 그래프 스냅샷 버전,
   골든셋 버전, 케이스별 점수, 집계 지표, 질의당 토큰 비용}`을 JSON으로 저장한다.
   이 시계열이 개선 이력의 증거가 된다. run별 **트랜스크립트**(도구 호출 목록·검색 결과)도
   저장한다 — 회귀가 발견됐을 때 재실행 없이 원인을 진단할 수 있다.

**그래프 재구축은 같은 입력에서도 같은 그래프를 보장하지 않는다**

수집 경로에 LLM 단계가 다수 있다 — Slack LLM 필터, Actor 동일인 판단, 이슈 링크 검증,
Layer 4 시맨틱 엣지. 같은 스냅샷 + 같은 코드로 두 번 재구축해도 그래프가 다를 수 있다.
"3회 실행 평균"은 질의 시점 변동만 흡수하고 빌드 시점 변동은 흡수하지 못한다. 따라서:

- 그래프 로직을 바꾸지 않은 측정에서 그래프를 재구축하지 않는다 (위 원칙 2 —
  불필요한 노이즈와 비용만 추가된다).
- 그래프 로직 변경 측정에는 빌드 편차가 섞인다는 한계를 인정하고, 재구축할 때마다
  **구조 지표(노드/엣지 수, Layer 4·REFERENCE 엣지 수)를 함께 기록**해 편차를 가시화한다.
  점수 델타가 노이즈 플로어 부근이면 구조 지표로 빌드 편차 여부를 교차 확인한다.
- 수집 LLM 산출물·임베딩 캐시(선행 작업 C-2)가 갖춰지면 같은 스냅샷 재생이 거의
  결정적이 되어 이 한계가 대부분 해소된다.

**예외 — 응답 스키마를 바꾸는 경우**

evidence id 형식 등 Structured Output 스키마가 바뀌면 채점기의 파싱 계층과 골든셋의
`expected_evidence_ids` 표기도 함께 마이그레이션해야 한다(측정 장치에 손대는 유일한 경우).
이때 지표의 *정의*(recall, 환각률 개념)는 유지하고, 전환 시점에 신·구 코드를 같은 골든셋으로
한 번씩 측정해 점수 연속성을 확인한다(브리지 측정).

토큰 비용을 함께 기록하는 이유: 품질 개선이 비용 증가(예: 재생성 루프 추가) 없이
이뤄졌는지 확인하는 보조 지표.

## 선행 작업

개선 작업 착수 전에 필요한 준비를 A(즉시)·B(엣지 eval)·C(e2e 하네스)로 나눈다.

### A. 즉시 시행 — 되돌릴 수 없는 것 보존

개선 작업을 한 줄이라도 시작하기 전에 완료한다. 나머지(B·C)는 나중에 해도 되지만,
이 세 항목은 시점을 놓치면 "개선 전" 상태가 영구히 사라진다. 세 항목은 서로 독립이라 병렬 가능.

**A-1. NormalizedEvent 캡처 가동**

NormalizedEvent는 현재 RabbitMQ를 통과할 뿐 어디에도 저장되지 않는다.
ai-engine consumer 수신 시점에 이벤트를 JSONL로 덤프한다.

- **dedupe**: 재시도 경로(`history.events.retry`)에서 같은 이벤트가 두 번 캡처될 수 있으므로
  이벤트 id 기준으로 중복 제거한다.
- **순서**: consumer는 프로젝트 간 동시 소비하므로 캡처 순서 ≠ 발행 순서.
  재생 시 프로젝트별 `occurredAt` 정렬을 보장한다.
- **보관 위치·명명**: `eval/snapshots/events-YYYY-MM-DD.jsonl` — 그래프 스냅샷
  (`graph-YYYY-MM-DD.dump`)과 같은 폴더에 두되 접두사로 구분한다. 폴더는 gitignore
  대상이라 파일은 팀 내 직접 전달로 공유하며, 원천 스냅샷은 재생성 불가능한 유일본이므로
  팀원 각자 사본을 보관한다. 이 파일명이 결과 기록의 참조 키가 된다.

**A-2. 기존 데이터 백필 가능성 확인**

캡처는 가동 시점 이후의 이벤트만 담는다. 과거 이벤트를 pipeline-worker 재수집으로
재생성할 수 있는지 확인하고, 가능하면 한 번 돌려 스냅샷을 완성한다.

- **Slack 우선 확인**: 워크스페이스 보존 정책 때문에 과거 메시지 재수집이 불가능할 수 있다.
  불가능하다면 현재 그래프 덤프(A-3)가 해당 데이터의 유일한 보존본이 된다.

**A-3. 현재 그래프 덤프 + 코드 커밋 태그**

- 현재 Neo4j 그래프를 덤프로 버전 붙여 보관한다. (그래프 덤프는
  `eval/snapshots/graph-2026-07-05.dump`로 확보됨 — 대응하는 코드 커밋 태그는 미완.)
- 해당 시점의 코드 커밋에 git 태그를 남긴다 (예: `eval-baseline`).
- 이 덤프는 ① 엣지 baseline 라벨링(B)의 대상, ② e2e 하네스 완성 후
  "개선 전" e2e baseline 소급 측정의 재료가 된다.

### B. 엣지 레벨 eval 구축

위 "엣지 레벨 eval" 섹션의 설계대로 라벨링·골든 쌍·스크립트를 만든다. A-3 덤프에만 의존한다.

### C. e2e 하네스 가동 전 준비

A-1·A-2에 의존하고 B와는 독립이므로 병행 가능.

- **C-1. 재생 스크립트**: 프로젝트 그래프 삭제 → `POST /test/ingest`로 이벤트 순차 재주입
  (프로젝트별 `occurredAt` 정렬) → `POST /graph/build`로 Layer 4 빌드까지 수행.
  재주입·빌드 경로는 이미 있으므로(admin API) 이를 엮는 스크립트만 필요하다.
- **C-2. 수집 LLM 산출물·임베딩 캐시**: 수집 경로의 LLM 산출물(diffSummary, Slack 필터
  판정, Actor 판단, 링크 검증)과 임베딩을 **콘텐츠 해시 + 프롬프트 버전** 키로 캐시한다.
  같은 스냅샷 재생이 거의 결정적이 되고(빌드 편차 제거), 재구축당 OpenAI 비용이 0에
  수렴해 "그래프 로직 변경 시에만 재구축" 제약이 느슨해진다. 키에 프롬프트 버전이
  포함되므로 수집 프롬프트를 바꾸는 실험은 자동으로 캐시가 무효화된다. C-1과 함께 만드는
  것이 효율적이다.
- **C-3. 골든셋 작성**: 위 스키마로 20~40케이스.
- **C-4. 골든셋 유효성 검사기**: 모든 `expected_evidence_ids`(및 aliases)가 스냅샷 그래프의
  실제 노드로 해석되는지 러너 실행 전에 검증한다. 오타·스냅샷 불일치로 측정 한 판을
  버리는 것을 막는다.
- **C-5. baseline 측정 + judge 신뢰도 검증**: baseline 3-run으로 노이즈 플로어를 확정하고,
  judge 판정 10~20건을 사람 채점과 대조한다.

### 의존 관계와 실행 순서

```
A-1 캡처 가동 ─┐
A-2 백필 확인 ─┼─ (병렬, 즉시)
A-3 덤프+태그 ─┘
      │
      ├─→ B (엣지 eval, A-3에만 의존) ──→ 그래프 개선 루프 시작
      │
      └─→ C (e2e 하네스 준비, A-1·A-2에 의존) — B·개선 루프와 병행
                │
                └─→ e2e 하네스 완성 → A-3 덤프로 "개선 전" e2e baseline 소급 측정
```

- **A가 끝나는 순간부터 그래프 개선 작업을 시작해도 비교 가능성이 깨지지 않는다.**
- B가 갖춰지면 개선 루프는 엣지 지표로 돌고, e2e 하네스(C)는 병행 구축한다.
- e2e baseline은 A-3 덤프 + git 태그 덕분에 하네스 완성 후 소급 측정이 가능하다
  — 단, 원천 이벤트(A-1·A-2)와 그래프 덤프(A-3)가 보존되어 있을 때만.

## 개선 단계와 종료

| 단계 | 측정 |
|------|------|
| 그래프 개선 루프 | 빌더 변경마다 엣지 eval. e2e 하네스 완성 후에는 주요 마일스톤마다 e2e도 실행 |
| 프롬프트·응답 개선 | 변경마다 e2e eval — 그래프 덤프 재사용 (재구축 불필요) |
| 품질 단계 종료 | 최종 측정 → 개선 전후 대비 확정 (예: 엣지 precision NN% → NN%, evidence recall NN% → NN%, 환각률 NN% → NN%) |

품질 개선 반복마다 eval을 돌리면 조치별 기여도가 기록된다. 예:

```
descendants 평탄화       → 사실 정답률 +11%p
시맨틱 엣지 임계 조정     → 엣지 precision +14%p · evidence recall +9%p
프롬프트 인용 규칙 강화    → 환각률 -6%p
```

(모두 노이즈 플로어를 넘는 델타만 효과로 기록한다.)

이 로그가 있으면 "무엇이 얼마나 효과 있었는지"를 근거를 갖고 말할 수 있고,
효과 없는 조치를 빠르게 되돌릴 수 있다.
