# 다국어(i18n) 준비 메모

**현재 상태**: 앱(제품 본체) UI·답변은 한국어 고정. **공개 페이지(랜딩·약관·개인정보·지원)만
2026-08-24부터 ko/en 2언어다** — `components/landing/LandingLanguageProvider.tsx`가
아래 §2 권고안을 그대로 구현했다(명시 선택 localStorage `ht.lang` > `navigator.languages`
ko 감지 > 영어, 감지 결과는 비영속, 위치 신호 미사용, `<html lang>`은 공개 페이지에서만
동기화·이탈 시 ko 복원). 이 Provider는 §3의 `UI_LOCALE`과 무관한 별도 구현이다(랜딩은
포맷터를 쓰지 않는다) — 앱 i18n을 도입할 때 `ht.lang` 키를 승계하고 `UI_LOCALE`을 훅으로
바꾸는 것이 다음 단계다.

이 문서는 i18n 계획서가 아니라, **먼저 끝난 시각 표시 작업이 i18n을 위해 세워 둔 계약**을 적는다.
언어를 추가하는 사람이 모르고 깨뜨리기 쉬운 것들이라 코드 주석과 함께 여기에 남긴다.

---

## 1. 로캘과 타임존은 독립된 두 축이다

이번 작업에서 가장 중요한 결정이다. 이 둘을 묶으면 반드시 누군가는 틀린 시각을 본다.

| 축 | 무엇이 정하나 | 코드 |
|---|---|---|
| **로캘**(표기 언어) | UI 언어 설정 | `lib/format.ts`의 `UI_LOCALE` |
| **타임존**(어느 시각) | 사용자 기기 설정 | `Intl.DateTimeFormat`에 `timeZone`을 **주지 않음** |

`formatInstant()`는 로캘만 받고 타임존은 지정하지 않는다. `timeZone`을 생략하면 브라우저가
기기 설정을 자동으로 쓰기 때문이다. 그래서 **언어를 바꿔도 시각은 안 움직이고, 여행을 가면
언어는 그대로인 채 시각만 움직인다.** 이게 의도한 동작이다.

깨지는 시나리오 (언어 기본값을 위치로 정할 때 특히 위험):

- **뉴욕에 사는 한국인** — 언어는 한국어가 편하지만 시각은 뉴욕 시간이어야 한다.
  위치로 언어를 정하면 영어가 기본이 되는데, 그건 언어 문제일 뿐 **시각과는 무관**하다.
- **서울 출장 중인 미국인** — 위치는 서울이지만 한국어를 못 읽는다. 시각은 서울 시간이 맞다.

> **규칙**: 언어 기본값을 위치로 정하더라도, 그 위치 정보를 **시각 표시에 절대 끌어들이지 않는다.**
> 반대로 사용자가 언어를 바꿨다고 시각 표기의 기준 시간대를 바꾸지 않는다.

## 2. 언어 기본값을 정할 때 쓸 수 있는 신호

결정은 아직 안 됐지만, 후보와 한계를 적어 둔다.

| 신호 | 얻는 법 | 한계 |
|---|---|---|
| 브라우저 UI 언어 | `navigator.languages` | 가장 정직한 "읽고 싶은 언어" 신호. 회사 지급 장비가 영어인 경우가 있음 |
| 기기 타임존 | `Intl.DateTimeFormat().resolvedOptions().timeZone` | **위치의 프록시일 뿐 언어의 프록시가 아니다.** 위 두 시나리오에서 그대로 틀림 |
| IP 지오 | 서버(backend)에서 판별 | VPN·해외 사무실에 취약. 서버 왕복 필요 |
| 사용자 명시 선택 | 설정 화면 | 가장 정확. 한 번 고르면 다른 모든 신호보다 우선하고 영속화해야 함 |

권고는 **`navigator.languages` 우선 → 사용자 명시 선택이 있으면 그것이 최우선**이며,
위치(타임존·IP)는 마지막 폴백으로만 쓴다. 위치를 1순위로 쓰면 "한국어 브라우저인데 영어로 뜨는"
경험이 생긴다.

## 3. 단일 교체 지점

로캘은 `clients/web-dashboard/src/lib/format.ts`의 **`UI_LOCALE` 한 곳**에서만 정한다.
i18n 도입 시 이 상수를 설정 훅(예: `useLocale()`)으로 바꾸면 아래가 함께 따라온다.

- `formatInstant()` — 답변 본문의 자연어 시각
- `formatRelative()` — "N분 전" (한국어 리터럴은 번역 테이블로 옮겨야 함. `Intl.RelativeTimeFormat` 후보)
- `formatTimestamp()` — 로캘 무관(고정 `YYYY-MM-DD HH:mm`). DESIGN.md상 타임스탬프는 라틴
  기술 토큰이라 UI 크롬에서는 일부러 로캘 표기를 쓰지 않는다. **이 함수는 번역 대상이 아니다.**

새 포맷터를 추가할 때 **호출부에 로캘 문자열을 흩뿌리지 않는다** — `UI_LOCALE`을 기본값으로 받는다.

## 4. 서버는 언어도 타임존도 모른다 (그대로 두어야 한다)

ai-engine은 답변 본문·`evidence[*].occurredAt` 모두 **UTC ISO 정준값**만 내보내고,
표시 변환은 전적으로 web-dashboard가 한다(`lib/remarkLocalTime.ts`, `docs/tools.md`).

이 분업 덕에 **언어가 늘어도 시각 관련 코드는 손댈 게 없다.** 모델이 어떤 언어로 답하든
ISO를 그대로 옮기기만 하면, 클라이언트가 각 사용자의 로캘·타임존으로 그린다.

**하지 말아야 할 것**:

- 서버(ai-engine·backend)에서 시각을 특정 타임존·언어로 포맷해 **저장**하지 않는다.
  저장된 답변이 그 설정에 영구히 묶여, 다른 언어·다른 시간대 사용자에게 되돌릴 수 없다.
  UTC 기준으로 기대값이 적힌 eval 골든셋(`eval/golden/case-43.yaml` 등)도 함께 깨진다.
- `Intl`이 주는 로캘 표준 표기를 손으로 조립하지 않는다. 한국어 "오후 5시 42분"을 만들려면
  `formatToParts`로 한국어 전용 패턴을 짜야 하는데, 로캘이 늘 때마다 그 분기가 늘어난다.
  그래서 CLDR 표준인 **"2026년 3월 12일 오후 5:42"**(en-US는 "March 12, 2026 at 5:42 PM")를 쓴다.

## 5. 답변 본문 언어는 별개의 작업 항목이다

프론트 문자열만 번역해도 **답변 본문은 여전히 한국어로 온다.** `agent/orchestrator.py`의
시스템 프롬프트가 "summary·unknown_aspects·quote를 한국어로 작성하라"고 지시하기 때문이다.
언어 분리의 실제 범위는 다음 셋이다.

1. web-dashboard UI 문자열
2. ai-engine 시스템 프롬프트의 **답변 언어 지시** (요청 단위로 언어를 넘겨야 함)
3. 대화 이력 — 과거 답변은 작성 당시 언어로 저장돼 있다. 언어를 바꿔도 옛 답변은 번역되지 않는다
   (재번역할지, 그대로 둘지 결정 필요)

시각 관련 프롬프트 규칙(**"본문에도 ISO 원문을 그대로 옮기고 날짜를 말로 풀어 쓰지 마라"**)은
언어와 무관하게 유지해야 한다. 영어로 "March 12"라고 풀어 써도 클라이언트가 변환할 대상을 잃는 건
똑같다.

## 6. 시각 표시 계약 (건드릴 때 주의)

`lib/remarkLocalTime.ts`가 지키는 규칙들이다. 리팩토링하다 무심코 깨기 쉽다.

- **날짜 단독(`2026-03-12`)은 변환하지 않는다.** 날짜는 instant가 아니라서 로컬로 옮기면
  음수 오프셋 지역에서 하루가 밀린다.
- **코드블록은 건드리지 않는다.** 커밋 로그·JSON을 통째로 인용한 자리라 원문이어야 한다.
- **인라인 코드는 노드 전체가 타임스탬프 하나일 때만 변환한다.** 모델이 시각을 백틱으로 감싸는
  버릇이 있어서(실측), 전부 건너뛰면 한 문장 안에서 어떤 시각은 변환되고 어떤 건 ISO로 남는다.
- **자동 링크(autolink) 라벨은 변환하지 않는다.** `https://…?from=2026-03-12T08:42:50Z` 같은
  URL은 remark-gfm이 만드는 링크의 표시 텍스트가 곧 href라, 라벨만 바꾸면 href와 어긋난다.
  매칭된 문자열이 부모 링크의 `url`에도 그대로 들어있는지로 판별한다 — `[2026-03-12T08:42:50Z
  로그](https://example.com/x)`처럼 표시 텍스트가 href와 무관한 명시 링크는 그대로 변환 대상이다.
- **`evidence[*].quote`(인용문)는 변환하지 않는다.** 인용 카드는 `Message.tsx`에서 quote를
  마크다운을 거치지 않고 평문으로 렌더하므로 remarkLocalTime을 타지 않는다 — 의도된 것이다.
  quote는 프롬프트상 "요약·번역·재구성 금지, 원문 그대로 인용"이 원칙이고, 서버가
  `_drop_unverified_quotes`로 도구 결과 문자열에 실존하는지 검증한다. 표시를 바꾸면 화면의
  인용문과 검증 대상이 어긋난다. 같은 카드의 날짜(메타데이터, 로컬 변환)와 인용문 속 시각
  (증거 원문, UTC 그대로)은 역할이 달라 표기가 갈리는 게 정상이다.
- `<time datetime="…">`에 **원본 UTC ISO를 보존**한다. 화면 표기가 로컬로 바뀌어도 정준값은 남는다.

## 7. 검증 방법

언어를 추가한 뒤에도 같은 방식으로 확인한다.

```bash
# 다른 타임존으로 브라우저 띄우기
TZ=America/New_York open -na "Google Chrome" --args --user-data-dir=/tmp/tz-test http://localhost:5173
```

- 같은 답변의 시각이 타임존별로 이동하는가 (언어는 그대로여야 한다)
- 언어를 바꿨을 때 시각의 **표기**만 바뀌고 **가리키는 순간**은 그대로인가
- 개발자도구에서 `<time datetime>`에 UTC 원본이 남아 있는가
- 본문 시각과 인용 카드 날짜가 서로 어긋나지 않는가

강한 판별기: **UTC 15시 이후 이벤트**는 KST에서 날짜가 하루 넘어간다(수집 데이터에 104건).
예 — PR #1 오픈 `2026-03-23T15:01:27Z` → KST `3월 24일 오전 12:01`.
