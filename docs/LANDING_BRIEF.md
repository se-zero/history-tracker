# History Tracker 랜딩 페이지 — 작업 브리프

> 이 문서는 새 세션의 오케스트레이터가 읽는 작업 지시서다.
> 코드 작업은 서브에이전트에 위임하되, 아래 판단 기준과 금지 사항은 오케스트레이터가 직접 관리한다.

---

## 1. 제품 맥락

**History Tracker** — GitHub·Jira·Slack의 개발 기록을 Neo4j 지식그래프로 엮어,
"이 코드가 왜 이렇게 바뀌었나 / 이 도메인을 누가 제일 잘 아나"를 자연어로 질문하는
개발자 컨텍스트 도구.

**포지셔닝 한 줄:** 머지되면 사라지는 개발 맥락을, 지식그래프로 되살려 자연어로 질문한다.

**시그니처(제품의 핵심 순간):** 질문 → 인용된 답변 → 우측 그래프에서 근거 노드와
그 사이 경로가 앰버빛으로 점등. 텍스트와 그래프가 함께 해소되는 이 순간이 곧 제품이다.

**타깃:** 개발자. 대중 소비자가 아니다. 친근하거나 귀엽지 않고, 정밀하고 담백해야 한다.

## 2. 이 작업의 목표와 성공 기준

랜딩(소개) 페이지를 완성한다. 최우선 품질 목표는 하나다:

> **"AI가 만들어준 것 같다"는 인상이 나지 않을 것.**

이 프로젝트에서 "AI 티"의 조작적 정의는 다음과 같다. 이 중 하나라도 해당하면 실패다.

- 슬레이트(`#0f172a`) 계열 배경 + 블루 액센트 + Inter 폰트 조합
- near-black 배경 + acid-green/vermilion 액센트 (다크 AI의 또 다른 디폴트)
- 컬러풀 그라데이션 blob, 떠다니는 3D 오브젝트, 무지개 그라데이션
- 브라우저 기본 이징(linear/ease)에 의존한 모션
- 좌우 50:50 대칭 분할 히어로 + 중앙정렬 디폴트 여백
- 어느 SaaS에 갖다 놔도 성립하는 카피

**성공 기준:** 각 섹션 완료 시 "이 화면이 아무 다크 SaaS에나 나올 템플릿처럼 보이는가?"를
자문하고, 그렇다면 무엇을 바꿨는지 명시할 수 있어야 한다.

## 3. DESIGN.md — 무엇이고, 어떻게 쓰고, 언제 고치는가

### 이 파일이 무엇인가

프로젝트 루트의 `DESIGN.md`는 **"어떻게 보일지"의 단일 정본**이다.
YAML 프런트매터에 정확한 디자인 토큰(색 hex, 서체, 간격 스케일, radius, 모션 이징),
그 아래 마크다운 산문으로 **그 결정을 내린 이유**가 적혀 있다.

`CLAUDE.md`와 역할이 다르다. CLAUDE.md는 "어떻게 코딩할지"(아키텍처·컨벤션),
DESIGN.md는 "어떻게 보일지"다. 둘은 겹치지 않고 나란히 간다.

### 어떻게 참고하는가

1. **UI 코드를 한 줄이라도 쓰기 전에 DESIGN.md를 처음부터 끝까지 읽는다.**
   훑지 말 것. 산문 부분에 토큰 목록만으로는 알 수 없는 규칙이 들어 있다.
2. **모든 색·타이포·간격·모션 결정을 이 파일에서 파생시킨다.** 임의의 hex나
   px 값을 새로 만들지 않는다. 필요한 값이 없으면 만들지 말고 오케스트레이터에 보고한다.
3. **서브에이전트에게 작업을 위임할 때도 DESIGN.md를 읽으라고 반드시 명시한다.**
   요약해서 전달하지 말 것 — 요약 과정에서 규칙이 소실된다.

### 반드시 지켜야 할 핵심 규칙 (전문은 파일 참조)

- **앰버(`#EBA23C`)의 의미는 하나뿐이다: "라이브 / 실행 / 선택".**
  기본 CTA, 포커스, 선택된 노드, 답변 경로, 활성 내비. 그 외 어디에도 쓰지 않는다.
  강조가 필요하지만 "라이브한 것"이 아니면 텍스트 웨이트나 elevation으로 푼다.
  → 이 규칙이 깨지는 것이 이 디자인 시스템의 최대 실패 모드다.
- **두 번째 강조색을 절대 도입하지 않는다.** 앰버 계열(hue 60~90)은 액센트가 독점한다.
- **색 네임스페이스 분리:** 노드 타입 색은 그래프 캔버스 안에서만, 시맨틱 색은
  UI 크롬에서만 산다. 액센트만 두 영역을 넘나든다.
- **`warning` 토큰은 의도적으로 존재하지 않는다.** 경고성 상태는 색이 아니라
  `text-muted` + 모노 라벨, 또는 `danger`, 또는 (옆에 컨트롤이 있을 때만) `accent`로 표현한다.
- **모노(JetBrains Mono)는 라틴 기술 토큰 전용:** 키(`HT-64`), 해시, 타임스탬프,
  파일 경로, eyebrow 라벨. **한글이 포함된 콘텐츠에는 모노를 쓰지 않는다.**
- **서체는 3종뿐이다.** 네 번째 패밀리를 추가하지 않는다.
- **한글 조판:** 헤드라인 weight는 라틴보다 한 단계 낮춘다(한글은 시각 무게가 크다).
  본문 행간 1.7~1.75. 한글 eyebrow에는 트래킹을 넣지 않는다.

### 언제 DESIGN.md를 함께 수정하는가

**수정한다 (새 결정이 생겼을 때):**
- 여러 섹션·화면에 반복 적용될 **새로운 규칙**이 정해졌을 때
  (예: 새 컴포넌트 패턴, 새 반응형 브레이크포인트 정책, 새 조판 규칙)
- 기존 규칙에 **명시되지 않은 빈틈**을 채우는 결정을 했을 때
- 이유가 함께 기록되어야 한다. 토큰만 추가하고 근거를 안 적으면 다음 사람이 되돌린다.

**수정하지 않는다:**
- 한 섹션에만 적용되는 일회성 레이아웃 값 (그건 그냥 그 컴포넌트에 둔다)
- "이 값이 더 예뻐 보여서" 같은 취향 조정

**절대 임의로 하지 않는다 — 반드시 오케스트레이터에 보고 후 사람의 승인:**
- **기존 토큰 값(hex, 폰트, 이징 커브)의 변경.**
  토큰은 공유 `tokens.css`에 있고 **앱(제품 본체)과 공유될 예정**이다.
  랜딩만 보고 색을 재튜닝하면 나중에 앱 마이그레이션이 깨진다.
- 앰버 사용 규칙의 확장·완화
- 서체 추가

### 토큰 구조에 대한 주의 (2026-07-24 현실 반영)

공유 `tokens.css` **한 파일에 추가만** 한다 — 별도 파일로 포크하지 않는다. 앱의 기존
변수는 그대로 둔 상태이고, 랜딩은 `--lp-*` 프리픽스 토큰만 참조한다. 프리픽스를 쓰는
이유: 앱의 기존 토큰과 이름이 겹치기 때문이다(`--node-*`, `--surface-*` 등이 이미
다른 값으로 존재해 무프리픽스 추가는 불가능했다). 같은 파일 안이므로 마이그레이션은
"프리픽스를 떼고 기존 참조를 새 값으로 돌리기" 한 번으로 끝난다.
보조 네임스페이스: 커넥터 브랜드 색은 `--brand-*`(외부 브랜드 자산 — 앰버 독점 규칙
비대상), 시스템 상태는 `--lp-success`(DESIGN.md 시맨틱 값 — `--lp-node-commit`과 hex가
같지만 네임스페이스가 다르다), 들린 표면 하이라이트는 `--lp-edge-highlight`.

## 4. 참고한 레퍼런스와 각각에서 가져온 것

이 랜딩은 아래 레퍼런스들을 분석해서 나온 결과물이다. 무엇을 가져오고 무엇을
버렸는지가 중요하다.

| 레퍼런스 | 가져온 것 | 버린 것 |
|---|---|---|
| **Notion** (notion.com) | 제작된 영상 히어로 방식(라이브 데모보다 현실적), `모노 eyebrow → 헤드라인 → 실제 화면` 섹션 리듬, front/back 레이어드 스크린샷 | 라이트 모드, 말랑한 3D 이모지 일러스트, 친근한 대중 톤 — 다크 기술 도구와 정면 충돌 |
| **Linear** (linear.app) | 다크 네이티브, 추상 일러스트 없이 실제 UI로 승부, 밀도 있는 화면 | — |
| **Vercel** (vercel.com) | 히어로가 제품을 직접 시연, 목적 있는 모션 | — |
| **Cursor** (cursor.com) | 개발자 대상 톤, 절제된 카피, "높은 기준을 가진 사람들의 도구"라는 인상 | — |
| **Perplexity** | 출처 카드 패턴 (앱 쪽 참고) | — |
| **Glean** | 지식그래프 + 커넥터 + 인용 답변이라는 제품 컨셉 (앱 쪽 참고) | — |
| **Neo4j Bloom** | 그래프 탐색 UI, Legend/필터 패턴 (앱 쪽 참고) | — |

**핵심 종합:** 노션의 *실행 방식*(영상 히어로·섹션 리듬) + Linear/Vercel의 *진정성*(실제 UI) +
자체 다크·그래프 정체성. 노션의 *스킨*은 쓰지 않는다.

**연속성 원칙:** 랜딩과 앱은 같은 다크 정체성이어야 한다. 밝고 말랑한 랜딩 뒤에
어두운 기술 앱이 뜨면 로그인 순간 신뢰가 깨진다.

## 5. 현재 상태

### 완료 — 히어로 (2026-07-25 5차 확정: 상하 구조 + 와이드 전폭 제품 UI 영상 슬롯, 다시 동결)

같은 날 다섯 라운드를 거쳤다. 1차(풀블리드 성좌 + 대형 헤드라인)는 우측이 추상 배경뿐이라
"볼 것이 있는 콘텐츠"가 못 됐고, 2차에서 우측을 실제 제품 UI(대화 화면) = 영상 슬롯으로
교체했으나 크기가 작아 "썸네일"로 읽혔으며, 3차의 대형화(우측 가장자리 크롭)는 좌우 분할
자체가 한계였다 — 우측 절반에 우겨넣어 여전히 좁고, 잘린 면이 뷰포트 끝에 안 붙어 애매하게
떴다. 4차에서 노션·Linear식 **상하 구조**로 전환: 위 텍스트 블록(좌측 정렬) → 아래 제품 UI
블록(컨테이너 전폭), **잘림은 하단(첫 화면 폴드) 한 방향뿐**이고 좌·우·상단은 온전하다.
5차 미세조정으로 **텍스트를 상단 여백을 두고 내리고(내비에 붙은 답답함 해소), 슬롯을
와이드 비율(≈1.9:1)로** 바꿨다 — 구조 불변, 비율·위치·여백만. 확정 형태:

- **카피(1차에서 확정, 불변):** eyebrow `개발 히스토리를 위한 지식 그래프`(한글이므로
  모노 금지 — 본문 서체) → 헤드라인 `코드베이스의 모든 결정을, 되짚을 수 있게.`(끝 마침표는
  본문 색 — 앰버 아님) → 서브 `흩어진 커밋·PR·이슈·대화를 하나의 그래프로 묶어, 물으면
  근거와 함께 답합니다.` CTA 2개(`GitHub으로 시작` accent 채움 → OAuth 직행 /
  `그래프 만져보기` → `/demo/graph`)와 안내문 유지.
- **스케일:** 헤드라인 display-xl 복귀 — `clamp(2.125rem, 4.6vw, 3.5rem)`. 3차의 3.25rem
  로컬 클램프는 좌우 분할의 3중 제약(2행×텍스트 트랙 545px×패널 가독)에서 나온 값이라
  상하 구조에서 근거가 소멸해 제거했다. 두 절은 inline-block 스팬 — 데스크톱 한 줄(폴드
  예산 −66px), 폭이 좁아지면 절 경계에서 2줄, 모바일 keep-all·balance. 트래킹 -0.02em,
  weight 500.
- **상하 배치(4차 구조 + 5차 배분 + 6차 기준선):** 헤더 아래 상단 여백 약 97px
  (`padding-top: calc(64px + 96px)`, Linear식 "내려와서 시작") → 텍스트 블록(1440×900
  실측 y 161~440 온전) → gap 48 → 와이드 슬롯이 y=488에서 시작해 폴드 안 가시 412px
  (**뷰포트 높이 45.8%**, 1920×1080은 54.8%), 하단은 폴드 아래로 이어져 스크롤하면
  드러난다. 상단 크롬과 좌·우 엣지는 온전. 히어로가 슬롯을 클리핑하지 않으므로 "하단만
  잘림"은 문서 흐름의 성질이다 — 영상 교체 후에도 동일하게 작동한다.
- **슬롯 비율(5차): `1280/675` ≈ 1.9:1 와이드.** 4차의 16:10(정사각형에 가깝다는 사람
  피드백)에서 세로를 줄인 값 — 16:9는 폭 확장 시 높이가 오히려 늘어 기각. 표준 16:9
  녹화 영상은 `object-fit: cover`로 수 % 크롭해 채운다(교체 주석에 안내).
- **슬롯 폭(6차 확정): 콘텐츠 폭 100% = 좌측 기준선 공유.** 5차의 ≥1344px 대칭 확장
  (+144px)은 6차 기준선 통일로 **폐기** — 로고·히어로 텍스트·슬롯의 왼쪽 가장자리가
  한 줄(1440에서 x=115)에 앉아야 하고, 기준선 위에서 확장하면 우측만 잘려 "한쪽만 잘림
  금지"를 위반한다. 1440 실측 1200×633(종횡비 고정이라 와이드 인상 유지, 폴드 가시
  45.8% 동일).
- **슬롯 내용(3단 셸, `HeroProductSlot.tsx`):** 고정 종횡비 컨테이너가 프레임(헤어라인
  보더 + r-lg + edge-highlight + surface-1)을 소유하고 내용물만 `<video>`로 교체하는 계약 유지
  (교체 주석: 파일 헤더·인라인·landing.css 모바일 블록). 윈도우 크롬(브레드크럼
  `history tracker / 대화` — 가짜 파일명 바 금지) 아래 **좌측 레일(4차 신규, ≥1180px 전용
  220px)** → 채팅 스트림(사용자 버블 `검색 기능 관련 PR이랑 지라 티켓 찾아줘` → 답변 산문 →
  출처 카드 3장) + 하단 컴포저 → 우측 `관련 그래프` 패널(340px). 레일은 기능 1 미리보기의
  `.lp-feature-chat-rail*` 클래스·데모 데이터(내비 5개 + 히스토리 4개)를 그대로 재사용 —
  새 식별자·날짜를 발명하지 않고 교차 정합을 유지한다. **레일 활성 표시(내비 `대화`·첫

### 문제 정의

```
헤드라인 (2행):
  git blame은 누가 바꿨는지 알려준다.
  왜 바꿨는지는 아무도 모른다.

본문:
  결정은 Slack에, 근거는 티켓에, 결과만 코드에 남는다.
  셋 다 검색되지만, 그 사이의 관계는 어디에도 저장되지 않는다.
```

**조판 의도:** `git blame`은 반드시 JetBrains Mono로 조판한다. 나머지 한글은
디스플레이 서체. "기술 토큰은 모노"라는 규칙을 헤드라인에서 시각적으로 증명하는 것이 의도다.
이미지·아이콘·배경 장식 전부 금지. 앰버 사용 금지(라이브한 것이 아니다).
히어로가 시각적으로 무거웠으므로 이 섹션은 여백이 넉넉한 숨 쉬는 자리다.

### 작동 방식 3스텝

```
eyebrow: HOW IT WORKS
헤드라인: 연결하고, 묻는다. 그 사이는 자동이다.

01 / 연결
저장소와 워크스페이스를 연결한다. GitHub, Jira, Slack.

02 / 구축
흩어진 기록 사이의 관계를 찾아 하나의 히스토리 그래프로 엮는다.
결정과 코드가 다시 이어진다.

03 / 질문
자연어로 묻는다. 답과 함께, 근거가 된 노드와 경로가 돌아온다.
```

**조판 의도:** `01 / 02 / 03` 번호는 모노(라틴이므로). 3단 가로 배치.
각 스텝 사이에 진행을 암시하는 헤어라인 또는 여백. 앰버는 쓰지 않는다
(단, 03의 "근거가 된 노드와 경로"를 시각적으로 암시하는 미니 요소에 한해
오케스트레이터 판단으로 허용 가능 — 그 경우 이유를 기록할 것).

→ **2026-07-24 채택·확장**: 사람 지시로 3스텝이 미니 그래프 시각화(같은 노드 배치를

2. 섹션 단위로 서브에이전트에 위임한다. **한 번에 한 섹션.**

6. 완료 후 다음 섹션으로.

### ⚠️ 스크린샷 검토는 필수다

이 프로젝트의 모든 개선은 **렌더된 화면을 보고** 나왔다. 코드만 읽어서는
"노드가 너무 고르게 흩어졌다", "스크롤 큐가 공중에 떴다", "여백이 절제가 아니라
미완성으로 보인다" 같은 판단을 할 수 없다.

**오케스트레이터는 브라우저 스크린샷을 찍을 수 있어야 한다**(Playwright/Puppeteer MCP,
dev-browser 계열 도구, 또는 스크린샷 스크립트 — 종류는 무관하다).
(2026-07-24 검증: 전역 `dev-browser` CLI가 4개 조건을 모두 충족한다 — Playwright Page API로
`setViewportSize`/`screenshot({fullPage})`/`document.fonts.ready` 대기, `saveScreenshot()`으로
`~/.dev-browser/tmp/`에 저장 후 파일을 직접 읽어 확인. 콘솔 수집은 `page.on("console")`.)
그것 없이는 "완료"를 선언하지 않는다.
스크린샷을 볼 수 없다면 그 사실을 먼저 사람에게 알리고 멈춘다.

도구가 무엇이든 아래 조건을 만족해야 한다.

1. **찍은 이미지를 오케스트레이터가 실제로 볼 수 있을 것.**
   디스크에 저장만 하는 도구라면, 저장 후 그 파일을 읽어서 확인하는 단계까지 수행한다.

2. **뷰포트 크기를 지정할 수 있을 것.** 최소 데스크톱(1440×900 권장)과
   모바일(390×844 권장) 두 가지. 스크린샷을 제시할 때 **찍은 뷰포트 크기를 함께 기록한다** —
   비율 판단에 필요하다.

3. **뷰포트 샷과 풀페이지 샷을 모두 찍을 것.**
   - 뷰포트 샷: "히어로가 첫 화면을 채우는가", "스크롤 큐가 바닥에 붙었는가",
     "하단이 비었는가" 같은 **뷰포트 비례 판단**에 쓴다. 이 판단은 풀페이지 샷으로는 불가능하다.
   - 풀페이지 샷: 섹션 간 리듬과 전체 흐름 확인에 쓴다.

4. **폰트 로딩 완료 후에 찍을 것 — 중요.**
   이 프로젝트의 서체는 전부 CDN 동적 서브셋으로 로드된다. 렌더 직후 촬영하면
   폴백 폰트 상태가 잡히고, 오케스트레이터가 **존재하지 않는 타이포 문제를 고치려 든다.**
   `document.fonts.ready` 이후, 가급적 짧은 추가 대기를 두고 촬영한다.

**콘솔 로그를 볼 수 있다면 함께 확인한다** — 폰트 로딩 실패, CSS 변수 미해결,
리소스 404가 여기서 먼저 드러난다.

**모션은 정적 스크린샷으로 검토할 수 없다.** 모션 라운드의 최종 판단은 사람이 한다.
오케스트레이터는 이징 토큰이 DESIGN.md대로 쓰였는지, `prefers-reduced-motion`
분기가 존재하는지 등 **코드 수준의 확인**까지만 하고, "자연스러운가"는 사람에게 올린다.

검토 시 확인할 것:
- 앰버가 규칙대로 쓰였는가 (라이브/실행/선택에만)
- 밀도가 적절한가 — 여백이 "자신감 있는 절제"인가 "flex 중앙정렬 디폴트"인가
- 앞뒤 섹션과 형식이 충분히 다른가 (리듬)
- 한글 조판이 자연스러운가 (웨이트, 행간, 혼용 줄의 균형)
- **템플릿 테스트:** 이 화면이 아무 다크 SaaS에나 나올 것 같은가?

### 서브에이전트 모델

기계적 구현은 Sonnet으로 충분하다. **판단은 오케스트레이터에 남긴다.**
다만 스펙이 촘촘할수록 결과가 좋으므로, 위임 프롬프트에 조판 의도와 금지 사항을
빠짐없이 넣는다.

### 자기 검토의 맹점

오케스트레이터가 자기 서브에이전트의 결과를 검토하면 통과시키는 쪽으로 기운다.
이를 완화하기 위해 각 섹션 완료 시 **명시적으로** 답한다:

> "이 섹션이 템플릿처럼 보이는가? 그렇다면 무엇을 바꿨는가?"

애매하면 통과시키지 말고 사람에게 올린다.

## 10. 사람에게 보고할 체크포인트

전 과정을 자동으로 돌리되, 아래 두 지점에서 멈추고 사람의 확인을 받는다.

**체크포인트 1 — 문제 정의 + 작동 방식 완료 후**
- 두 섹션의 스크린샷
- 내린 판단 중 **다른 선택지가 있었던 것**들을 목록으로 (무엇을 골랐고 왜, 대안은 무엇이었는지)
- 확인이 필요한 사실 주장 (특히 "02 / 구축"의 파이프라인 서술)

**체크포인트 2 — 유스케이스 + 최종 CTA + 푸터 완료 후**
- 전체 페이지 스크린샷 (데스크톱 + 모바일)
- 남은 우려 사항
- DESIGN.md에 추가한 규칙이 있다면 그 목록과 이유

**즉시 멈추고 물어야 하는 경우:**
- DESIGN.md의 기존 토큰을 바꿔야 할 것 같을 때
- 앰버 규칙을 확장해야 할 것 같을 때
- 확정 카피가 레이아웃상 안 맞을 때
- 이 브리프에 답이 없는 구조적 결정이 필요할 때
