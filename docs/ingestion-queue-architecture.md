# 수집 큐 아키텍처 결정 기록

> 이 문서는 수집 큐가 "왜 이 구조인가"를 남긴다. 결정은 두 개다.
> **결정 1(2026-10-27)**: 큐 구조를 트랜잭셔널 아웃박스 + 프로젝트별 큐로 바꾼다.
> **결정 2(2026-11-11)**: 릴레이가 보내지 못하는 행이 생기면 그 행만 빼서 혼자 재시도하고 운영자에게 알린다.
> 코드가 지켜야 할 세부 규칙은 `services/pipeline-worker/CLAUDE.md`와 `services/ai-engine/CLAUDE.md`, 운영 절차는 `docs/deployment.md`에 있다.

## 0. 한 장 요약

**현재 구조**

```
외부 소스 ──API 수집──▶ pipeline-worker
                          수집기 ──▶ PostgreSQL 아웃박스 표 (ingest_outbox)
                          릴레이 ──▶ RabbitMQ 프로젝트별 큐 ──소비──▶ ai-engine ──▶ Neo4j
```

**결정 1. 큐 구조.** 큐가 하나뿐이라 큰 프로젝트가 큐를 독점했고, 수집기가 브로커 발행과 커서 저장을 서로 다른 저장소에 따로 써서 브로커가 느리면 수집 전체가 실패했다. 수집기는 DB의 아웃박스 표에만 쓰고, 릴레이가 그 행을 프로젝트별 큐로 옮기게 바꿨다. 후보 셋(A·B·C2) 중 A다. 근거는 2장.

**결정 2. 보내지 못하는 행.** 결정 1 뒤에도 릴레이는 행 하나가 계속 거부되면 모든 프로젝트의 전달을 세웠고, 신호는 경고 로그뿐이었다. 실패한 행만 정상 흐름에서 빼서 간격을 늘려 가며 혼자 재시도하고, Slack으로 알리게 바꿨다. 나머지 행은 계속 나간다. 근거는 3장.

## 1. 초기 구조

### 1-1. 흐름

```
외부 소스 ──API 수집──▶ pipeline-worker ──발행(페이지마다)──▶ RabbitMQ ──소비──▶ ai-engine ──▶ Neo4j
                            │                               (큐 1개, 선입선출)
                            │ 루프가 끝나면 커서 저장
                            ▼
                        PostgreSQL
```

- 큐가 하나이고 선입선출이다. 프로젝트 사이에 순서를 조정하는 장치가 없다.
- 수집기는 한 페이지를 수집할 때마다 브로커에 발행하고, 브로커가 받았다는 확인 응답(confirm)을 최대 10초 기다린다.
- 커서(어디까지 수집했는지)는 루프가 다 끝난 뒤에 PostgreSQL에 저장한다.

### 1-2. 문제 두 가지

1. **큰 프로젝트의 큐 독점.** 커밋 5,000개짜리 프로젝트가 먼저 연결되면 커밋 50개짜리 프로젝트는 몇 시간을 기다린다.
2. **이중 쓰기.** 한 작업의 결과를 서로 다른 두 저장소(브로커와 DB)에 따로 쓰므로 한쪽만 성공하는 상태가 생긴다. 확인 응답이 늦으면 예외가 나서 수집 전체가 실패하고, 사용자는 연동을 해제했다가 다시 걸어야 한다. 발행과 커서 저장 사이에 프로세스가 죽으면 다음 수집이 같은 이벤트를 다시 발행한다.

## 2. 결정 1: 큐 구조 (2026-10-27)

### 2-1. 전제

비교를 시작하기 전에 다음을 정했다. 전제가 바뀌면 결론도 달라질 수 있어서 함께 적는다.

| 전제 | 내용 | 이유 |
|---|---|---|
| 공정성은 균등 | 프로젝트 사이는 균등하게 번갈아 처리한다. 가중치나 우선순위는 두지 않는다 | 무료 플랜은 프로젝트 1개에 증분 수집이 없어 큐를 오래 점유하지 않는다. 요금제별 우선순위가 필요한 상황이 아직 없다 |
| 진행률 표시는 하지 않는다 | "5,000건 중 1,234건" 같은 표시는 범위에 넣지 않는다 | 웹훅으로 데이터가 계속 들어와 분모가 움직인다. 머지가 잦은 프로젝트일수록 퍼센트가 오르내려 의미가 약하다 |
| 수집 실패 표시는 별도 작업 | 수집 실패를 사용자에게 보여 주는 기능은 이 결정과 독립이다 | 어느 구조를 고르든 같은 모양으로 만들 수 있다 |
| 작업량은 비교 기준에서 뺀다 | 구현에 드는 시간으로 후보를 가르지 않는다 | 문제를 제대로 푸는 구조를 고르는 것이 우선이다 |

### 2-2. 후보 세 가지

세 후보 모두 **트랜잭셔널 아웃박스**를 쓴다. 큐에 넣을 내용을 브로커가 아니라 자기 DB의 표(아웃박스)에 쓰고, 브로커로 옮기는 일은 나중에 따로 하는 방식이다. 수집 트랜잭션이 브로커 상태와 무관하게 성공하므로 "브로커가 느려서 수집 실패"가 사라진다. 후보가 갈리는 지점은 그 표의 행을 누가, 어떻게 ai-engine까지 전달하느냐다.

**A. 아웃박스 + 릴레이 + 프로젝트별 큐.** 릴레이(아웃박스 표의 행을 읽어 브로커로 옮기는 구성요소)가 행을 순서대로 전부 RabbitMQ의 프로젝트별 큐로 옮긴다. 브로커가 큐마다 한 건씩 번갈아 ai-engine에 건네므로 공정성이 브로커의 기본 동작으로 나온다. 그림과 흐름은 2-5.

**B. ai-engine이 표를 직접 읽기.** 표 자체가 큐다. RabbitMQ를 쓰지 않는다.

```
pipeline-worker
  수집기 ──▶ PostgreSQL: 작업 표
                           ▲
                           │ 프로젝트를 점유하고 순번대로 집기, 끝나면 상태 갱신
                       ai-engine ──▶ Neo4j
```

ai-engine이 표에서 다음에 처리할 프로젝트를 번갈아 고르고, 그 프로젝트에 "내가 잡았다, 언제까지"라는 만료 있는 점유(lease)를 건 뒤 이벤트를 순번대로 집는다. 처리 중에는 점유를 주기적으로 연장하고, 연장이 끊겨 만료된 행은 다시 집기 대상이 된다. 실패는 행의 시도 횟수와 마지막 오류에 남는다.

**C2. 표가 정본, 릴레이가 스케줄러.** 큐는 하나만 두고, 릴레이가 프로젝트마다 몇 건씩만 큐에 넣는다.

```
pipeline-worker
  수집기 ──▶ 아웃박스 표
  릴레이 ──▶ 프로젝트마다 "처리 중" 건수가 8건 이하가 되도록 골라 작업 큐에 넣음
  결과 소비자 ◀── 결과 큐에서 완료/실패를 받아 표의 상태를 바꾸고 다음 건을 보충

RabbitMQ
  작업 큐 (1개) ──▶ ai-engine ──▶ Neo4j
  결과 큐       ◀── ai-engine
```

큐 하나 안에서 프로젝트가 섞이므로 공정해진다. ai-engine은 처리가 끝나면 결과 큐에 완료나 실패를 돌려주고, pipeline-worker가 그것을 받아 표를 갱신한다.

### 2-3. 비교

| 주제 | A | B | C2 |
|---|---|---|---|
| 수집과 발행의 분리 | 아웃박스 | 아웃박스 | 아웃박스 |
| ai-engine의 PostgreSQL 접근 | 없음 | 있음 | 없음 |
| 공정성을 만드는 쪽 | 브로커 | 집는 쿼리 | 릴레이의 입장 제어 |
| 소비자가 죽었을 때 재처리 | 브로커 내장(재배달, 처리 시간 제한) | 점유·연장·만료 정리를 직접 구현 | 브로커 내장 |
| ai-engine을 여러 대로 늘릴 때 순서 | 큐마다 단일 활성 소비자 | 프로젝트 점유 | 프로젝트별 큐로 전환 필요 |
| 가중치 정책을 넣는 곳 | ai-engine의 처리 슬롯 배분 | 집는 쿼리 | 창 크기·보충 빈도 |
| 진행률·실패 이력 | 표와 브로커를 합쳐야 함 | 표 한 곳 | 표 한 곳 |
| 멈춘 프로젝트 진단 | 표 + 브로커 | 표 한 곳 | 표 + 브로커 |
| 구성요소 | RabbitMQ 유지 | RabbitMQ 불필요 | RabbitMQ 유지 + 결과 큐 |
| 새로 관리할 것 | 프로젝트 큐의 선언·발견·수명 | DB 역할, 통합 테스트 환경, 행 정리 | 릴레이 스케줄러, 결과 큐 |
| 백로그 위치 | 브로커(diff 포함) | 표 | 표(브로커에는 창만) |
| 새 로직의 검증 | Spring 쪽 기존 테스트 흐름 | ai-engine에 PostgreSQL 통합 테스트 환경 신설 | Spring 쪽 + 결과 큐 소비자 |
| 변경 폭 | 가장 작음 | 전달 매체 교체 | 중간 |

### 2-4. A를 고른 이유

전제(균등 공정, 진행률 없음, 요금제 정책 없음) 아래에서 A가 다른 둘보다 나은 점은 넷이다.

1. **경계를 지킨다.** ai-engine이 PostgreSQL에 닿지 않는다.
2. **재처리 장치를 직접 짜지 않는다.** 브로커의 재배달과 처리 시간 제한, 단일 활성 소비자를 쓰고, 이미 있는 재시도 큐·DLQ·parking 큐·모니터링이 그대로 살아 있다.
3. **균등 공정성이 기본 동작으로 나온다.** 큐를 프로젝트별로 나누면 끝이다. 스케줄러를 짤 필요가 없다.
4. **변경 폭이 가장 작다.** pipeline-worker에 아웃박스 표와 릴레이가 생기고, ai-engine은 구독하는 큐의 모양만 바뀐다.

B의 장점인 "진단 한 곳", "큐 관리 없음", "브로커 백로그 없음"은 자격증명 확대와 점유 장치의 자체 구현보다 가볍다고 판단했다. C2의 핵심 장점은 진행률이었는데 전제에서 빠졌다.

표만으로 이유가 전달되지 않는 주제는 아래에 따로 적는다.

**ai-engine이 PostgreSQL에 닿지 않게 한 이유.** 여러 서비스가 한 DB를 공유하면 표가 통보 없이 바뀔 때 상대 서비스가 실행 중에 깨지고, 누가 주인인지 흐려지고, 독립 배포가 막힌다. B도 조건을 갖추면 변호할 수 있다. 전용 논리 DB, 읽기와 상태 열 갱신만 허용하는 역할 권한, 열은 추가만 허용, 계약 테스트, 접근 코드의 격리, 이 다섯이다. 그러나 다섯 조건을 세우고 지키는 비용이 생긴다. 보안 면에서도 차이가 크다. ai-engine은 외부에서 온 diff·이슈·메시지를 LLM에 넣는 서비스라 프롬프트 인젝션에 가장 넓게 노출돼 있다. 여기서 코드 실행이 나면 B에서는 그 자격증명으로 모든 사용자의 코드 diff를 보관 기간 내내 읽을 수 있다. A에서는 메시지로 흐르는 동안에만 보인다. A는 이 비용을 처음부터 만들지 않는다.

**커서를 아웃박스 트랜잭션에 넣지 않은 이유.** 교과서형 아웃박스는 "이벤트 저장 + 커서 갱신"을 한 트랜잭션으로 묶는다. 여기서는 이벤트만 넣는다. 커서를 쓰는 시점이 커넥터마다 달라서다. GitHub는 커밋 루프 뒤에 PR 커서를 쓰고, 정렬이 내림차순으로 고정된 API(Linear·Notion)는 수집이 끝난 뒤에만 쓸 수 있다. 유실은 "INSERT가 전부 성공한 뒤에만 커서를 쓴다"는 순서로 막는다. 남는 것은 INSERT 뒤, 커서를 쓰기 전에 죽었을 때의 재수집 중복이고, ai-engine이 같은 이벤트를 두 번 받아도 결과가 같게 쓰므로(멱등) 피해는 처리 비용뿐이다. 묶으려면 커넥터별 커서 시점을 다시 설계해야 해서 하지 않았다.

**균등 공정성만 둔 이유.** 다른 정책 후보는 모두 접었다.

| 후보 정책 | 판단 |
|---|---|
| 작은 프로젝트 먼저 | 작은 것이 계속 들어오면 큰 것이 영원히 밀린다. 채택하지 않는다 |
| 요금제 가중치 | 무료 플랜은 프로젝트 1개에 증분 수집이 없어 지금은 필요 없다 |
| OpenAI 예산에 따라 항목 크기 고르기 | 한도가 분 단위로 초기화되고 호출 조절 장치가 이미 있다. 효과 없다 |
| 질의 중인 프로젝트에 양보 | 질의 호출은 수집용 동시 실행 제한을 거치지 않는다. 이미 대부분 해결돼 있다 |

큐 하나에 전부 넣으면 초기 구조의 독점이 그대로 재현되므로, "큐 하나"를 고르면 릴레이의 입장 제어가 필수가 되고 그것이 C2다. 나중에 가중치가 필요해지면 A에서도 ai-engine이 큐별로 미리 받아 둔 메시지 사이에서 처리 슬롯을 배분하는 비율로 넣을 수 있다.

### 2-5. 바뀐 뒤 구조

```
pipeline-worker
  수집기 ──▶ PostgreSQL: 아웃박스 표 (이벤트 N건, 페이지마다 한 트랜잭션. 커서는 따로)
  릴레이 ──▶ 아웃박스 행을 번호 순으로 RabbitMQ에 옮기고 "보냈음" 표시

RabbitMQ
  history.project.<projectId 1>  ─┐
  history.project.<projectId 2>  ─┼─ 큐마다 한 건씩 번갈아 ──▶ ai-engine ──▶ Neo4j
  history.project.<projectId N>  ─┘   (큐마다 단일 활성 소비자)
                                      재시도 큐 / DLQ / parking 큐
```

1. 수집기는 페이지를 받을 때마다 이벤트 행들을 한 트랜잭션으로 아웃박스 표에 저장한다. 브로커와는 대화하지 않는다.
2. 릴레이가 1초마다 아직 안 보낸 행을 번호 순으로 읽어 해당 프로젝트 큐에 발행하고, 브로커의 확인 응답을 받은 행을 "보냈음"으로 표시한다. 큐는 발행 전에 선언한다. 보낸 행은 하루 뒤에 지운다.
3. ai-engine은 프로젝트 큐들을 구독하고, 브로커가 큐마다 한 건씩 번갈아 건네 준다. 큐마다 단일 활성 소비자(큐 하나에 소비자가 여럿 붙어도 한 번에 하나만 받게 하는 RabbitMQ 기능)를 켜 두어, ai-engine을 여러 대로 늘려도 한 프로젝트의 이벤트는 한 인스턴스로만 간다.
4. ai-engine은 5초마다 RabbitMQ 관리 HTTP API에서 큐 목록을 읽어 새 큐는 구독하고 사라진 큐는 정리한다. 큐는 영구이고, 프로젝트를 삭제할 때 ai-engine이 지운다. 연동 해제는 큐를 지우지 않는다.
5. 처리에 실패한 이벤트는 재시도 큐를 거쳐 원래 프로젝트 큐로 돌아오고, 횟수를 다 쓰면 DLQ에 보관된다.

**릴레이가 지키는 순서의 범위.** 커밋 뒤에 그 커밋을 가리키는 PR 갱신이 오고, 만든 뒤에 지우는 이벤트가 오므로 순서는 지켜야 한다. 릴레이는 번호 순으로 보내므로, 실패가 없는 한 같은 프로젝트의 같은 소스 안에서는 보낸 순서가 지켜진다. 브로커가 거부한 행은 혼자 재시도하느라 뒤 행보다 늦게 나갈 수 있다(3-5). 한 프로젝트에서 소스 여럿이 동시에 수집될 때는 번호 순서(INSERT 시점)와 커밋 순서가 어긋날 수 있어 소스 사이의 순서는 보장하지 않는다. 순서가 필요한 관계는 전부 같은 소스 안에 있어 피해는 없다.

### 2-6. 받아들이는 비용

- **프로젝트 큐의 관리.** 선언은 pipeline-worker가, 발견은 ai-engine이 맡는다. 발견이 늦어도 이벤트는 내구 큐에 남아 있어 유실은 없고 지연만 있다.
- **백로그가 브로커에 diff째 쌓인다.** 지금 규모에서는 문제가 없다. 커지면 diff를 메시지 밖에 두고 참조만 싣는 방식을 붙인다.
- **진단이 두 곳으로 갈린다.** 멈춘 프로젝트를 볼 때 표의 "보냈음"과 브로커의 큐 상태를 함께 본다.
- **가중치 정책의 위치.** 브로커에는 가중 배분이 없어, 필요해지면 ai-engine의 슬롯 배분에서 해야 한다.
- **기존 DB 공유는 그대로다.** pipeline-worker는 backend 소유의 연동 표를 직접 읽고, backend는 pipeline-worker의 커서 표를 읽고 지운다. 표 정의(Flyway)도 전부 backend에 있다. 이 결정에서 정리하지 않았다.

### 2-7. 다시 꺼낼 조건

- **B로 뒤집히는 경우.** 운영 진단을 한 곳에서 하는 것이 중요해지거나, RabbitMQ를 운영 항목에서 빼기로 하거나, 균등이 아닌 복잡한 정책을 처리 직전 부하에 따라 정해야 할 때. 세 후보가 아웃박스 표를 공유하므로 ai-engine에 표를 읽는 코드를 붙이면 옮겨 갈 수 있다.
- **C2로 뒤집히는 경우.** 진행률이나 실패 이력을 표 한 곳에서 보여 줘야 하는데 ai-engine은 여전히 PostgreSQL에 닿지 않아야 할 때.

함께 검토했다가 접은 변형은 셋이다.

- **아웃박스 없이 서비스별 DB만 분리한 A.** 이중 쓰기가 그대로 남는다.
- **완료를 HTTP 콜백으로 돌려주는 C.** ai-engine에는 실패한 콜백을 보관할 저장소가 없고, 릴레이가 "느린지 죽었는지"를 알 수 없어 주기적 생존 신호까지 필요해진다. 결과 큐 방식(C2)으로 대체했다.
- **A에 결과 큐를 더한 것.** 진행률을 빼면 결과 큐의 용도가 사라져 A와 같아진다.

## 3. 결정 2: 릴레이가 보내지 못하는 행의 처리 (2026-11-11, 실기동 2026-11-13)

### 3-1. 문제

결정 1의 릴레이는 아직 안 보낸 행을 프로젝트 구분 없이 번호 순으로 200건씩 읽고, 첫 실패 앞까지만 "보냈음"으로 표시했다.

1. **행 하나가 전체를 세운다.** 브로커가 계속 거부하는 행(예: 본문이 브로커의 크기 제한을 넘는 메시지)이 맨 앞에 있으면, 그 뒤의 모든 프로젝트가 같이 선다.
2. **신호가 경고 로그뿐이다.** 바꾸기 전에는 브로커 문제가 수집 실패로 시끄럽게 드러났지만, 아웃박스 뒤로는 수집은 성공하고 전달만 조용히 멈춘다.
3. **재전송 간격이 늘지 않는다.** 실패한 묶음을 약 11초마다 그대로 다시 보낸다.

### 3-2. 고른 방식

실패한 **행만** 정상 흐름에서 빼서 혼자 재시도한다. 나머지 행은 같은 프로젝트·같은 소스 것이라도 계속 나간다.

릴레이가 한 번 도는 것(틱)은 두 단계다.

| 단계 | 대상 | 보내는 방식 |
|---|---|---|
| ① 재시도 단계 | 실패한 적이 있고(`attempts` 1 이상) 다음 시도 시각이 지난 행 | 번호 순으로 **한 건씩**. 행마다 응답을 기다린다 |
| ② 정상 단계 | 실패한 적 없는 행(`attempts` 0) | 200건씩 **묶어서** |

행을 보낸 결과는 셋 중 하나다. 브로커가 받았다고 답하거나(ack), 받지 않겠다고 답하거나(nack, 또는 보낼 큐가 없다는 반환), 제한 시간(10초) 안에 답이 없거나.

| 항목 | 내용 |
|---|---|
| 상태를 두는 곳 | 아웃박스 표의 행. `attempts`(실패 횟수)와 `next_attempt_at`(다음 시도 시각) 열 |
| 실패로 세는 기준 | 브로커가 **명시적으로 거부**한 행은 어느 단계에서든 센다. **답이 없는 것**은 혼자 보냈을 때(①)만 세고, 묶음(②)에서는 세지 않는다 |
| 재시도 간격 | 묶음에서 거부되면 바로 다음 틱에 혼자 보낸다. 그 뒤로 5초·15초·30초·60초로 늘리고, 이후에는 10분마다 계속한다. 멈추지 않는다 |
| 행 실패 알림 | 5번째 실패(첫 실패부터 약 50초)에 Slack으로 알린다. 계속 실패하면 1시간에 한 번 다시 알린다 |
| 적체 알림 | pipeline-worker가 1분마다 "보낼 수 있어야 할 행" 중 가장 오래된 것의 나이를 본다. 10분을 넘으면 Slack으로 알린다 |
| 브로커에 닿지 못할 때 | 큐 선언이나 전송 자체가 실패하면 행에 아무것도 기록하지 않고, 릴레이의 다음 시도를 1·2·4·8·16·30초씩 늦춘다 |

**첫 재시도를 바로 하는 이유.** 묶음에서 거부됐다고 그 행이 문제라는 뜻은 아니다. 다른 행 때문에 채널(연결 하나 안의 논리적 통로)이 닫혀 같은 채널의 행이 덩달아 거부될 수 있다. 혼자 보내 봐야 원인이 가려지므로 기다릴 이유가 없고, 기다리면 그사이 같은 소스의 새 행이 먼저 나가 순서가 밀린다. ①이 ②보다 먼저 돌기 때문에 덩달아 거부된 행들은 새 행보다 먼저, 원래 번호 순서로 다시 나간다.

**"답이 없는 것"을 단계별로 달리 세는 이유.** 릴레이는 답이 없는 원인을 알 수 없다. 묶음에서는 200건이 같이 나갔으니 어느 행 탓인지 가릴 수 없고, 대개 브로커 쪽 문제다. RabbitMQ는 메모리나 디스크가 부족하면 보내는 쪽 연결을 막는데, 이때 릴레이에는 "답이 없음"으로만 보인다. 이것을 세면 멀쩡한 행 200건이 한꺼번에 재시도 상태로 넘어간다. 반대로 혼자 보냈는데 답이 없는 행을 세지 않으면 그 행이 매 틱 10초를 차지한다. 그래서 혼자 보냈을 때만 센다.

**알림을 둘로 나눈 이유.** 잡는 상황이 다르다. 행 실패 알림은 "특정 행이 계속 거부된다"이고 릴레이가 실패를 기록하는 순간에 보낸다. 적체 알림은 "보낼 수 있어야 할 행이 안 나가고 있다"이고, 실패라는 사건이 없어도 알려야 해서 표를 주기적으로 본다. 브로커 장애, 브로커가 보내는 쪽을 막은 상태, 릴레이가 멈춘 경우가 여기에 걸린다. 적체 점검은 이미 행 실패 알림이 나간 행(`attempts` 5 이상)을 빼고 보므로, 미발행 행은 둘 중 하나에 걸린다.

### 3-3. 바뀐 뒤 동작

14:00:00에 A 프로젝트의 행 501·502·503과 B 프로젝트의 행 504·505가 미발행이고, 502가 계속 거부된다고 하자.

| 시각 | 일어나는 일 | 502번 행 |
|---|---|---|
| 14:00:00 | ② 5건을 묶어 보낸다. 502만 거부. 501·503·504·505는 "보냈음" 표시 | `attempts=1`, 바로 재시도 |
| 14:00:01 | ① 502를 혼자 보낸다. 거부. ② 새 행이 있으면 묶어 보낸다 | `attempts=2`, 5초 뒤 |
| 14:00:06, :21, :51 | ① 502를 혼자 보낸다. 거부 | `3`, `4`, `5`. 5가 되는 순간 **행 실패 알림**(프로젝트, 소스, 행 번호, 사유) |
| 14:01:51 | 다시 거부 | `attempts=6`, 이후 10분마다 |
| 이후 | 실패할 때마다 알림 함수를 부르고, 1시간에 한 번만 실제로 전송된다 | `attempts` 증가 |
| 원인 해소 뒤 | 다음 재시도가 성공한다 | `published_at` 채워짐 |

운영자가 다시 켜는 절차는 없다. 원인(브로커 설정, 보낼 수 없는 행)을 고치면 다음 재시도에서 스스로 재개된다. 기다리기 싫으면 그 행의 `next_attempt_at`을 지금으로 당긴다(`docs/deployment.md` 4-6).

### 3-4. 검토하고 접은 선택지

**실패한 행의 소스 전체를 기다리게 하기.** 한 행이 실패하면 같은 프로젝트의 같은 소스에 속한 뒤 행을 전부 세워 순서를 지키려던 방식이고, 처음에는 이것을 골랐다. 접은 이유는 셋이다. 첫 묶음에서 실패한 행의 뒤 행이 이미 큐에 들어가므로 순서를 완전히 지키지 못한다. ai-engine도 처리에 실패한 이벤트만 미루고 다음 이벤트를 처리하므로, 릴레이만 순서를 지켜도 끝까지 유지되지 않는다. 그리고 소스 전체가 운영자 조치 때까지 멈추고, 밀린 행을 매 틱 읽고 버리는 비용이 생긴다.

**5회 실패 뒤 완전히 멈추기.** 알림을 보낸 뒤 재시도를 그만두는 방식이다. 원인을 고친 뒤 운영자가 실패 횟수를 되돌리는 SQL을 실행해야 재개되고, 일시 장애를 잘못 판정하면 사람이 풀 때까지 멈춘다. 실패가 더는 일어나지 않아 다시 알릴 계기도 없다. 10분에 전송 한 건이라는 비용으로 이 셋을 없앴다.

**상태를 pipeline-worker의 메모리에 두기.** 표를 바꾸지 않는 대신, 행이 사라질 때(프로젝트 삭제, 연동 해제) 상태를 따로 지워야 하고 재시작마다 횟수가 0으로 돌아가며 릴레이를 여러 대로 늘리면 쓸 수 없다. 표의 열은 행과 함께 사라져 뒷정리가 없다.

**답이 없는 것을 전부 세기.** 묶음의 시간 초과도 행의 실패로 세는 방식이다. 브로커가 보내는 쪽을 막으면 멀쩡한 행이 200건씩 재시도 상태로 넘어가 엉뚱한 행 실패 알림이 가고, 풀린 뒤에도 최대 10분 늦게, 순서가 밀려 나간다.

**답이 없는 것을 전혀 세지 않기.** 혼자 보내도 답이 없는 행이 매 틱 맨 앞에서 10초를 쓰고, 그동안 정상 행이 밀린다.

**적체 점검을 ai-engine에 두기.** ai-engine은 PostgreSQL에 닿지 않아 아웃박스 표를 볼 수 없고(2-4), 알 수 있는 것은 자기 RabbitMQ 연결이 끊겼다는 것뿐이다. 그래서 Slack 전송 코드를 pipeline-worker에도 두었다. 환경변수는 ai-engine과 같은 `ALERT_SLACK_WEBHOOK_URL`이다.

### 3-5. 받아들이는 비용

- **혼자 보내도 실패하는 행은 순서가 밀린다.** 그 행은 같은 소스의 뒤 행보다 늦게 도착한다. ai-engine은 이벤트 시각을 비교하지 않고 받은 순서대로 쓰므로, 늦게 도착한 옛 내용이 새 내용을 덮어쓸 수 있다. ai-engine의 재시도에도 같은 성질이 이미 있다.
- **브로커 장애 중에는 원래 실패 중이던 행의 횟수가 잘못 오른다.** 그 행은 자기 차례에 혼자 나갔다가 답을 못 받는다. 영향은 숫자와 최대 10분의 추가 지연이다.
- **덩달아 거부된 행이 재시도를 기다리는 순간에 브로커가 막히면 그 행들이 늦게 나간다.** 두 사건이 1초 안에 겹쳐야 한다.
- **알림 억제는 메모리에 있고 종류 단위다.** pipeline-worker를 재시작하면 다음 실패 때 알림이 한 번 더 간다. 또 한 행의 알림이 나간 뒤 1시간 안에 다른 행이 5회 실패해도 Slack에는 오지 않으므로, 알림을 받으면 실패 중인 행 전체를 SQL로 본다(`docs/deployment.md` 4-6).
- **pipeline-worker가 죽으면 적체 점검도 멈춘다.** 이 경우는 컨테이너 재시작 알림이 맡는다.
- **같은 이름의 큐가 다른 설정으로 미리 만들어져 있으면 여전히 전체가 선다.** 큐 선언이 거부되는 경우이고 행의 실패로 세지 않는다. 적체 알림으로 10분 안에 드러난다.
- **진단은 여전히 두 곳이다.** 실패 횟수는 표에서, 큐 상태는 브로커에서 본다.

### 3-6. 실기동에서 확인한 것 (2026-11-13, 로컬 스택)

| 상황 | 관찰 |
|---|---|
| 한 프로젝트의 큐가 발행을 거부 | 그 프로젝트의 행만 남고 같은 묶음의 다른 프로젝트 행은 나갔다. 넣은 뒤 1·2·7·22·52초에 `attempts` 1·2·3·4·5, 5회째에 알림 한 줄 |
| 크기 제한을 넘는 행이 묶음 가운데에 있음 | 브로커는 채널만 닫고 연결은 유지했다. 원인 행은 시간 초과가 아니라 **거부**로 돌아왔다. 뒤 행 하나의 전송이 닫히는 채널에서 예외로 끝났고, 그 뒤 행들은 다음 틱에 묶음으로 나갔다. 횟수가 오른 것은 원인 행뿐이고 유실·중복은 없었다 |
| 브로커 정지 | 모든 행의 횟수가 그대로였고, 재시도 간격이 늘어났다. 재시작 30초 뒤 밀린 행이 한 번에 나갔다 |
| 브로커가 보내는 쪽만 막음 | 새 행의 횟수가 0으로 유지됐고, 풀린 뒤 8초에 나갔다. 중복은 3행 중 1건 |
| 미발행 행이 10분 넘게 남음 | 다음 1분 점검에서 적체 알림 |

브로커가 보내는 쪽을 막은 상태에서 한 가지를 고쳤다. 릴레이는 메시지를 보내기 전에 채널 열기·큐 선언 요청의 응답을 기다리는데, 이 대기 한도의 기본값이 10분이라 릴레이가 그 자리에서 멈췄다. 한도를 10초로 줄여(`spring.rabbitmq.channel-rpc-timeout`) 막힌 동안에도 간격을 늘려 가며 재시도하고 로그를 남기게 했다.

### 3-7. 다시 꺼낼 조건

- **미발행 행이 수만 건 쌓인 채 오래 갈 때.** 재시도 대상 조회가 미발행 행 전체를 훑는다. 실패한 적 있는 행만 담는 부분 인덱스를 넣는다.
- **릴레이를 여러 대로 늘릴 때.** 지금은 한 대만 도는 전제다. 늘리면 같은 행을 둘이 집지 않게 하는 장치와 함께, 알림 억제를 메모리에서 공유 저장소로 옮겨야 한다.
- **보낼 수 없는 행이 자주 생길 때.** 지금은 운영자가 행을 직접 고치거나 지운다. 잦아지면 그 행을 별도 표로 옮겨 보관하는 격리 장치를 검토한다.
- **순서가 밀려 옛 내용이 새 내용을 덮어쓰는 일이 실제로 보일 때.** ai-engine에서 이벤트 시각을 비교해 옛 이벤트의 덮어쓰기를 막는다.
