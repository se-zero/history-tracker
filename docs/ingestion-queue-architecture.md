# 수집 큐 아키텍처 결정 기록

> **결정(2026-10-27): A. 트랜잭셔널 아웃박스 + 프로젝트별 큐.**
> 이 문서는 "왜 이 구조인가"를 남기는 문서다. 구현 계획과 단계는 별도 문서에서 다룬다.

## 0. 한 장 요약

**풀려는 문제 두 가지**

1. 수집 큐가 하나뿐이라 먼저 들어온 큰 프로젝트가 큐를 독점한다. 커밋 5,000개짜리 프로젝트가 먼저 연결되면 커밋 50개짜리 프로젝트는 몇 시간을 기다린다.
2. 수집기가 "브로커에 발행"과 "커서 저장"을 서로 다른 두 저장소에 따로 쓴다. 브로커가 느리면 수집 전체가 실패하고, 중간에 죽으면 재수집 때 같은 이벤트가 또 발행된다.

**검토한 후보 세 가지**

| 이름 | 한 줄 정의 |
|---|---|
| **A** | 수집기는 DB의 아웃박스 표에만 쓰고, 릴레이가 그 행을 RabbitMQ의 **프로젝트별 큐**로 옮긴다. 공정성은 브로커가 큐를 번갈아 비우면서 만든다 |
| **B** | 작업 표 자체가 큐다. ai-engine이 Postgres의 표를 직접 집어 처리하고 상태를 갱신한다. RabbitMQ는 쓰지 않는다 |
| **C2** | 표가 정본이고, 릴레이가 스케줄러가 되어 프로젝트마다 몇 건씩만 단일 큐에 넣는다. ai-engine은 처리 결과를 결과 큐로 돌려준다 |

**결정: A.** 이유는 넷이다. ai-engine이 Postgres에 닿지 않아 보안과 계약 비용이 생기지 않고, 배달 보장을 브로커와 기존 재시도·DLQ 장치로 해결하며, 균등 공정성이 브로커의 기본 동작으로 나오고, 변경 폭이 가장 작다. 자세한 근거는 5장.

## 1. 배경

### 1-1. 지금 구조

```
외부 소스 ──API 수집──▶ pipeline-worker ──발행(페이지마다)──▶ RabbitMQ ──소비──▶ ai-engine ──▶ Neo4j
                            │                               (큐 1개, 선입선출)
                            │ 루프가 끝나면 커서 저장
                            ▼
                        PostgreSQL
```

- 큐가 하나이고 선입선출이다. 프로젝트 사이에 순서를 조정하는 장치가 없다.
- 수집기는 한 페이지를 수집할 때마다 브로커에 발행하고, 브로커가 받았다는 확인(confirm)을 최대 10초 기다린다. 확인이 늦으면 예외가 나서 수집 전체가 실패하고, 사용자는 연동을 해제했다가 다시 걸어야 한다.
- 커서(어디까지 수집했는지)는 루프가 다 끝난 뒤에 저장한다. 발행과 커서 저장 사이에 프로세스가 죽으면, 다음 수집이 같은 이벤트를 다시 발행한다. 지금은 ai-engine이 같은 노드를 두 번 받아도 한 번만 만드는 병합 쓰기로 버티고 있을 뿐이다.

### 1-2. 이 결정의 전제

비교를 시작하기 전에 다음을 정했다. 전제가 바뀌면 결론도 달라질 수 있어서 함께 적는다.

| 전제 | 내용 | 이유 |
|---|---|---|
| 공정성은 균등 | 프로젝트 사이는 균등 라운드로빈. 가중치나 우선순위는 두지 않는다 | 무료 플랜은 프로젝트 1개에 증분 수집이 없어 큐를 오래 점유하지 않는다. 요금제별 우선순위가 필요한 상황이 아직 없다 |
| 진행률 표시는 하지 않는다 | "5,000건 중 1,234건" 같은 표시는 이번 범위에 넣지 않는다 | 웹훅으로 데이터가 계속 들어오므로 분모가 계속 움직인다. PR과 머지가 잦은 프로젝트일수록 퍼센트가 오르내려 의미가 약하다 |
| 수집 실패 표시는 별도 작업 | 수집이 실패했음을 사용자에게 보여 주는 기능은 이 결정과 독립이라 따로 다룬다 | 어느 구조를 고르든 같은 모양으로 만들 수 있다 |
| 작업량은 비교 기준에서 뺀다 | 구현에 드는 시간은 후보를 가르는 기준으로 쓰지 않는다 | 지금의 문제를 제대로 푸는 구조를 고르는 것이 우선이다 |

## 2. 고려한 주제

후보를 가를 때 따진 주제를 하나씩 적는다. 주제마다 "무엇을 따졌나", "선택지", "이 결정에서의 결론" 순서다.

### 2-1. 인계의 원자성

**무엇을 따졌나.** 수집기가 이벤트를 큐에 넘기는 순간, "커서 저장"과 "이벤트 발행"이 하나의 단위로 성공하거나 실패하는가. 둘을 서로 다른 저장소에 따로 쓰는 것을 **이중 쓰기**라고 부르고, 한쪽만 성공하는 상태가 생길 수 있다.

**선택지.**

| 선택지 | 설명 |
|---|---|
| 지금처럼 | 브로커에 발행한 뒤 DB에 커서 저장. 두 저장소, 원자성 없음 |
| 트랜잭셔널 아웃박스 | 이벤트를 브로커가 아니라 자기 DB의 표(아웃박스)에 쓴다. 교과서형은 커서까지 같은 트랜잭션에 넣지만 여기서는 이벤트만 넣는다(이유는 아래 결론). 브로커로 옮기는 일은 나중에 따로 한다 |

**결론.** 아웃박스. 세 후보 모두 아웃박스를 포함한다. 수집 트랜잭션이 브로커 상태와 무관하게 성공하므로 "브로커가 느려서 수집 실패"가 사라진다. 커서는 같은 DB에 지금 시점대로 쓰며 이 트랜잭션에 넣지 않는다 — 커서를 쓰는 시점이 커넥터마다 달라(GitHub는 커밋 루프 뒤, 내림차순 API는 런 끝) 페이지 트랜잭션에 묶을 수 없고, 유실은 "INSERT가 전부 성공한 뒤에만 커서"라는 순서로 막힌다.

### 2-2. 서비스 경계와 DB 소유권

**무엇을 따졌나.** ai-engine이 Postgres에 닿아도 되는가. 마이크로서비스 원칙에서 여러 서비스가 한 DB를 공유하는 것은 가장 강한 결합으로 분류된다. 표가 통보 없이 바뀌면 상대 서비스가 실행 중에 깨지고, 누가 주인인지 흐려지고, 독립 배포가 막히기 때문이다.

지금도 공유는 있다. pipeline-worker는 backend 소유의 연동 표를 SQL로 직접 읽고, backend는 pipeline-worker가 쓰는 커서 표를 읽고 지운다. 표 정의(Flyway)는 전부 backend에 있다. 이 결정에서 이 기존 공유를 정리하지는 않고, 별도 작업으로 둔다.

**선택지.**

| 선택지 | 설명 |
|---|---|
| 닿지 않는다 | ai-engine은 브로커와 HTTP만 본다. 교과서적 경계 |
| 인터페이스로 공개된 표에만 닿는다 | 도메인 표가 아니라 작업 큐 표 하나를 인터페이스로 공개한다. 전용 논리 DB, 읽기와 상태 컬럼 갱신만 허용하는 역할 권한, 컬럼은 추가만 허용, 계약 테스트, 포트/어댑터 격리를 조건으로 한다 |

**결론.** 닿지 않는다(A). 두 번째 선택지도 조건을 갖추면 변호할 수 있지만, 조건 다섯 개를 세우고 지키는 비용이 생긴다. 그 비용을 처음부터 만들지 않는 쪽을 골랐다.

### 2-3. 데이터의 성격과 보관

**무엇을 따졌나.** 이벤트에는 커밋의 diff 본문이 통째로 실린다. 브로커는 전달하고 버리는 저장소라 처리가 끝나면 사라지고, 다시 처리하려면 GitHub를 다시 호출해야 한다. GitHub는 시간당 호출 한도가 있다. 표에 두면 처리 뒤에도 남길 수 있지만 얼마나 남길지 정해야 한다.

**선택지.**

| 선택지 | 설명 |
|---|---|
| 브로커에만 | 처리 후 사라진다. 재처리는 재수집 |
| 표에 두고 즉시 삭제 | 브로커와 같다 |
| 표에 두고 며칠 보관 | 그 기간 안에서는 GitHub 호출 없이 재발행할 수 있다 |
| 영구 보관 | 원문 저장소가 된다. 용량 관리가 필요하다 |

**결론.** A에서도 아웃박스 행은 발행 뒤 바로 지우지 않고 며칠 보관한 뒤 지우는 것을 기본안으로 둔다. 기간은 계획 때 정한다. 백로그가 커져 브로커 용량이 문제가 되면 diff를 메시지 밖에 두고 참조만 싣는 방식(Claim Check)을 그때 붙인다.

### 2-4. 공정성을 만드는 장치

**무엇을 따졌나.** 프로젝트 사이를 번갈아 처리하게 만드는 장치를 어디에 두는가.

**선택지.**

| 선택지 | 설명 | 특징 |
|---|---|---|
| 브로커의 프로젝트별 큐 | 프로젝트마다 큐를 하나씩 두고, 브로커가 큐마다 한 건씩 번갈아 소비자에게 건넨다 | 브로커 기본 동작. 균등만 된다 |
| 집는 쿼리 | ai-engine이 표에서 집을 때 쿼리로 프로젝트를 고른다 | 정책 자유. 직접 짜야 한다 |
| 릴레이의 입장 제어 | 큐는 하나만 두고, 릴레이가 프로젝트마다 몇 건씩만 큐에 넣는다. 끝난 만큼 보충한다 | 큐 하나로 공정성을 얻는 유일한 방법. 릴레이가 완료를 알아야 한다 |

**결론.** 브로커의 프로젝트별 큐(A). 전제가 "균등"이라 브로커 기본 동작으로 충분하다. 큐 하나에 전부 넣으면 지금의 독점이 그대로 재현되므로, "큐 하나"를 고르면 입장 제어가 필수가 되고 그것이 C2다.

### 2-5. 정책

**무엇을 따졌나.** 균등 말고 다른 규칙이 필요한가. 요금제별 가중치, 작은 프로젝트 먼저, 처리 용량이나 OpenAI 예산에 따라 고르기, 질의 중인 프로젝트 양보 같은 것들이다.

**선택지와 판단.**

| 후보 정책 | 판단 |
|---|---|
| 작은 것 먼저 | 작은 것이 계속 들어오면 큰 것이 영원히 밀린다(기아). 채택하지 않는다 |
| 요금제 가중치 | 무료 플랜은 프로젝트 1개에 증분 없음이라 지금은 필요 없다 |
| OpenAI 예산에 따라 항목 크기 고르기 | 한도가 분 단위로 초기화되고 limiter가 이미 호출을 조절한다. 효과 없다 |
| 질의 중 프로젝트 양보 | 질의 호출은 배경 게이트를 거치지 않고, limiter가 조직 전체 소비를 반영한다. 이미 대부분 해결돼 있다 |

**결론.** 균등만. 나중에 가중치가 필요해지면 A에서도 ai-engine이 큐별로 미리 받아 둔 버퍼 사이에서 처리 슬롯을 배분하는 비율로 넣을 수 있다.

### 2-6. 가시성

**무엇을 따졌나.** 사용자에게 진행률을 보여 줄 것인가, 실패 이력을 어디에 남길 것인가, 운영자가 "멈춘 프로젝트"를 어디서 진단하는가.

**선택지.**

| 항목 | 표가 정본일 때(B, C2) | 브로커가 정본일 때(A) |
|---|---|---|
| 진행률 | 표 집계 한 번 | 표의 "보낸 수"와 브로커의 "남은 수"를 합쳐야 함 |
| 실패 이력 | 표의 컬럼 | DLQ 메시지 |
| 멈춘 프로젝트 진단 | 표 한 곳 | 표와 브로커 둘 다 |

**결론.** 진행률은 전제에서 뺐다. 실패 표시는 별도 작업이다. 그래서 가시성은 더 이상 후보를 가르는 기준이 아니고, 운영자 진단이 두 곳으로 갈리는 것만 A의 비용으로 남는다.

### 2-7. 배달 보장과 신뢰성

**무엇을 따졌나.** 소비자가 처리 중에 죽으면 누가 알아채고 다시 처리하게 하는가. "느린 것"과 "죽은 것"을 구분할 방법은 없으므로 어디선가 시간 제한을 둬야 한다.

**선택지.**

| 선택지 | 설명 |
|---|---|
| 브로커 | 확인(ack)이 안 된 채 연결이 끊기면 메시지를 큐로 되돌린다. 처리 시간 제한(consumer timeout)이 고정 임대 역할을 한다. 재시도 큐와 DLQ는 이미 있다 |
| 표의 lease | 집을 때 행에 "내가 잡았다, 언제까지"를 적고, 처리 중 주기적으로 연장한다. 만료된 행은 다시 집는다. 직접 구현해야 한다 |

**결론.** 브로커(A). 검증된 장치를 쓰고 기존 재시도·DLQ·parking 큐와 모니터링을 그대로 살린다.

### 2-8. 보안

**무엇을 따졌나.** B를 고르면 Python 서비스(ai-engine)가 Java 서비스가 소유한 DB의 자격증명을 갖게 된다. ai-engine은 외부에서 온 diff·이슈·메시지를 LLM에 넣는 서비스라 프롬프트 인젝션 표면이 가장 넓다. 여기서 코드 실행이 나면 그 자격증명으로 작업 표 전체, 즉 전 테넌트의 코드 diff를 보관 기간 내내 읽을 수 있다. 지금도 메시지로 흐르는 동안은 보지만, "흐르는 동안"에서 "보관 기간 전체"로 넓어진다. 그 밖에 비밀이 하나 늘고, 새 SQL 경로가 생기고, DB 네트워크 노출이 늘어난다.

**선택지.** 전용 역할과 논리 DB 격리, 컬럼 단위 갱신 권한, 파라미터 바인딩, 클라우드에서는 IAM 인증으로 줄일 수 있다. 다만 줄이는 것이지 없애는 것은 아니다. ai-engine이 Postgres에 닿지 않으면 이 항목 자체가 없다.

**결론.** A는 이 비용이 없다.

### 2-9. 수평 확장과 순서

**무엇을 따졌나.** ai-engine을 두 대 이상 띄울 때 같은 프로젝트의 이벤트 순서를 어떻게 지키는가. 커밋 뒤에 그 커밋을 가리키는 PR 갱신이 오고, 만든 뒤에 지우는 이벤트가 오므로 프로젝트 안의 순서는 지켜야 한다. "소비자가 여럿"과 헷갈리기 쉬운데, 같은 서비스의 인스턴스 여러 개는 한 이벤트를 하나가 처리하는 경쟁 소비자이고, 다른 서비스가 같은 이벤트를 각자 받는 것은 팬아웃이다. 지금 소비자는 ai-engine 하나다.

**선택지.**

| 구조 | 순서를 지키는 방법 |
|---|---|
| 프로젝트별 큐(A) | 큐마다 단일 활성 소비자(SAC)를 켠다. 한 프로젝트의 흐름이 항상 한 인스턴스로만 간다. 브로커 내장 기능 |
| 표 직접 읽기(B) | 인스턴스가 "프로젝트 X는 내가 잡는다"는 lease를 걸고 순번대로 집는다 |
| 단일 큐(C2) | 두 인스턴스가 나눠 받으면 깨진다. 결국 프로젝트별 큐가 필요하다 |

**결론.** 지금은 단일 인스턴스라 당장의 문제는 아니다. 늘릴 때 A는 내장 기능으로, B는 직접 구현으로, C2는 큐 구조를 바꿔서 해결한다.

### 2-10. 구성요소와 운영

**무엇을 따졌나.** RabbitMQ를 계속 운영할 것인가. 큐가 프로젝트마다 생기면 선언·발견·수명을 어떻게 관리하는가. 브로커에 백로그가 쌓이면 어떻게 되는가. 표를 큐로 쓰면 Postgres의 완료 행 정리와 부풀기 관리가 운영 항목이 된다.

**선택지와 비용.**

| 구조 | 운영 항목 |
|---|---|
| A | RabbitMQ 유지. 프로젝트 큐의 선언(worker가 첫 발행 전에), 발견(ai-engine이 관리 API로 주기적으로 목록을 맞춤), 수명(유휴 만료로 자동 삭제). 백로그가 브로커에 diff째 쌓임 |
| B | RabbitMQ 불필요. Postgres가 수집의 핫패스가 되어 완료 행 정리와 autovacuum 조정이 필요. ai-engine에 드라이버·연결 풀·통합 테스트 환경 추가 |
| C2 | RabbitMQ 유지 + 결과 큐 + 릴레이 스케줄러. 표와 브로커를 함께 운영 |

**결론.** A의 큐 관리는 장치 하나(주기적 목록 맞춤)로 시작한다. 이벤트는 내구 큐에 안전하게 쌓이므로 발견이 늦어도 유실은 없고 지연만 있다.

### 2-11. 테스트 가능성

**무엇을 따졌나.** 새로 생기는 로직을 어디서 어떻게 검증하는가.

**결론.** A의 릴레이는 Spring 서비스 안에 놓여 기존 JUnit·TDD 흐름으로 검증한다. ai-engine 쪽 변경은 구독하는 큐의 모양뿐이다. B는 ai-engine에 Postgres를 띄우는 통합 테스트 환경을 새로 만들어야 한다.

### 2-12. 되돌리기

**무엇을 따졌나.** 고른 구조가 틀렸을 때 얼마나 쉽게 바꾸는가.

**결론.** 세 후보 모두 아웃박스 표를 공유한다. A에서 시작해 나중에 표를 직접 읽는 B로 가려면 ai-engine에 읽기 어댑터를 붙이면 되고, 반대도 마찬가지다. 표 설계를 어느 쪽으로도 갈 수 있게 해 두면 결정이 영구 고정이 아니다.

## 3. 후보 아키텍처

### 3-1. A. 아웃박스 + 펌프 릴레이 + 프로젝트별 큐

```
pipeline-worker
  수집기 ──▶ PostgreSQL: 아웃박스 표 (이벤트 N건, 페이지마다 한 트랜잭션. 커서는 지금 시점대로 따로)
  릴레이 ──▶ 아웃박스 행을 순서대로 전부 RabbitMQ로 옮기고 "보냈음" 표시

RabbitMQ
  history.events.<프로젝트 1>  ─┐
  history.events.<프로젝트 2>  ─┼─ 큐마다 한 건씩 번갈아 ──▶ ai-engine ──▶ Neo4j
  history.events.<프로젝트 N>  ─┘   (큐마다 단일 활성 소비자)
                                      재시도 큐 / DLQ / parking 큐는 지금 그대로
```

**흐름.**

1. 수집기는 페이지를 받을 때마다 이벤트 행들을 한 트랜잭션으로 저장한다. 커서는 지금처럼 따로 쓴다. 브로커와는 대화하지 않는다.
2. 릴레이가 주기적으로 아직 안 보낸 행을 읽어 해당 프로젝트 큐에 발행하고 "보냈음"으로 표시한다. 큐는 첫 발행 전에 선언한다.
3. ai-engine은 프로젝트 큐들을 구독하고, 브로커가 큐마다 한 건씩 번갈아 건네 준다. 처리와 그래프 쓰기는 지금과 같다.
4. ai-engine은 주기적으로 관리 API에서 큐 목록을 읽어 새 큐는 구독하고 사라진 큐는 정리한다.

**장점.**

- ai-engine이 Postgres에 닿지 않는다. 보안 비용과 표 계약이 생기지 않는다.
- 배달 보장을 직접 짜지 않는다. 재배달, 처리 시간 제한, 단일 활성 소비자, 재시도 큐, DLQ, parking 큐, 모니터링이 그대로다.
- 균등 공정성이 브로커의 기본 동작으로 나온다.
- 변경 폭이 가장 작다. pipeline-worker에 표와 릴레이가 생기고, ai-engine은 구독 방식만 바뀐다. 소비 로직은 그대로다.

**단점.**

- 프로젝트 큐의 선언·발견·수명을 관리해야 한다.
- 백로그가 브로커에 diff째 쌓인다. 커지면 diff를 메시지 밖으로 빼는 추가 작업이 필요하다.
- 멈춘 프로젝트를 진단할 때 표와 브로커를 함께 봐야 한다.
- 가중치 정책을 넣으려면 브로커가 아니라 ai-engine의 슬롯 배분에서 해야 한다. 브로커에는 가중 라운드로빈이 없다.

### 3-2. B. ai-engine이 표를 직접 읽기

```
pipeline-worker
  수집기 ──▶ PostgreSQL (ingest 논리 DB): 작업 표 (이벤트 + 커서, 한 트랜잭션)
                                             ▲
                                             │ 프로젝트 lease를 잡고 순번대로 집기 (SKIP LOCKED)
                                             │ 처리 중 lease 연장, 끝나면 status 갱신
                                         ai-engine ──▶ Neo4j

RabbitMQ 없음
```

**흐름.**

1. 수집기는 A와 같이 표에 쓴다.
2. ai-engine이 표에서 "다음에 처리할 프로젝트"를 라운드로빈으로 고르고, 그 프로젝트에 lease를 걸고 이벤트를 순번대로 집는다. 다른 인스턴스는 lease가 걸린 프로젝트를 건너뛴다.
3. 처리 중에는 주기적으로 lease를 연장하고, 끝나면 행을 완료로 바꾼다. 연장이 끊겨 만료된 행은 다시 집기 대상이 된다.
4. 실패는 행의 시도 횟수와 마지막 오류에 남고, 횟수를 넘기면 실패로 표시한다.

**장점.**

- 조정 루프가 하나다. 집기, 처리, 갱신.
- 진단이 표 한 곳에서 끝난다. 상태, lease, 시도 횟수, 마지막 오류가 같은 행에 있다.
- 인스턴스를 늘릴 때 프로젝트 lease 하나로 순서가 지켜진다.
- 큐 관리가 없고 RabbitMQ가 필요 없다.
- 정책을 처리 직전에, 부하를 아는 쪽에서 자유롭게 정할 수 있다.

**단점.**

- ai-engine이 Java 서비스 소유 DB의 자격증명을 갖는다. 침해 시 전 테넌트 payload를 보관 기간 내내 읽을 수 있는 범위가 된다.
- 경계를 지키려면 조건이 다섯 개 필요하다. 전용 논리 DB, 역할 권한, 컬럼 추가만 허용, 계약 테스트, 포트/어댑터 격리.
- lease, 연장, 만료 정리를 직접 구현한다.
- ai-engine에 Postgres 통합 테스트 환경을 새로 만든다.
- 수집 부하가 사용자 DB와 같은 Postgres 인스턴스를 탄다.

### 3-3. C2. 표가 정본, 릴레이가 스케줄러, 브로커는 전달

```
pipeline-worker
  수집기 ──▶ 아웃박스 표 (이벤트 + 커서, 한 트랜잭션)
  릴레이 ──▶ 프로젝트마다 "처리 중" 건수가 8건 이하가 되도록 골라 작업 큐에 넣음
  결과 소비자 ◀── 결과 큐에서 완료/실패를 받아 표의 status를 바꾸고 창을 보충

RabbitMQ
  작업 큐 (1개) ──▶ ai-engine ──▶ Neo4j
  결과 큐       ◀── ai-engine (처리 완료 / 최종 실패)
```

**흐름.**

1. 수집기는 A와 같이 표에 쓴다.
2. 릴레이는 백로그를 표에 두고, 프로젝트마다 몇 건씩만 작업 큐에 넣는다. 큐 하나 안에서 프로젝트가 섞이므로 공정해진다.
3. ai-engine은 작업 큐를 소비하고, 처리가 끝나면 결과 큐에 완료나 실패를 발행한 뒤 입력을 확인(ack)한다.
4. pipeline-worker가 결과 큐를 소비해 행을 완료나 실패로 바꾸고, 그만큼 다음 건을 넣는다.

**장점.**

- ai-engine은 Postgres에 닿지 않으면서 표가 완료까지 안다. 진행률과 실패 이력이 표 한 곳에 모인다.
- 큐 하나로 공정성을 얻고, 가중치를 창 크기나 보충 빈도에 곱하면 되어 정책 확장이 자연스럽다.
- 브로커 안의 diff 총량이 "창 × 활성 프로젝트 수"로 묶인다.
- 배달 보장은 브로커가 맡는다. 결과를 큐로 돌리므로 HTTP 콜백 재시도나 heartbeat가 필요 없다.

**단점.**

- 이벤트가 세 번 자리를 옮기고, 표와 브로커 두 시스템이 같은 사실을 따로 들고 있어 어긋날 수 있다.
- 릴레이가 작은 스케줄러가 된다. 창 관리, 보충, 재발행 판단이 붙는다.
- pipeline-worker에 결과 큐 소비자가 추가된다.
- 인스턴스를 늘리면 단일 큐로는 순서가 깨져 결국 프로젝트별 큐가 필요하다.
- 진행률을 전제에서 빼면 가장 큰 이점이 사라진다.

### 3-4. 함께 검토했다가 접은 변형

- **아웃박스 없이 서비스별 DB만 분리한 A.** 이중 쓰기가 그대로 남아 제외.
- **완료를 HTTP 콜백으로 돌려주는 C.** ai-engine에는 실패한 콜백을 보관할 저장소가 없고, 릴레이가 "느린지 죽었는지"를 알 수 없어 heartbeat까지 필요해진다. 결과 큐 방식(C2)으로 대체.
- **A에 결과 큐를 더한 것.** 진행률을 빼면 결과 큐의 용도가 사라져 A로 수렴.

## 5. 결정과 이유

### 5-1. A를 고른 이유

전제(균등 공정, 진행률 없음, 요금제 정책 없음) 아래에서 A가 다른 둘보다 나은 점은 다음 넷이다.

1. **경계를 지킨다.** ai-engine이 Postgres에 닿지 않으므로 자격증명 확대, 표 계약 다섯 개, 경계 침식 걱정이 처음부터 생기지 않는다. 가장 오래 따진 주제가 통째로 사라진다.
2. **배달 보장을 직접 짜지 않는다.** lease, 연장, 만료 정리 대신 브로커의 재배달과 처리 시간 제한, 단일 활성 소비자를 쓴다. 지금 있는 재시도 큐, DLQ, parking 큐, 모니터링이 그대로 살아 있다.
3. **균등 공정성이 기본 동작으로 나온다.** 큐를 프로젝트별로 나누면 끝이다. 스케줄러를 짤 필요가 없다.
4. **변경 폭이 가장 작아 리스크가 가장 작다.** pipeline-worker에 아웃박스 표와 릴레이가 생기고, ai-engine은 구독하는 큐의 모양만 바뀐다. 릴레이는 Spring 쪽이라 기존 TDD 흐름으로 검증한다.

B의 장점인 "진단 한 곳", "큐 관리 없음", "브로커 백로그 없음"은 자격증명 확대와 lease 자체 구현보다 가볍다고 판단했다. C2의 핵심 장점은 진행률이었는데 전제에서 빠졌다.

### 5-2. 받아들이는 비용

- 프로젝트 큐의 선언은 pipeline-worker가, 발견은 ai-engine이 관리 API 목록을 주기적으로 맞추는 방식으로 한다. 발견이 늦어도 이벤트는 내구 큐에 안전하게 남아 있다.
- 백로그가 브로커에 diff째 쌓인다. 지금 규모에서는 문제가 없고, 커지면 diff를 메시지 밖에 두는 방식을 붙인다.
- 멈춘 프로젝트를 진단할 때 표의 "보냈음"과 브로커의 큐 상태를 함께 본다.
- 아웃박스 행은 발행 뒤 며칠 보관한 뒤 지운다. 기간은 계획 때 정한다.

### 5-3. 다시 꺼낼 조건

- **B로 뒤집히는 경우.** 운영 진단을 한 곳에서 하는 것이 중요해지거나, RabbitMQ를 운영 항목에서 빼기로 하거나, 균등이 아닌 복잡한 정책을 처리 직전 부하에 따라 정해야 할 때.
- **C2로 뒤집히는 경우.** 진행률이나 실패 이력을 표 한 곳에서 보여 줘야 하는데 ai-engine은 여전히 Postgres에 닿지 않아야 할 때.

### 5-4. 이번 범위 밖

- 수집 실패를 사용자에게 보여 주는 기능. 별도 작업.
- pipeline-worker와 backend 사이의 기존 DB 공유 정리(연동 표 직접 읽기, 커서 표 읽기·삭제를 HTTP로 바꾸고 논리 DB를 나누는 것). 별도 작업.
- diff를 메시지 밖에 두는 것. 백로그가 실제로 커질 때.
- ai-engine 다중 인스턴스. 필요해질 때 단일 활성 소비자를 켠다.
- 커서를 아웃박스 트랜잭션에 넣는 것(이벤트 N건 + 커서, 한 트랜잭션). 커넥터별 커서 시점의 재설계가 선행돼야 해서, 아웃박스와 프로젝트별 큐가 끝난 뒤 조사해 별도 작업으로 다룬다.

## 6. 용어

| 용어 | 뜻 |
|---|---|
| 이중 쓰기 | 한 작업의 결과를 서로 다른 두 저장소에 따로 쓰는 것. 한쪽만 성공할 수 있다 |
| 트랜잭셔널 아웃박스 | 큐에 넣을 내용을 브로커가 아니라 자기 DB의 표에, 본 작업과 같은 트랜잭션으로 쓰는 방식 |
| 릴레이 | 아웃박스 표의 행을 읽어 브로커로 옮기는 구성요소. 표를 주기적으로 읽는 방식을 Polling Publisher라고 부른다 |
| 펌프 / 밸브 | 이 문서에서 쓴 비유. 펌프는 행을 순서대로 전부 옮기는 릴레이(A), 밸브는 정책대로 골라 조금씩 넣고 완료를 보고 보충하는 릴레이(C2) |
| 단일 활성 소비자(SAC) | 큐 하나에 소비자가 여럿 붙어도 한 번에 하나만 활성으로 두는 RabbitMQ 기능. 활성 소비자가 죽으면 다음으로 넘긴다 |
| prefetch | 소비자가 확인(ack)하기 전에 미리 받아 둘 수 있는 메시지 수 |
| consumer timeout | 받은 메시지를 이 시간 안에 확인하지 않으면 브로커가 연결을 끊고 메시지를 되돌리는 제한 |
| lease | 행에 "누가, 언제까지 잡았다"를 적어 두는 만료 있는 점유. 처리 중 연장하고, 만료되면 남이 가져간다 |
| SKIP LOCKED | 여러 소비자가 같은 표에서 행을 집을 때 남이 잠근 행은 건너뛰게 하는 Postgres 기능 |
| 멱등 처리 | 같은 이벤트를 두 번 받아도 결과가 한 번 받은 것과 같게 처리하는 것. 지금 ai-engine의 그래프 쓰기가 이렇다 |
| Claim Check | 큰 본문을 메시지에 싣지 않고 별도 저장소에 두고 참조만 싣는 패턴 |
| 경쟁 소비자 / 팬아웃 | 경쟁 소비자는 같은 서비스의 인스턴스 여럿이 한 이벤트를 하나만 처리하는 것. 팬아웃은 서로 다른 소비 서비스가 같은 이벤트를 각자 받는 것 |
