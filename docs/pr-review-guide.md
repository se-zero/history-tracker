# PR 리뷰 가이드

> PR을 올리고 → 리뷰를 기다리고 → 수정하는 구간이 우리 팀의 가장 큰 병목이었다.
> 그 대기 시간을 줄이려고 **리뷰 봇**을 넣었고, 그에 맞춰 사람이 하는 일도 다시 나눴다.
> 이 문서는 그 흐름을 정리한 것이다.

## 한 줄 요약

**봇이 먼저 훑고, 사람은 봇이 볼 수 없는 것만 본다.**

버그·보안·계약 불일치처럼 코드를 읽으면 알 수 있는 것은 봇이 잡는다.
"이걸 지금 하는 게 맞나", "되돌릴 수 있나"처럼 코드에 답이 없는 것은 사람이 본다.

---

## 1. 전체 흐름

```
작성자                          봇                        리뷰어
  │
  ├─ 로컬에서 자가 점검
  │
  ├─ PR 오픈 ──────────────▶ 자동 리뷰
  │  (리뷰어 지정 안 함)          │
  │◀──── 🟠 수정 필요 ───────────┘
  │
  ├─ 수정 후 push ─────────▶ 재리뷰
  │                              │
  │◀──── 🟢 머지 가능 ───────────┘
  │
  ├─ 리뷰어 지정 ─────────────────────────────────▶ 검토
  │                                                   │
  │◀───────────────── 승인 ────────────────────────────┘
  │
  ├─ 머지
  └─ 실제로 돌려보고 확인
```

**핵심은 리뷰어를 나중에 지정한다는 점이다.**
작성자와 봇이 주고받는 동안 리뷰어 칸이 비어 있어서, 리뷰어에게는 **알림이 가지 않는다.**
정리가 끝난 PR만 받아보게 되므로, "고치는 중인 PR"을 여러 번 다시 열어볼 일이 없다.

| 단계 | 누가 | 무엇을 |
|---|---|---|
| 1 | 작성자 | 로컬 자가 점검 → PR 본문 작성 → **리뷰어 없이** PR 오픈 |
| 2 | 봇 | 자동 리뷰. 판정과 지적을 코멘트로 남김 |
| 3 | 작성자 | 지적 반영 후 push → 봇이 다시 판정 (🟢 나올 때까지 반복) |
| 4 | 작성자 | 본문 최신화 후 **리뷰어 지정** |
| 5 | 리뷰어 | 검토 → **승인** |
| 6 | 작성자 | **머지** → 실제로 돌려보고 확인 |

> **승인은 리뷰어, 머지는 작성자.** 머지를 작성자가 하는 이유는 **문제가 생겼을 때 되돌릴 사람이 작성자**이기 때문이다. 남이 머지하면 책임이 애매해진다.

---

## 2. 봇이 하는 일

PR을 열거나 새 커밋을 올릴 때마다 자동으로 돈다. Draft에서는 돌지 않는다.

### 보는 것 — 네 가지

| | 무엇을 보나 |
|---|---|
| **동작 정확성** | 의도대로 동작하는가. 빠진 예외 처리, 경계값, 널 처리 |
| **보안·개인정보** | 토큰이 로그에 찍히는가, 권한 검사가 빠졌는가, 남의 데이터를 볼 수 있는가 |
| **서비스 간 정합성** | 한쪽을 고쳤는데 반대편이 그대로인가 (수집기 ↔ 그래프 엔진, 백엔드 ↔ 프론트, DB 스키마 ↔ 코드) |
| **본문 대비 실제 동작** | PR 본문에 적은 것과 실제 변경이 일치하는가 |

세 번째가 봇을 넣은 가장 큰 이유다. 우리 서비스는 넷으로 나뉘어 있어서
한 곳을 고치면 다른 곳도 같이 고쳐야 하는데, **그 반대편은 보통 diff에 없어서 눈에 안 띈다.**

### 보지 않는 것

**더 간결하게 쓸 수 있다 / 이름을 바꾸자 / 중복을 합치자** — 이런 지적은 하지 않는다.

이미 커밋된 코드에 그런 지적을 달면 반영하는 데 커밋이 하나 더 붙고, 그만큼 머지가 늦어진다.
이 영역은 **작성자가 커밋 전 로컬 점검에서 끝내는 것**이 우리 규칙이다.

### 하지 않는 일

봇은 **승인하지 않고, 머지하지 않고, 코드를 고치지 않는다.** 지적만 남긴다.

---

## 3. 판정 읽는 법

봇은 각 지적에 등급을 매기고, 그걸로 **전체 판정을 기계적으로** 낸다.

| 등급 | 뜻 | 판단 기준 |
|---|---|---|
| 🔴 **Critical** | 머지 금지 | 지금 배포되면 사용자나 데이터에 피해가 간다 |
| 🟠 **Major** | 머지 전 수정 | 코드가 의도대로 동작하지 않는다 |
| 🟡 **Minor** | 이번에 고치면 좋음 | 동작은 맞다 |
| 💡 **Note** | 안 고쳐도 됨 | 취향의 영역 |

```
Critical 있음  → 🔴 머지 금지
Major 있음     → 🟠 수정 필요
나머지         → 🟢 머지 가능
```

### 코멘트가 달리는 위치

- **머지를 막는 지적(🔴🟠)** 은 해당 코드 줄에 직접 달린다
- **종합 판정과 나머지 지적**은 PR에 코멘트 하나로 달리고, push할 때마다 **그 코멘트가 갱신**된다
  (새 코멘트가 쌓이지 않으므로 항상 맨 아래 것만 보면 된다)
- **바뀐 파일이 아닌 곳을 지적할 때**는 코드 줄에 달 수 없어서 종합 코멘트 본문에 파일 경로와 함께 적힌다

> **🟢은 승인이 아니다.** "이제 사람을 불러도 된다"는 신호일 뿐이다.

---

## 4. 리뷰어가 하는 일

> **코드를 리뷰하는 게 아니라, 작성자의 판단을 리뷰한다.**

코드는 이미 세 번 읽혔다 — 작성자가 커밋 전에, 작성자가 PR 직전에, 봇이 PR에서.
리뷰어가 새로 볼 수 있는 것은 **그 과정에서 작성자가 내린 판단**뿐이다.

### 봇이 원리적으로 답할 수 없는 네 가지

| 사람이 답할 것 | 왜 봇은 못 하나 |
|---|---|
| **의도가 옳은가** | 본문이 "X를 한다"고 하고 코드가 X를 하면 봇은 통과시킨다. **본문 자체가 틀려도 통과한다** |
| **빠진 것이 있는가** | 봇은 바뀐 코드를 본다. **안 쓴 코드는 볼 수가 없다** (연동 해제 처리 누락, 삭제 규칙 누락 등) |
| **되돌릴 수 있는가** | 스키마가 맞는지는 봐도, "데이터가 10만 건 쌓인 뒤에 이걸 바꿔야 하면?"은 못 본다 |
| **실제로 돌아가는가** | 리뷰는 코드를 읽지 **실행하지 않는다** |

### 어디를 볼지 — 두 갈래

PR 본문의 **`확인 필요`** 칸을 먼저 본다. 여기 체크가 하나라도 있으면 **게이트**, 없으면 **패스**다.

| | 조건 | 리뷰어가 할 일 | 대략 |
|---|---|---|---|
| **게이트** | DB 마이그레이션 / 서비스 간 계약 / 그래프 스키마 / 외부 연동 정책 중 하나라도 해당 | 배경 + **해당 파일만** 열어보기 + 실제로 돌려봤는지 확인 | 15~30분 |
| **패스** | 그 외 전부 | 배경 + 봇 판정 + 화면 캡처·시나리오 | 3분 |

> **패스에서 diff를 열지 않는 것은 대충 보는 게 아니라 규칙이다.**
> 명시해두지 않으면 결국 매번 전부 열어보게 되고, 그게 다시 병목이 된다.
>
> 게이트가 여러 개 체크되는 건 정상이다. 새 연동을 추가하면 마이그레이션·계약·정책이 같이 움직인다.
> 개수는 "쪼개라"는 신호가 아니라 **시간 예산**으로 읽는다.

### 게이트일 때 읽는 순서

| | 무엇을 | 왜 |
|---|---|---|
| ① | **배경** | 봇 판정을 먼저 보면 "잘 고쳤나" 확인하는 사람이 되어버린다 |
| ② | 변경 파일 목록 ↔ `확인 필요` 대조 | **어긋나면 그게 질문거리다** |
| ③ | **DB 마이그레이션 정독** | 이 PR에서 유일하게 되돌리기 어려운 것 |
| ④ | 계약 변경과 그 반대편 | 한쪽만 고치고 만 것은 없는지 |
| ⑤ | 테스트 설정 | **테스트 삭제·스킵이 조용히 섞이는 게 흔한 패턴이다** |
| ⑥ | `검증` 칸 | "수동: 미완"이면 멈추고 묻는다 |
| ⑦ | 봇 종합 코멘트 | **마지막에.** 접힌 Minor 중 게이트에 걸치는 게 있나 |
| ⑧ | `범위 밖` | 빠진 것을 확인할 수 있는 유일한 칸 |

### 승인 전 세 문장

셋 다 "예"면 승인, 하나라도 아니면 질문한다.

1. 이 방향이 맞다고 **나도** 생각하나?
2. 이 PR에서 **되돌릴 수 없는 게 뭔지 말할 수 있나?**
3. 작성자가 실제로 돌려봤다는 것을 확인했나?

> 2번에서 **"없다"는 정답**이다(패스 티어). **"모르겠다"가 아직 승인할 상태가 아니라는 뜻**이다.

### 하지 않아도 되는 것

버그 찾기(봇의 몫) · 더 간결하게 쓰라는 지적(이미 끝난 단계) · 패스 티어에서 diff 열기 ·
💡 Note 확인 · 테스트 코드 정독

### 흔한 함정 셋

- **봇 코멘트를 먼저 읽는다** → "잘 고쳤나" 확인자가 되고, "이걸 하는 게 맞나"라는 시선이 사라진다. 봇 코멘트는 **마지막에**
- **`배경`을 그대로 믿는다** → 변경 요약처럼 읽히면 사람이 쓴 게 아니다. 그때는 승인하지 말고 **"이거 왜 해?"를 직접 묻는다**
- **크면 훑고 넘어간다** → 훑고 승인하는 건 승인 안 하는 것보다 나쁘다. 봤다는 기록만 남는다

## 5. PR 본문 칸 설명

칸마다 읽는 사람과 쓰임이 정해져 있다.

| 칸 | 누가 읽나 | 쓰임 |
|---|---|---|
| **배경** | 리뷰어가 제일 먼저 | 이걸 지금 하는 게 맞는지 판단 |
| **주요작업 · 시나리오** | 봇 + 리뷰어 | 봇이 "말한 것과 실제가 같은가"를 검증하는 입력 |
| **확인 필요** | 리뷰어 | 게이트/패스 판정 |
| **검증** | 리뷰어 | 실제로 돌려봤는지. 안 했으면 "미완"이라고 그대로 적는다 |
| **범위 밖** | 리뷰어 | 일부러 안 한 것. 빠진 것을 확인할 유일한 입구 |

`배경` · `범위 밖` · 수동 검증 결과는 **작성자가 직접 쓴다.**
변경 내용에서 자동으로 뽑아낸 글로 그 변경을 검증하면 동어반복이 되어, 봇 검증이 항상 통과하고
리뷰어가 배경을 읽어도 물을 것이 없어지기 때문이다.

## 6. 자주 생기는 상황

| 상황 | 어떻게 |
|---|---|
| 봇이 🟢인데 승인해도 되나? | 🟢은 "사람을 불러도 된다"는 뜻이다. 승인 전 세 문장으로 따로 판단한다 |
| 봇 지적이 틀린 것 같다 | 작성자가 **혼자 무시하지 않고 반박 답글**을 단다. 기각은 작성자의 제안이고, 리뷰어의 승인이 동의다 |
| 봇이 못 잡은 걸 리뷰어가 잡았다 | **가장 값진 경우다.** 봇이 볼 차원을 늘릴 근거가 되므로 꼭 남긴다 |
| PR이 너무 크다 | 기준은 크기가 아니라 **`배경`에 적힌 목적의 개수**다. 목적이 하나면 커도 한 PR, "겸사겸사"가 섞였으면 작아도 나눈다 |
| 되돌릴 게 여러 개다 | 리뷰어가 **"문제 생기면 무엇을 어떤 순서로 되돌리나"** 를 묻는다. 머지하면 롤백 단위가 하나로 묶이기 때문이다 |
| Draft로 열고 싶다 | 가능하다. 봇은 Draft에서 돌지 않고, **Ready로 바꾸는 순간 시작**된다 |

## 7. 작성자를 위한 로컬 도구 (선택)

Claude Code를 쓰면 레포에 포함된 도구를 그대로 쓸 수 있다. 안 써도 흐름에는 지장 없다.

| 도구 | 언제 | 무엇을 |
|---|---|---|
| `branch-review` | 커밋 전 / PR 직전 | 커밋 전에는 넓게, PR 직전에는 **봇과 같은 기준으로** 미리 점검 |
| `pr-description` | PR 열기 전 | `확인 필요` 자동 체크 + 본문 초안. 사람만 답할 수 있는 것은 물어본다 |

PR 직전 점검을 봇과 같은 기준으로 돌리는 이유는, **PR에 올린 뒤에야 🟠을 받는 왕복을 줄이기 위해서**다.

---

## 8. 아직 정하지 않은 것

- 봇이 놓친 것과 리뷰어가 놓친 것을 어디에 기록할지
- 봇의 리뷰 깊이를 얼마나 줄지 (지금은 기본값)

봇을 넣은 목적이 **대기 시간 단축**이므로, 실제로 줄었는지 몇 주 써보고 조정한다.
이 문서의 규칙도 그때 함께 손본다.
