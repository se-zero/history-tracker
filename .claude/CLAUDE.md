# 로컬 작업 규칙 (팀 공유 전 개인 검증 중)

## 항상 지키는 것

- **결정은 사용자에게 묻는다.** 판단만으로 정할 수 없는 것(리뷰 지적의 반영 여부, 설계 선택지,
  범위 변경)은 임의로 정하거나 서브에이전트에 지시하지 말고 먼저 사용자에게 묻는다.
  물을 때는 선택지 UI(AskUserQuestion)가 아니라 **채팅에 선택지·근거·추천을 펼쳐 놓고 기다린다.**
- **질문에는 채팅 답변이 먼저다.** 플랜 모드 중이든 계획 직후든, 사용자 발화가 질문이면
  계획서·선택지 UI로 대신하지 않는다. 채팅으로 답하고, 끝난 뒤에 계획으로 돌아간다.
- **설명은 배경지식을 가정하지 않는다.** 기술 용어는 먼저 풀어 쓰고, 구체적인 예시를 들어 설명한다.
- **커밋은 사용자가 한다.** 작업이 완전히 끝나도 커밋하지 않는다. 사용자가 코드를 읽고 결정한다.

기능 단위 작업의 진행 방식(계획 → 위임 → 리뷰)은 `feature-cycle` 스킬을 따른다.

## TDD 규칙 (Spring 서비스 공통)

기존 파일에 새 메서드를 추가할 때도 반드시 TDD 순서를 지킨다.

1. **테스트 케이스 먼저**: 기존 `*Test.java`에 새 메서드에 대한 테스트를 먼저 추가한다.
   테스트 파일이 없는 신규 클래스라면 테스트 파일부터 만든다.
2. **실패 확인**: `./gradlew test --tests "...Test"` 로 빨간 상태(컴파일 에러 또는 실패)를 확인한다.
3. **구현**: 테스트를 통과시키는 최소한의 프로덕션 코드를 작성한다.
4. **통과 확인**: PostToolUse 훅이 자동으로 테스트를 실행하고, 통과하면 서비스 전체 테스트도 실행한다.

테스트가 불필요한 변경(DTO 필드 추가, 설정 클래스, `config/` 패키지 등)은 이 순서를 생략할 수 있다.
