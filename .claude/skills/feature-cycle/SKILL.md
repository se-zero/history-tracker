# Feature Cycle 스킬

기능 단위 작업을 **계획 → 단계별 위임 → 리뷰 → 반영**으로 진행한다.
오케스트레이터(너)는 **직접 구현하지 않는다.** 계획을 세우고, 위임하고, 리뷰하고, 사용자에게 묻는다.

## 적용 범위

**적용한다**: 여러 파일·여러 계층에 걸친 기능, 기존 흐름 전환, 새 서비스 연동.

**적용하지 않는다**: 한 파일 수정, 오타·문구 수정, 문서 편집, 설정값 변경, 사용자가 직접 지시한
단순 명령. 이런 작업에 계획서부터 쓰면 비용만 늘어난다 — 그냥 하고 결과를 보고한다.

**2단계 위임(테스트↔구현 분리)은 Java 서비스 코드에만 적용한다.** ai-engine은 pytest는 있지만
`spring-test-writer`가 Spring 전용이라 해당 없고, web-dashboard는 테스트 러너 자체가 없어
(`npm run typecheck && npm run build`가 기준선) 성립하지 않는다.

---

## 1단계 — 계획 (플랜 모드에서)

**가장 먼저 `EnterPlanMode`를 호출한다.** 코드를 읽기 전에 부른다.

플랜 모드에서는 편집이 차단되고 계획 파일만 쓸 수 있다. 승인 전에 손대는 일이 원천적으로
불가능해지는 것이 목적이다 — "계획을 확실히 세우고 나서 위임한다"를 규율이 아니라 상태로 만든다.

탐색은 플랜 모드가 지시하는 절차(Explore 서브에이전트)를 따르고, 계획서는 **계획 파일에** 쓴다.
채팅에 요약본을 따로 늘어놓지 않는다.

계획서에 반드시 담을 것:

- 각 phase마다 **기술 상세 앞에 "무엇을 / 왜 / 어떻게"를 자연어로** 먼저 쓴다.
  낯선 용어는 질문받기 전에 설명한다.
- 각 단계에 **성공 기준**을 붙인다 ("작동하게 만들어"가 아니라 "이 테스트가 통과하면 끝").
- 각 단계가 **어느 에이전트에 어떤 단위로 위임될지**가 드러나게 쪼갠다.
- 세부 단계를 **리뷰 응집도 기준으로 묶음(체크포인트)으로 묶은 표**를 계획서에 넣는다 —
  실행·리뷰·커밋은 묶음 단위로 돈다. 묶음이 곧 위임 1회분(TDD면 test-writer+implementer 한 쌍)
  이다. 기준: 같은 묶음 = 한 diff로 읽었을 때 목적이 하나로 설명되는 범위. 공용 코드 수정
  (안전장치류)은 묶음 안에서도 커밋 분리 대상으로 표시한다. 묶음별로 **병렬 실행 가능 여부**
  (서비스 디렉터리 비겹침)와 순서 제약(의존성)을 표에 함께 적는다.
  (근거: 13단계를 단계별 사이클로 돌면 에이전트 기동·전체 테스트·리뷰가 13번 반복된다 —
  Linear 커넥터에서 7묶음으로 줄여 위임 11회·리뷰 6회로 완료.)
- **하지 않는 것**을 명시한다. 범위 밖으로 판단한 항목과 그 이유를 남겨야 나중에 다시 논쟁하지 않는다.
- 사실관계가 불확실하면(외부 API 정책, 만료 기간 등) **추측해서 쓰지 말고 확인한 뒤 근거를 함께 남긴다.**

결정이 필요한 갈림길이 있으면 **채팅에서 선택지·근거·추천을 펼쳐 묻고 답을 기다린다**
(`AskUserQuestion` UI는 쓰지 않는다 — 사용자는 근거를 읽고 채팅으로 답하는 방식을 선호한다).
계획이 확정되면 **`ExitPlanMode`로 승인을 받는다.** 승인 전에 위임하지 않는다.

> 설명을 먼저 요구받으면 계획서나 선택지 UI로 답하지 말고 **채팅으로 직접 설명한다.**
> 설명이 끝난 뒤에 계획으로 돌아간다.

## 2단계 — 묶음 단위 위임 + 병렬 실행

계획의 묶음 단위로 위임한다. TDD도 묶음 단위 배치다 — test-writer가 묶음 전체의 테스트를
한 번에 쓰고(red), implementer가 한 번에 통과시킨다(green). 묶음보다 잘게 쪼개 위임하면
기동·테스트·리뷰 오버헤드만 늘어난다.

**병렬 실행 원칙 — "파일이 안 겹치면 동시에":**

- 서비스 디렉터리가 다른 묶음(backend ∥ pipeline-worker ∥ ai-engine ∥ web-dashboard ∥ 문서)은
  **동시에 위임한다.** gradle 빌드 디렉터리도 서비스별로 분리라 충돌하지 않는다.
- 단, **순서 제약이 병렬보다 우선한다.** 예: 소비자 측 격리는 첫 실수집 전에, 문서는 그 내용의
  계약이 확정된 뒤에, 공용 가드는 그것을 밟을 코드보다 먼저.
- 같은 서비스 안의 묶음은 순차로 — 파일·훅(전체 테스트 자동 실행)이 겹친다.
- 병렬 중 턴 종료 훅의 전체 테스트가 실패하면, **코드 리그레션인지 동시 gradle 충돌
  (`in-progress-results-*.bin` 오류)이나 의도된 red 상태인지 먼저 판별한다** — 진행 중인
  에이전트와 겹치는 재실행은 같은 충돌만 재발시킨다.
- 에이전트가 무진행으로 죽으면(스톨) 새로 띄우지 말고 **SendMessage로 같은 컨텍스트를 재개**한다.

**오케스트레이터가 위임하지 않고 직접 하는 것**: 계획·프롬프트, 리뷰, 리뷰 반영 중 소규모
수정(위임 오버헤드가 수정보다 큰 것), 그리고 **미확정 외부 사실의 검증** — 정렬 방향·필드
존재 여부 같은 외부 API 사실은 위임 전에 공식 문서·스키마 원본으로 확정해 프롬프트에 박는다.
에이전트에게 "검증하라"고 시키면 추측 매핑이 섞인다.

### Java 서비스 코드 (backend, pipeline-worker)

```
① spring-test-writer 에 테스트 위임
② red 확인  (./gradlew test --tests "...Test")
③ implementer 에 구현 위임
④ green 확인
```

**①의 지시에 반드시 포함할 것**: "이 테스트가 **의도한 결함이 있을 때 실제로 실패하는지** 확인하라.
구현이 잘못돼도 통과하는 테스트는 없느니만 못하다."

> 이 문장이 필요한 이유: 과거에 트랜잭션 전파를 검증하려던 가짜 매니저가 `isExistingTransaction()`을
> 구현하지 않아 `REQUIRED`와 `REQUIRES_NEW`에서 같은 결과를 내, 잡으려던 결함을 구분하지 못했다.

**③에서 `implementer`가 "테스트가 없어 막혔다"고 보고하면** 우회시키지 말고 ①로 돌아간다.
`enforce-tdd.sh` 훅이 그 지점에서 차단하도록 되어 있다.

**`implementer`가 "테스트가 틀린 것 같다"고 보고하면** 그 판단을 서브에이전트에 맡기지 말고
직접 확인한 뒤, 테스트를 고칠지 사용자에게 묻는다.

### 그 외 (ai-engine, web-dashboard, 설정·인프라)

`implementer` 에 한 단계씩 위임한다. 검증은 해당 서비스의 기준선 명령으로 한다.

### 위임 프롬프트에 매번 넣지 않아도 되는 것

`.env` 금지, 토큰 원문 로그 금지, 한국어 주석, 커밋 금지, 외과적 변경은
`agents/implementer.md`에 이미 있다. **작업 고유의 맥락만 전달한다.**

## 3단계 — 리뷰

묶음이 끝날 때마다 `branch-review` 스킬로 미커밋 작업 트리를 리뷰한다.

- **병렬 진행 중에는 리뷰 범위를 그 묶음의 파일(서비스 디렉터리)로 한정한다** — 작업 트리에
  다른 묶음의 미완성 변경이 섞여 있다. 리뷰 두 개가 비슷하게 끝나면 하나씩 순서대로 제시한다.
- 리뷰 지적은 등급(🔴 Critical / 🟠 Major / 🟡 Minor / 💡 Note)을 매기고,
  **반영/디퍼/현행 유지 추천을 붙인 표**로 모아 사용자에게 한 번에 묻는다.
- **표로 제시하기 직전에 `.claude/review-severity.md` 기준으로 전 항목의 등급을 한 번 재확인한다.**
  리뷰를 여러 묶음·여러 회차로 돌리면 각자 자기가 찾은 것 중 제일 큰 걸 Critical로 올려,
  합치면 Critical 5건인데 진짜 Critical은 0건이 되기 쉽다. **보정은 여기서 한 번만** 한다.

- 서브에이전트가 **계획에서 의도적으로 벗어났다고 보고하면, 그 부분을 특히 깊이 검증한다.**
  벗어난 판단이 맞는 경우가 실제로 있다 — 계획이 틀렸을 수 있다.
- 리뷰 결과 중 반영이 필요한 항목을 같은 서브에이전트에 수정 지시한다.
- **반영하지 않기로 한 항목은 `docs/oauth-integration-known-issues.md` 같은 문서에 남긴다.**
  "기록해뒀다"고 말만 하고 실제로 안 남기지 않는다.

## 4단계 — 결정은 사용자에게

**내 판단만으로 정할 수 없는 것은 서브에이전트에 지시하지 않고 먼저 사용자에게 묻는다.**
리뷰 지적의 반영 여부, 설계 선택지, 범위 변경, 트레이드오프가 있는 모든 갈림길이 해당한다.
사용자가 결정하면 그때 위임한다.

묻기 전에 설명을 요구받으면 1단계의 규칙(채팅으로 직접 설명)이 여기서도 그대로 적용된다.

## 5단계 — 커밋하지 않는다

작업이 완전히 끝나도 커밋하지 않는다. 사용자가 코드를 읽고 직접 결정한다.
`git commit`은 확인 대상으로 걸려 있다(`settings.json`의 `permissions.ask`).
