# Branch Review 스킬

현재 브랜치의 작업 내용을 한국어로 상세 리뷰한다. **작업 트리 상태에 따라 두 모드로 갈린다.**

| 모드 | 트리거 | 보는 차원 | 목적 |
|---|---|---|---|
| **단계 리뷰** (주 용도) | 미커밋 작업 트리가 있을 때 | **9영역 전부** (단순화·재사용성·데드코드 포함) | "뭘 더 고칠까?" |
| **전체 브랜치 리뷰** | 작업 트리가 깨끗할 때 (`develop...HEAD`) | **PR 봇과 동일한 4차원** | "올려도 되나?" — 봇 예행연습 |

> **왜 모드마다 차원이 다른가**
> 단순화·재사용성·스타일·네이밍은 **로컬에서 전부 소진하는 것이 정책**이다. 이미 커밋·푸시된
> 코드에 "3줄로 줄일 수 있어요"를 다는 건 소음이고, 반영하려면 커밋이 하나 더 붙는다.
> 그래서 단계 리뷰가 그 영역의 **유일한 기회**다.
> 반대로 전체 브랜치 리뷰는 PR 봇과 범위가 정확히 같으므로, **같은 차원으로 돌려 예행연습**한다.
> PR에 올라간 뒤에야 Major를 발견하는 일이 줄어든다.

> **경계**: GitHub에 올라간 PR의 리뷰는 CI에서 도는 `pr-review` 봇이 담당한다.
> 이 스킬은 로컬 브랜치의 단계별 점검·PR 전 자가 점검 용도다.

## 시작 전 필수

**`.claude/review-severity.md`를 읽는다.** 등급(🔴 Critical / 🟠 Major / 🟡 Minor / 💡 Note) 정의와
전체 판정 규칙, 그리고 **"필터는 찾을 때가 아니라 달 때 건다"** 원칙이 거기에 있다.
등급 정의를 이 스킬에 복사해 두지 않는 이유는 PR 봇과 어휘가 갈라지면 안 되기 때문이다.

## 실행 순서

### 0단계: 작업 컨텍스트 파악

사용자가 "~를 구현했어", "~를 수정했어", "이번에 ~를 작업했어" 등 작업 내용을 함께 제공한 경우,
그 내용을 기억해두고 리뷰 전 과정에서 중점 기준으로 삼는다.
제공하지 않은 경우에는 diff에서 작업 의도를 스스로 파악한다.

### 1단계: 리뷰 모드·범위 파악

```bash
# 현재 브랜치와 작업 트리 상태
git branch --show-current
git status --porcelain

# 이번 단계 변경 (staged + unstaged)
git diff HEAD

# untracked 새 파일 목록 — git diff에 안 잡히므로 Read로 파일을 직접 읽는다
git ls-files --others --exclude-standard

# 커밋된 이전 단계 (배경 컨텍스트)
git log develop..HEAD --oneline
git diff develop...HEAD --stat
```

작업 트리 상태로 리뷰 모드를 결정한다.

- **작업 트리에 변경이 있으면 (미커밋 수정 또는 untracked 파일) → 단계 리뷰**:
  그 변경이 리뷰 초점이다. untracked 파일은 diff에 없으므로 반드시 파일을 직접 읽어 리뷰 대상에 포함한다.
  커밋된 이전 단계(`develop...HEAD`)는 다시 리뷰하지 않고 이번 변경과의 일관성 확인용 배경으로만 쓴다.
- **작업 트리가 깨끗하고 브랜치에 커밋이 있으면 → 전체 브랜치 리뷰**:
  `git diff develop...HEAD` 전체를 리뷰한다. **3-B단계의 4차원만 본다.**
- 둘 다 없으면 "리뷰할 변경이 없습니다"라고 알리고 종료한다.

> **병렬 작업 중이면 범위를 한정한다.** `feature-cycle`로 여러 묶음을 동시에 돌리는 중이라면
> 작업 트리에 다른 묶음의 미완성 변경이 섞여 있다. 이번 묶음의 서비스 디렉터리로 범위를 제한하고,
> 리포트 머리에 "범위: `services/backend/` 한정"을 명시한다.

### 2단계: 컨텍스트 파악

diff만으로 판단하기 어려운 경우 변경된 파일의 전체 내용을 읽어 더 넓은 맥락을 파악한다.
특히 다음 상황에서는 반드시 원본 파일을 읽는다:
- 함수 시그니처나 클래스 구조가 변경된 경우
- 새 파일이 추가된 경우
- 기존 로직을 대폭 수정한 경우

**그리고 diff 밖으로 나간다.** 바뀐 함수·DTO·이벤트 필드의 **호출부와 반대편 소비자**를 찾아 읽는다.
diff 안에만 머물면 cross-file 차원(3-A ⑦ / 3-B ③)이 원천적으로 작동하지 않는다.

또한 변경된 파일이 속한 서비스의 CLAUDE.md(`services/backend/CLAUDE.md`,
`services/pipeline-worker/CLAUDE.md` 등)를 읽어 해당 서비스의 코딩 규칙을 파악한다.

### 3-A단계: 단계 리뷰 — 9영역

> **찾기 단계에서는 등급으로 거르지 않는다.** 발견한 것은 사소해 보여도 일단 다 적고,
> 등급 분류는 4단계(리포트)에서 한다. (`review-severity.md` §3)

**① 규칙 준수 (Conventions)**
- 루트 `CLAUDE.md`, `.claude/CLAUDE.md`에 명시된 규칙을 위반하지 않았는가?
- 해당 서비스의 CLAUDE.md 규칙(패키지 구조, 컨트롤러에 비즈니스 로직 없음, Flyway migration 등)을 지켰는가?

**② 아키텍처**
- 전체 데이터 흐름(pipeline-worker → RabbitMQ → ai-engine → Neo4j → backend → web-dashboard)과 일관성이 있는가?
- 레이어 경계를 지켰는가? (controller는 위임만, 비즈니스 로직은 service에만)
- 서비스 간 책임 분리가 올바른가? (backend가 직접 Neo4j를 쓰거나 pipeline-worker가 backend DB를 직접 건드리는 등)
- 새로운 의존성이나 결합이 생겼다면 의도한 것인가?

**③ 정확성 (Correctness)**
- 변경된 코드가 의도한 대로 동작하는가?
- 엣지 케이스(빈 값, null, 경계값, 빈 컬렉션, 중복 이벤트)를 누락하지 않았는가?
- 잠재적 런타임 오류, NullPointerException, 경쟁 조건은 없는가?
- 로직 오류, 잘못된 조건문, 오프-바이-원 오류는 없는가?
- API 계약, 데이터 타입, 반환값이 올바른가?

**④ 보안 (Security)**
- 시크릿·API 키·토큰이 코드나 설정 파일에 **하드코딩**되어 있지 않은가?
- 토큰·암호화 키·webhook 시크릿이 **로그에 원문으로** 찍히지 않는가? (예외 메시지·`toString()` 포함)
- **권한 검사가 누락되지 않았는가** — 요청자가 그 project/integration의 소유자인지 확인하는가?
  (IDOR: id만 알면 남의 데이터를 읽을 수 있는 엔드포인트)
- webhook 서명 검증, OAuth state 검증을 건너뛰지 않았는가?
- SQL 인젝션, XSS, 인증 우회 여지는 없는가?

**⑤ 개인정보 (Privacy)**
> 이 레포는 OAuth 토큰·암호화 키·Jira 개인정보·Slack/Discord 메시지 원문이 **실제로 흐르는** 코드다.
- 저장하면 안 되는 원문(메시지 본문, 이메일, 실명)이 새로 저장·전파되지 않는가?
- 외부(LLM 프롬프트, 로그, 응답 payload)로 나가는 데이터에 개인정보가 섞이지 않는가?
- `docs/jira-personal-data-policy.md`의 삭제 규칙(closed/access_lost)이 적용되어야 할 경로인데 빠지지 않았는가?
- 연동 해제(revoke) 시 지워야 할 데이터가 남지 않는가?

**⑥ 테스트 커버리지**
- TDD 순서를 지켰는가? (테스트 없이 구현 코드만 추가했으면 명시 — DTO/설정 클래스 등 예외 제외)
- **어떤 케이스가 빠졌는가?** 테스트가 "있다"에서 멈추지 않는다. 실패 경로, 경계값,
  예외 분기, 빈 응답, 중복 호출 중 검증되지 않은 것을 지목한다.
- **결함이 있어도 통과하는 테스트**는 없는가? (단언이 너무 느슨하거나, 가짜 객체가 구분을 못 하는 경우)
- 테스트가 삭제·`@Disabled`·skip 처리되지 않았는가?

**⑦ cross-file 정합성**
> 서비스가 4개로 갈려 있고 계약이 파일을 넘나든다. **로컬 리뷰에서 가장 얇아지기 쉬운 영역이다.**
- `NormalizedEvent` 필드를 바꿨는데 **ai-engine consumer/handler**가 그대로인가? `docs/normalized-event.md`는 갱신됐는가?
- Flyway migration과 JPA Entity가 어긋나지 않는가? (`ddl-auto: validate`라 어긋나면 기동 실패)
- backend DTO를 바꿨는데 web-dashboard의 타입·호출부가 그대로인가?
- 새 provider를 추가했는데 checkpoint provider 제약(CHECK 제약·enum)에 값이 안 들어갔는가?
- 설정 키를 추가했는데 `infra/docker/.env.example`·compose에 빠지지 않았는가?

**⑧ 유지보수 (재사용성 · 단순화 · 데드 코드)**
> **이 영역은 로컬 전용이다. PR 봇은 보지 않는다 — 여기서 못 잡으면 아무도 안 잡는다.**
- 유사한 코드가 이미 있는데 중복 작성했는가? 공통 유틸/헬퍼로 추출할 수 있는 로직이 있는가?
- 더 간결하게 표현할 수 있는가? 불필요한 복잡성·과도한 추상화는 없는가?
- **이번 변경으로 고아가 된 코드**는 없는가? 더 이상 호출되지 않는 메서드, 사용처가 사라진
  import·변수·상수·DTO 필드, 도달 불가능해진 분기 → **이 변경에서 제거해야 할 대상**
- 교체된 구현의 잔재(주석 처리한 옛 코드, 참조 없는 설정 키·CSS 클래스·테스트 픽스처)가 남았는가?
- 변경과 무관한 **기존** 데드 코드는 제거 대상이 아니라 💡 Note로만 언급한다 (전역 CLAUDE.md 규칙)

**⑨ 효율성 (Performance)**
- N+1 쿼리, 루프 내 과도한 연산, 불필요한 객체 생성은 없는가?
- Neo4j 쿼리가 인덱스를 타는가? 전체 스캔을 유발하지 않는가?
- 불필요한 외부 API 왕복, 배치로 묶을 수 있는 반복 호출은 없는가?

### 3-B단계: 전체 브랜치 리뷰 — PR 봇과 동일한 4차원

**작업 트리가 깨끗할 때만 이 경로를 탄다.** 단순화·재사용성·네이밍은 **보지 않는다** —
이미 단계 리뷰에서 소진했고, 여기서 다시 꺼내면 PR 직전에 커밋만 늘어난다.

**① correctness** — 3-A ③과 동일하되, **브랜치 전체가 하나로 맞물리는지**를 본다.
단계별로는 맞았지만 합쳐 놓으면 어긋나는 것(앞 단계에서 만든 가정을 뒤 단계가 깬 경우)이 표적이다.

**② security + privacy** — 3-A ④⑤와 동일. 브랜치 전체 diff에서 다시 훑는다.
**머지 후 발견하면 진짜 아픈 유일한 축**이라 중복을 감수한다.

**③ cross-file 정합성** — 3-A ⑦과 동일. **여기서 반드시 diff 밖 파일을 연다.**
브랜치 전체에서 바뀐 계약(`NormalizedEvent`, DTO, migration, 설정 키)을 모아
각각의 **반대편**을 하나씩 확인한다.

**④ behavioral — 의도 대비 실제 동작**
- 입력: 사용자가 설명한 작업 내용 + `git log develop..HEAD` 커밋 메시지
  + **`pr-description` 스킬로 만든 본문 초안이 있으면 그것**
- "말한 것은 X인데 코드는 Y를 한다"를 찾는다.
- 말한 것 중 **코드에 없는 것**도 찾는다 (하겠다고 적어놓고 빠진 항목).
- 이 차원은 PR 봇이 본문을 입력으로 다시 수행한다. 여기서 미리 걸러두면 봇 왕복이 줄어든다.

> 본문 초안이 아직 없으면 그 사실을 리포트에 적는다 — behavioral을 **커밋 메시지만으로** 수행했다는
> 뜻이고, 봇 단계에서 새 지적이 나올 여지가 남아 있다는 신호다.

### 4단계: 리포트 출력

**여기서 처음으로 등급을 매긴다.** `review-severity.md` 기준으로 3단계에서 모은 항목을
**한 번에** 훑어 등급을 확정한다(§4의 보정 지점 = 여기). 그 뒤 아래 형식으로 한국어 출력한다.

### 상세 리뷰

#### ✅ 잘된 점
- 잘 작성된 부분을 구체적으로 언급한다 (형식적인 칭찬은 생략)

#### 🔴 Critical — 머지 금지
지금 배포되면 사용자/데이터에 피해가 발생하는 항목만.

- **[파일명:라인]** 문제 설명
  - 현재 코드: `코드 스니펫`
  - 이유: 왜 문제인지
  - 제안: 어떻게 고칠지 (코드 예시 포함)

#### 🟠 Major — 머지 전 수정
코드가 의도대로 동작하지 않는 항목. 형식은 Critical과 동일.

#### 🟡 Minor — 이번에 고치면 좋음
동작은 맞지만 고치면 나아지는 항목.

- **[파일명:라인]** 개선 제안

## 리포트 작성 원칙

- **구체적으로**: "이 코드는 문제가 있습니다" 대신 파일명, 라인 번호, 코드 스니펫을 함께 제시한다.
- **근거 기반**: 모든 지적 사항에 이유(why)를 설명한다.
- **균형 잡힌 시각**: 문제점만 열거하지 않고, 잘된 부분도 구체적으로 언급한다.
- **실행 가능한 제안**: 추상적인 조언보다 고칠 수 있는 코드 예시를 제공한다.
- **없는 문제를 만들지 않기**: 확신이 없으면 **등급을 한 단계 낮춘다. 다만 항목을 빼지는 않는다.**
  (찾기 단계에서 거르지 않는 이유는 `review-severity.md` §3)
- **사용자 작업 내용이 있으면 우선순위**: 사용자가 직접 언급한 기능·변경 영역을 더 깊이 분석한다.

## 리뷰 후

- 지적 항목은 **반영/디퍼/현행 유지 추천을 붙인 표**로 모아 사용자에게 한 번에 묻는다.
  반영 여부를 임의로 정하지 않는다.
- **반영하지 않기로 한 항목은 문서(`docs/*-known-issues.md`)에 남긴다.**
  "기록해뒀다"고 말만 하고 실제로 안 남기지 않는다.
- 커밋하지 않는다. 사용자가 코드를 읽고 직접 결정한다.
