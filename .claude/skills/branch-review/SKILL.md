# Branch Review 스킬

현재 브랜치의 작업 내용을 한국어로 상세 리뷰한다. 두 가지 모드로 동작한다.

- **단계 리뷰 (기본)**: 미커밋 작업 트리(untracked 새 파일 포함)가 리뷰 초점. 커밋된 이전 단계는 이미 리뷰를 거쳤으므로 배경 컨텍스트로만 쓴다.
- **전체 브랜치 리뷰**: 작업 트리가 깨끗하면 `develop` 대비 브랜치 전체를 리뷰한다 (PR 생성 전 최종 점검).

> 경계: GitHub에 올라간 PR 리뷰는 내장 `/review`를 쓴다. 이 스킬은 로컬 브랜치의 단계별 점검·PR 전 자가 점검 용도다.

## 실행 순서

### 0단계: 작업 컨텍스트 파악

사용자가 "~를 구현했어", "~를 수정했어", "이번에 ~를 작업했어" 등 작업 내용을 함께 제공한 경우, 그 내용을 기억해두고 리뷰 전 과정에서 중점 기준으로 삼는다. 제공하지 않은 경우에는 diff에서 작업 의도를 스스로 파악한다.

### 1단계: 리뷰 모드·범위 파악

```bash
# 현재 브랜치와 작업 트리 상태
git branch --show-current
git status --porcelain

# 이번 단계 변경 (staged + unstaged)
git diff HEAD

# untracked 새 파일 목록 — git diff에 안 잡히므로 Read로 파일을 직접 읽는다
git ls-files --others --exclude-standard

# 커밋된 이전 단계 (배경 컨텍스트)
git log develop..HEAD --oneline
git diff develop...HEAD --stat
```

작업 트리 상태로 리뷰 모드를 결정한다.

- **작업 트리에 변경이 있으면 (미커밋 수정 또는 untracked 파일) → 단계 리뷰**: 그 변경이 리뷰 초점이다. untracked 파일은 diff에 없으므로 반드시 파일을 직접 읽어 리뷰 대상에 포함한다. 커밋된 이전 단계(`develop...HEAD`)는 다시 리뷰하지 않고 이번 변경과의 일관성 확인용 배경으로만 쓴다.
- **작업 트리가 깨끗하고 브랜치에 커밋이 있으면 → 전체 브랜치 리뷰**: `git diff develop...HEAD` 전체를 리뷰한다 (PR 생성 전 최종 점검).
- 둘 다 없으면 "리뷰할 변경이 없습니다"라고 알리고 종료한다.

### 2단계: 컨텍스트 파악

diff만으로 판단하기 어려운 경우 변경된 파일의 전체 내용을 읽어 더 넓은 맥락을 파악한다.
특히 다음 상황에서는 반드시 원본 파일을 읽는다:
- 함수 시그니처나 클래스 구조가 변경된 경우
- 새 파일이 추가된 경우
- 기존 로직을 대폭 수정한 경우

또한 변경된 파일이 속한 서비스의 CLAUDE.md(`services/backend/CLAUDE.md`, `services/pipeline-worker/CLAUDE.md` 등)를 읽어 해당 서비스의 코딩 규칙을 파악한다.

### 3단계: 리뷰 수행

아래 8개 영역을 빠짐없이 분석한다. 사용자가 작업 내용을 명시한 경우 해당 영역을 더 깊이 파고든다.

**CLAUDE.md 규칙 준수**
- 프로젝트 루트 `CLAUDE.md`와 `.claude/CLAUDE.md`에 명시된 규칙을 위반하지 않았는가?
- 해당 서비스의 CLAUDE.md 규칙(패키지 구조, 컨트롤러에 비즈니스 로직 없음, Flyway migration, TDD 순서 등)을 지켰는가?
- TDD 규칙: 테스트 없이 구현 코드만 추가한 경우 명시한다 (단, DTO/설정 클래스 등 예외 항목은 제외)

**아키텍처**
- 이 변경이 전체 아키텍처(CLAUDE.md의 데이터 흐름: pipeline-worker → RabbitMQ → ai-engine → Neo4j → backend → web-dashboard)와 일관성이 있는가?
- 레이어 경계를 지켰는가? (controller는 위임만, 비즈니스 로직은 service에만)
- 서비스 간 책임 분리가 올바른가? (예: backend가 직접 Neo4j를 쓰거나 pipeline-worker가 backend DB를 직접 건드리는 등의 위반)
- 새로운 의존성이나 결합이 생긴다면 의도한 것인가?

**정확성 (Correctness)**
- 변경된 코드가 의도한 대로 동작하는가?
- 엣지 케이스(빈 값, null, 경계값)를 누락하지 않았는가?
- API 계약, 데이터 타입, 반환값이 올바른가?

**버그 (Bugs)**
- 잠재적 런타임 오류, NullPointerException, 경쟁 조건은 없는가?
- 로직 오류, 잘못된 조건문, 오프-바이-원 오류는 없는가?
- 보안 취약점(SQL 인젝션, XSS, 인증 우회 등)은 없는가?

**재사용성 (Reusability)**
- 유사한 코드가 다른 곳에 이미 있는데 중복 작성했는가?
- 공통 유틸리티나 헬퍼로 추출할 수 있는 로직이 있는가?

**단순화 (Simplification)**
- 더 간결하게 표현할 수 있는 로직이 있는가?
- 불필요한 복잡성이나 과도한 추상화는 없는가?

**데드 코드 (Dead Code)**
- 이번 변경으로 고아가 된 코드는 없는가? — 더 이상 호출되지 않는 메서드, 사용처가 사라진 import·변수·상수·DTO 필드, 도달 불가능해진 분기 (이건 이 변경에서 제거해야 할 대상)
- 교체된 구현의 잔재가 남아 있지 않은가? — 주석 처리로 남긴 옛 코드, 더 이상 참조되지 않는 설정 키·CSS 클래스·테스트 픽스처
- 변경과 무관한 기존 데드 코드를 발견하면 제거 대상이 아니라 💡 Notes로만 언급한다 (전역 CLAUDE.md 규칙)

**효율성 (Efficiency)**
- 명백한 성능 문제(N+1 쿼리, 루프 내 과도한 연산, 불필요한 객체 생성)는 없는가?
- 더 나은 자료구조나 알고리즘을 쓸 수 있는가?

### 4단계: 리포트 출력

아래 형식을 정확히 따라 한국어로 출력한다.

## 브랜치 리뷰: `<브랜치명>`

**작업 내용**: <사용자가 명시한 경우 기재, 없으면 diff에서 파악한 작업 의도 한 줄>

### 종합 평가

> 한 문단으로 전체 변경의 목적과 품질을 요약. 큰 문제가 없으면 긍정적으로 시작하되, 핵심 개선점을 명확히 언급한다.

---

### 상세 리뷰

#### ✅ 잘된 점
- 잘 작성된 부분을 구체적으로 언급한다 (형식적인 칭찬은 생략)

#### 🔴 반드시 수정 (Critical)
버그, 보안, 데이터 손실 위험, CLAUDE.md 핵심 규칙 위반이 있는 항목만 포함한다.

- **[파일명:라인]** 문제 설명
  - 현재 코드: `코드 스니펫`
  - 이유: 왜 문제인지
  - 제안: 어떻게 고칠지 (코드 예시 포함)

#### 🟡 개선 권장 (Suggestions)
수정하면 코드 품질이 높아지지만 필수는 아닌 항목.

- **[파일명:라인]** 개선 제안

#### 💡 참고 사항 (Notes)
스타일, 작은 단순화, 미래를 위한 고려사항.

## 리포트 작성 원칙

- **구체적으로**: "이 코드는 문제가 있습니다" 대신 파일명, 라인 번호, 코드 스니펫을 함께 제시한다.
- **근거 기반**: 모든 지적 사항에 이유(why)를 설명한다.
- **균형 잡힌 시각**: 문제점만 열거하지 않고, 잘된 부분도 구체적으로 언급한다.
- **실행 가능한 제안**: 추상적인 조언보다 고칠 수 있는 코드 예시를 제공한다.
- **없는 문제를 만들지 않기**: 확실한 문제만 Critical로 분류하고, 불확실하면 Suggestion 또는 Notes에 넣는다.
- **사용자 작업 내용이 있으면 우선순위**: 사용자가 직접 언급한 기능·변경 영역을 다른 부분보다 더 깊이 분석한다.
