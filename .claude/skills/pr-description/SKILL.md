# PR Description 스킬

PR 본문 초안을 만든다. **PR을 생성하지는 않는다** — 본문만 만들고 사용자가 직접 연다.

## 왜 PR을 열기 *전에* 하는가

리뷰 봇의 **behavioral 차원이 PR 본문을 입력으로 쓴다.**
"본문은 X라는데 diff는 Y다"를 검증하려면 본문이 먼저 있어야 한다.
빈 본문으로 열면 그 차원이 통째로 무의미해진다.

## 이 스킬의 핵심 규칙

> **에이전트가 써도 되는 칸과, 절대 쓰면 안 되는 칸이 갈려 있다.**

| 종류 | 칸 | 에이전트가 |
|---|---|---|
| 경로에서 기계적으로 나옴 | `확인 필요` 체크 (앞의 3개) | **채운다 — 사람보다 정확하다** |
| diff에서 파생 가능 | `주요작업` · `시나리오` · `검증`-자동 | **초안**을 쓴다. 사용자가 검수 |
| **사용자 머릿속에만 있음** | `배경` · `범위 밖` · `검증`-수동 · **외부 연동 정책 체크** | **쓰면 안 된다 — 물어서 받아적는다** |

**사람 칸을 에이전트가 쓰면 안 되는 이유**: diff로 만든 글로 diff를 검증하면 **동어반복**이다.
봇의 behavioral이 항상 통과해 버리고, 팀원이 `배경`을 읽어도 물을 것이 없어진다.

**`확인 필요` 체크를 에이전트가 채우는 이유**는 정반대다. 자기신고의 실패 양상은
*"작성자가 안 위험하다고 판단해 체크를 안 함"*인데, **그 판단이 정확히 팀원이 검증할 대상**이다.
경로 대조는 판단이 섞이지 않으므로 그 필터를 없애지 않는다.

## 실행 순서

### 1단계: 변경 수집

```bash
git branch --show-current
git log develop..HEAD --oneline
git diff --name-only develop...HEAD
git diff --stat develop...HEAD
```

작업 트리에 미커밋 변경이 있으면 **먼저 알린다** — PR에 안 들어갈 내용이 초안에 섞이면 안 된다.

### 2단계: `확인 필요` 체크박스 — 경로 대조 (자동)

`git diff --name-only develop...HEAD` 결과를 아래 글롭과 대조한다.
**판단하지 않는다. 걸리면 체크한다.**

| 체크 항목 | 경로 글롭 |
|---|---|
| **Flyway migration** | `services/backend/src/main/resources/db/migration/V*__*.sql` |
| **서비스 간 계약** | `services/pipeline-worker/src/main/java/**/dto/NormalizedEvent.java`<br>`services/pipeline-worker/src/main/java/**/normalizer/**`<br>`services/ai-engine/graph/event_handler.py`<br>`services/ai-engine/graph/consumer.py`<br>`services/backend/src/main/java/**/dto/**`<br>`clients/web-dashboard/src/**/api/**`, `clients/web-dashboard/src/**/types/**`<br>`docs/normalized-event.md` |
| **그래프 스키마** | `services/ai-engine/graph/schema.py`<br>`services/ai-engine/graph/builder.py`<br>`services/ai-engine/graph/writes.py`<br>`services/ai-engine/graph/reference_builder.py`<br>`docs/graph-schema.md` |

> 글롭이 안 걸렸는데 실제로는 계약이 바뀐 경우가 있다(새 경로 추가 등).
> **글롭은 하한선이지 상한선이 아니다** — diff를 읽다가 계약 변경이 보이면 체크하고, 그 사실을 알린다.

**네 번째 항목 `외부 연동 정책 (수집 범위·삭제·권한)`은 자동으로 체크하지 않는다.**
아래 경로가 걸리면 **체크 대신 3단계에서 사용자에게 묻는다** — 정책이 실제로 바뀌었는지는 판단이 필요하고,
그 판단이 팀원의 검증 대상이기 때문이다.

```
services/backend/src/main/java/com/history/backend/auth/**
services/*/src/main/java/**/common/crypto/**
services/*/src/main/java/**/*OAuth*.java, **/*Token*.java, **/*Credential*.java
services/pipeline-worker/src/main/java/**/webhook/**
services/ai-engine/graph/privacy.py
docs/jira-personal-data-policy.md
```

세 항목 모두 안 걸리고 정책 질문에도 "아니다"면 **`해당 없음`을 체크한다.**

### 3단계: 사용자에게 묻는다 (핵심 단계)

**채팅에 질문을 펼쳐 놓고 답을 기다린다.** 선택지 UI(`AskUserQuestion`)를 쓰지 않는다.
초안을 먼저 보여준 뒤 묻는다 — 사용자가 뭘 채워야 할지 보이는 상태에서 답하는 게 빠르다.

물을 것 (3~4개, 상황에 따라 가감):

1. **배경 — 왜 지금 이걸 하나?** (diff 요약 말고, 이 작업을 하기로 한 이유)
2. **범위 밖 — 일부러 안 한 것이 있나?** 있다면 이유는?
3. **검증(수동) — 실기동이나 eval을 돌렸나?** 안 돌렸으면 그대로 "미완"으로 적는다.
4. (조건부) **외부 연동 정책** — 수집 범위·삭제 규칙·권한 중 바뀐 것이 있나?
5. (조건부) **게이트에서 특히 봐줬으면 하는 것**이 있나?

> **답변은 다듬되 늘리지 않는다. 사용자가 말하지 않은 것은 쓰지 않는다.**
> 한 줄로 답하면 한 줄로 적는다. 문장을 풍성하게 만들려고 diff에서 내용을 끌어오지 않는다.
> "안 돌렸다"는 답을 "부분 검증함" 같은 말로 바꾸지 않는다.

사용자가 답하지 않고 넘어간 칸은 **비워 두고 `<작성 필요>`로 표시한다.** 지어내지 않는다.

### 4단계: 본문 조립

`.github/PULL_REQUEST_TEMPLATE.md`와 같은 순서로 쓴다.

```markdown
## 배경
<사용자 답변 그대로. 왜 지금 이걸 하는가. 이 칸만 서술형(`~다`)으로 쓴다.>

## 주요작업
### <작업 이름>
- 설명
### <작업 이름>
- 설명

## 시나리오
1. <사용자 관점의 동작 흐름>

## 확인 필요
- [x] Flyway migration
- [ ] 서비스 간 계약 (NormalizedEvent / DTO↔프론트 타입)
- [ ] 그래프 스키마
- [ ] 외부 연동 정책 (수집 범위·삭제·권한)
- [ ] 해당 없음

## 검증
- 자동: <추가·수정된 테스트 범위>
- 수동: <실기동·eval 결과 또는 "미완">

## 범위 밖
- <일부러 안 한 것과 이유. 없으면 "없음">
```

**어투와 눈높이**

- **`배경`만 서술형(`~다`)으로 쓴다.** 사용자가 말한 이유를 문장으로 옮기는 칸이라
  명사형으로 압축하면 뉘앙스가 깎인다. ("~병목을 크게 느꼈다. ~개선하려는 것이 목적이다.")
- **나머지 칸은 명사형으로 쓴다.** ("~를 추가함" / "~ 처리 분리" — "~를 추가했습니다" 아님)
- **코드 세부를 쓰지 않는다.** 클래스명·메서드명 나열 대신 무엇이 달라졌는지를 쓴다.
- **다른 파트 사람이 봐도 이해되게** 쓴다. 변경 파일 목록은 GitHub이 보여주므로 쓰지 않는다.

**넣지 않는 칸**: 변경 파일 목록(GitHub이 보여줌) · 리뷰 포인트(봇의 몫) · 테스트 통과 체크(CI의 몫).

### 5단계: 출력

- 완성본을 **채팅에 그대로 출력**하고, 동시에 파일로 저장해 `gh pr create --body-file`에 쓸 수 있게 한다.
- **PR을 생성하지 않는다.** `gh pr create`를 실행하지 않는다 — 사용자가 직접 연다.
- 아직 안 채워진 칸(`<작성 필요>`)이 있으면 목록으로 알린다.
- 리뷰어를 지정하지 말라고 한 줄 덧붙인다:

> PR을 열 때 **리뷰어는 지정하지 않습니다.** 봇 리뷰를 받고 반영이 끝난 뒤 지정하면,
> 그 구간 동안 팀원에게 알림이 가지 않습니다.

## 갱신 모드 — 봇 지적을 반영한 뒤

이미 PR이 열려 있는 상태에서 호출되면(또는 사용자가 "본문 갱신"이라고 하면) 초안을 새로 만들지 않고
**기존 본문과 새 커밋의 차이만** 반영한다.

```bash
gh pr view <N> --json body --jq .body
git log <PR 오픈 시점>..HEAD --oneline
```

- **가장 자주 빠뜨리는 단계다.** 봇 지적을 반영해 **동작이 바뀌었으면 `시나리오`가 낡는다.**
- 실기동을 새로 돌렸으면 `검증`-수동을 갱신한다.
- `확인 필요` 체크는 **파일이 새로 추가됐을 수 있으므로 2단계를 다시 돌린다.**
- 본문을 바꿀지는 사용자가 결정한다. 초안을 보여주고 묻는다.
